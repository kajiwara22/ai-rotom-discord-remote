## コンテキスト

### 状況 (Situation)

現在の ai-rotom は Discord スラッシュコマンド (`/ask`, `/reset`) のみを受け付ける単一チャネルの Bot である。
アーキテクチャは Cloudflare Worker（Discord Interactions 受信・署名検証・転送）+ Raspberry Pi（AI 処理・MCP 接続・会話管理）のハイブリッド構成。
セッションはチャンネル単位（`channel:{channelId}`）、システムプロンプトは `tool-definitions.ts` にハードコードされている。
フロントエンドは存在せず、UI は Discord クライアントが担う。

### 課題 (Complication)

家族（娘たち）が PC のブラウザからチャットベースで AI に質問できる家庭用ツールとしても使いたい。
Discord アカウントを持たない家族でも利用でき、かつ以下の要件を満たす必要がある：

1. **ユーザーごとのシステムプロンプト調整**: 各ユーザーの年齢・語彙・関心に合わせた応答スタイルのカスタマイズ
2. **複数セッションの切り替え**: トピックごとに会話を分け、過去の会話スレッドに戻って続けられる

### 論点 (Question)

以下の設計判断が必要：
1. Web UI をどこに配置し、どのように配信するか
2. 認証・ユーザー識別の方式
3. セッション管理のキー構造と切り替え方式
4. システムプロンプトの管理方式
5. Discord 用と Web 用で AI 処理の共通化をどう図るか

### 検討した選択肢

- **案1: Pi 一体型（rpi-bridge がフロント配信も担当）**
  - 概要: `rpi-bridge/src/index.ts` の HTTP サーバーに HTML/JS/CSS の配信と Web 用 API を追加。全機能が Pi 上で完結。
  - メリット: シンプルな構成、デプロイ不要、LAN 内で完結、追加インフラ不要
  - デメリット: Pi の負荷がやや増加（静的ファイル配信は軽量のため実質問題なし）

- **案2: フロントを Cloudflare Pages に分離**
  - 概要: チャット UI を Pages にデプロイし、API だけ Pi に向ける
  - メリット: Pi の負荷軽減、CDN 配信
  - デメリット: 認証の仕組みが別途必要（Cloudflare Access 等）、構成が複雑化

- **案3: Worker にフロント配信と API プロキシを追加**
  - 概要: 既存 Worker に静的配信＋Web 用プロキシエンドポイントを追加
  - メリット: 既存インフラの活用
  - デメリット: Discord の 3 秒制約と混在する複雑さ、Worker の無料枠消費

- **案4: 認証あり（Cloudflare Access ワンタイムPIN）**
  - 概要: 外出先からのアクセスも想定した認証
  - メリット: セキュリティ堅牢
  - デメリット: 自宅 LAN 内利用には過剰、娘たちの操作が煩雑になる

- **案5: ユーザー名選択方式（認証なし）**
  - 概要: ブラウザで開いたらユーザー名を選択/入力するだけ
  - メリット: シンプル、LAN 内なら十分なセキュリティ
  - デメリット: LAN 外からは利用不可（今回の要件では許容）

- **案6: セッション管理: DB 上で user_id + session_id の複合キー**
  - 概要: `conversations` テーブルに `user_id` と `session_name` カラムを追加し、`user:{userId}:session:{sessionId}` をキーとする
  - メリット: 既存の Discord チャンネル単位セッション（`channel:{channelId}`）と共存可能
  - デメリット: テーブル構造の変更が必要

- **案7: システムプロンプト: system_prompts テーブルで管理**
  - 概要: DB にユーザーごとのプロンプトを保存
  - メリット: 永続化、管理 UI から編集可能、ユーザー追加が容易
  - デメリット: テーブル追加・管理 UI の実装が必要

- **案8: システムプロンプト: 設定ファイル（JSON）**
  - 概要: JSON ファイルで管理
  - メリット: 実装が単純
  - デメリット: 変更時に再起動が必要、管理 UI との連携が面倒

## 決定

### 全体アーキテクチャ: 案1（Pi一体型）を採用する

rpi-bridge の HTTP サーバーを拡張し、Web チャット UI の配信と API の両方を Raspberry Pi 上で完結させる。
追加のインフラ（Pages, Worker 拡張）は不要。LAN 内利用に最適化されたシンプルな構成を維持する。

### 認証方式: 案5（ユーザー名選択方式）を採用する

自宅 LAN 内のみの利用を前提とし、認証は行わない。ユーザーはブラウザでユーザー名を選択/入力するだけで利用開始できる。
初回利用時にユーザー名を入力し、以降はブラウザの localStorage に保存して自動選択する。

### セッション管理: 案6（user_id + session_id 複合キー）を採用する

`conversations` テーブルに `user_id` と `session_name` カラムを追加する。
セッションキーは Web 用を `user:{userId}:session:{sessionId}`、Discord 用は既存の `channel:{channelId}` を維持し、両者を共存させる。

- セッションは最初のメッセージ送信時に自動作成される（明示的な作成操作は不要）
- 自動作成時のセッション名は `{YYYY-MM-DD HH:mm} - {先頭30文字}` 形式（例: `2025-07-26 14:30 - ピカチュウの育成について教えて`）
  - **更新（[ADR-0005](./ADR-0005.md)）**: 日付プレフィックスは廃止。名前は本文（先頭40文字）のみとし、日時は一覧側で相対表示する
- ユーザーは後からセッション名を自由に変更できる
- セッション一覧から過去の会話スレッドを選択して続けられる

### システムプロンプト: 案7（DBテーブル管理）を採用する

`system_prompts` テーブルを追加し、ユーザーごとのカスタムプロンプトを格納する。

- デフォルト: 既存の `getSystemPrompt()` の内容を全ユーザーのデフォルトとする
- カスタマイズ: 管理者が Web UI または API 経由でユーザーごとに上書き可能
- プロンプト未設定のユーザーはデフォルトプロンプトを使用する
- ユーザー本人（娘たち）がプロンプトを編集することは想定せず、管理用 UI で親のみが操作する

### AI処理の共通化

`ai-service.ts` の `runAsk()` をリファクタリングし、AI 処理のコアロジック（`processAI()`）と応答配送（`deliverResponse()`）を分離する。
Discord 用は Webhook PATCH、Web 用は直接 HTTP レスポンスとする。

### CSSフレームワーク: MVP.css を採用する

> **差し替え済み（[ADR-0005](./ADR-0005.md)）**: MVP.css の classless 前提が
> レイアウトと表示モード切り替えの妨げになったため廃止し、自前 CSS（`style.css`）に
> 一本化した。外部 CDN・npm への非依存という原則は維持している。

classless CSS フレームワークである MVP.css を使用する。HTML タグにクラスを付与せず、セマンティックなマークアップのみでスタイリングが完結する。
CDN からではなく、`mvp.css` を rpi-bridge の静的ファイルとして配信する（Pi のネットワーク負荷と依存管理を避けるため）。

### プロンプト編集権限: 管理者ユーザーの概念は設けず、全ユーザーが自身のプロンプトを編集可能とする

> **差し替え済み（[ADR-0004](./ADR-0004.md)）**: 実利用者が小 1・小 5 の子どもであり、
> AI の人格を子どもが壊せる・他人の履歴を消せるといった事故が現実的だったため、
> 保護者操作を 4 桁 PIN + トークンで保護し、サーバー側でも強制する方式に変更した。
> アバターと文字サイズは見た目だけの設定として子ども自身に開放している。

実運用上は親が各ユーザーのプロンプトを設定するが、システム的に制限はかけない。
UI 上もシンプルに「設定」画面を全ユーザーに提供する。

### セッション一覧の表示順: 最終更新日時の降順とする

手動並び替えやピン留め機能は実装せず、シンプルに `updated_at DESC` でソートする。

### 画面構成: 1画面統合型を採用する

- **左ペイン**: セッション一覧（最終更新日時降順）＋ 新規チャット開始ボタン
- **右ペイン**: チャット本文（メッセージ履歴）＋ 入力欄
- **上部**: ユーザー名表示 ＋ ユーザー切り替え ＋ 設定ボタン
- 設定ボタンからプロンプト編集ダイアログを開く

セッション選択画面は設けず、チャット画面をメインの単一画面とする。
新規チャット開始時は、左ペインの先頭に新規セッションが追加され、自動的に選択状態となる。

### Web版AI応答: 同期方式を採用する

`POST /api/web/ask` はAI処理が完了するまで待ち、完了後に完全な応答を返す。
Discord と異なり3秒制約がないため、シンプルな同期方式で十分。
フロント側は `fetch` 中にスピナーを表示し、ユーザーに処理中であることを伝える。

### ユーザー管理: 初回利用時に自動作成する

ユーザーが未登録の名前でログインした場合、`users` テーブルに自動登録する。
事前のユーザー登録操作は不要。

### Web用APIエンドポイント

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/` | チャットUI配信（index.html） |
| GET | `/public/*` | 静的ファイル（`public/` 以下） |
| GET | `/api/users` | ユーザー一覧取得 |
| POST | `/api/users` | ユーザー作成（自動作成用、既存ならスキップ） |
| GET | `/api/users/:id/prompt` | システムプロンプト取得 |
| PUT | `/api/users/:id/prompt` | システムプロンプト更新 |
| POST | `/api/web/ask` | AI質問（`{user_id, session_id?, message}`） |
| POST | `/api/web/reset` | セッションリセット（`{user_id, session_id}`） |
| GET | `/api/sessions?user_id=xxx` | ユーザーのセッション一覧 |
| PUT | `/api/sessions/:id` | セッション名変更 |

### ツール定義

既存の28ツールは全ユーザー共通で利用可能とする。ユーザーごとのツール制限は行わない。

## 影響

### メリット

- 家族がブラウザ一つで AI アシスタントを利用できる
- ユーザーごとに応答スタイルを調整でき、各ユーザーに最適化された体験を提供できる
- トピックごとにセッションを分けることで、会話の文脈が混ざらない
- 追加インフラ不要で Pi 上に完結するため、運用コストが変わらない
- Discord Bot としての既存機能は影響を受けない

### デメリット・トレードオフ

- Pi の負荷がやや増加する（静的ファイル配信 + 追加の HTTP ハンドリング）
- DB スキーマ変更に伴うマイグレーションが必要
- ユーザー名選択方式のため、なりすましが技術的に可能（LAN 内の信頼を前提とする）
- プロンプト管理 UI の実装コストが発生する
- セッション管理の複雑度が増す（Discord 用と Web 用の2系統）

### 今後チームが意識すべきこと

1. **セッションキーの命名規則**: Discord 用 `channel:{channelId}` と Web 用 `user:{userId}:session:{sessionId}` を混同しないこと
2. **プロンプトのデフォルト値**: `getSystemPrompt()` の変更時は、全ユーザーのプロンプトが未設定の場合にのみ影響する。個別設定済みのユーザーには影響しない
3. **DB マイグレーション**: `conversations` テーブルの `ALTER TABLE` は既存データとの互換性を確認してから行う
4. **フロントエンドの依存**: 外部 CDN や npm パッケージに依存せず、vanilla JS + MVP.css（ローカル配信）で実装する。MVP.css はリポジトリに静的ファイルとして含める
5. **LAN 内限定**: ユーザー名選択方式のため、Pi の HTTP サーバーを LAN 外に公開しないこと（Cloudflare Tunnel の公開設定に注意）
