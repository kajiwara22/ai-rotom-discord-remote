# ADR-0018: 対戦記録の選出・先発の体数は battleFormat に応じて出し分ける

## ステータス

採用

> 実装に先立ってドメイン知識（利用者）に確認し、シングルは選出 3 体・先発 1 体、
> ダブルは選出 4 体・先発 2 体とした。未知の `battleFormat` はダブル扱いで fallback
> する（現状の記録はダブル中心のため）。

## コンテキスト

### 状況 (Situation)

対戦記録の Parquet（[ADR-0010](./ADR-0010.md)）には `battleFormat`（`single` /
`double`）があり、`get_match` がそのまま返している。一方で、AI へ渡す文言のうち
選出・先発の体数に触れる箇所は、**ダブル前提の「選出 4 体」「先発 2 体」で固定**
されている。

- `match-repository.ts` の `get_match` の `notes`（2 箇所）
- `tool-definitions.ts` の `get_match` の description
- `tool-definitions.ts` のシステムプロンプト（対戦振り返りの手順）

[ADR-0010](./ADR-0010.md) / [ADR-0012](./ADR-0012.md) 当時の記録はダブルのみだった
ため、この固定表記でも実害はなかった。

### 課題 (Complication)

シングルの対戦を振り返る際、AI が「選出 4 体」「先発 2 体」を前提に語ると、実データ
（選出 3 体・先発 1 体）と食い違う。`notes` は AI の判断を誘導する役割を持ち
（ADR-0010）、ここが誤っていると「選出が 1 体足りない」等の誤った指摘につながる。
実際には `battleFormat` は手元にあるため、固定表記にしておく理由がない。

### 論点 (Question)

1. 選出・先発の体数表記を `battleFormat` に応じて出し分けるか
2. 未知・欠損の `battleFormat` をどう扱うか
3. 修正範囲（`notes` / ツール description / システムプロンプト）をどこまでにするか

### 検討した選択肢 (Options)

- **案A: `battleFormat` に応じて出し分ける（採用）**
  - 概要: `single` なら選出 3・先発 1、`double` なら選出 4・先発 2 を動的に表記する。
  - メリット: シングル・ダブルどちらでも AI を誤誘導しない。
  - デメリット: notes 生成が `battleFormat` を見る分だけ複雑になる（ごく軽微）。
- **案B: 固定表記のまま（現状）**
  - メリット: 変更なし。
  - デメリット: シングルの対戦で誤誘導する。却下。

## 決定

### 体数表記は `battleFormat` に応じて出し分ける（案A）

- `single`（または `singles`）→ 選出 3 体・先発 1 体
- `double`（または `doubles`）→ 選出 4 体・先発 2 体
- 未知・欠損の値は**ダブル扱いで fallback** する（現状の記録がダブル中心のため。
  記録側が体数を明示するようになったら追随する）

### 修正範囲は notes・description・システムプロンプトの 3 箇所

- `match-repository.ts`: `get_match` の `notes` を動的表記に変更
- `tool-definitions.ts`: `get_match` の description を「体数は battleFormat に応じる」
  旨に変更（description はツール呼び出し前に参照されるため、両方の体数を併記する）
- `tool-definitions.ts`: システムプロンプトの「選出 4 体」を「シングル 3 体／ダブル
  4 体」に変更

### ADR-0010 / ADR-0012 の記述は書き換えない

「選出 4 体」「先発 2 体」という文言は当時のデータ（ダブル）を反映した歴史的記録
であり、決定を覆すものではない。採用済み ADR を書き換えず、本 ADR で現在の扱いを
定める（テンプレートの「一度採用した決定が覆る場合は新 ADR を作成」に従う）。

## 影響

### メリット

- シングル・ダブルどちらの対戦でも、選出・先発の体数を誤らない。
- 体数の知識がコード内の 1 関数（`selectionAndLeadSize`）に集約され、記録側の仕様が
  変わったときに追随しやすい。

### デメリット・トレードオフ

- notes の文言生成が `battleFormat` に依存する（軽微）。
- `get_match` の description は長くなる（両方の体数を併記するため）。ただしこれは
  静的な定義であり、毎ターンの再送コストは既存の範囲内（ADR-0006 の固定費と同質）。

### 今後チームが意識すべきこと

1. **体数の正はドメイン仕様**。`selectionAndLeadSize` に埋め込むのは現状の橋渡しであり、
   解析側 Parquet が選出・先発の体数を明示するようになったら、そちらを正として追従する。
2. **記録にシングルの行が増えたら、notes の文言が実データと一致するか確認する。**
3. **`battleFormat` の値の揺れ（`single`/`singles`、`double`/`doubles`）は関数内で
   吸収する**。呼び出し側で正規化しない。
