# ADR-0015: LLM モデルは実行時に切り替え可能とし、既定値と Web 利用者別上書きを保護者設定で管理する

## ステータス

採用

> 壁打ちで論点を 5 つに切り出し、以下の方針で確定した。**モデル名の差し替えではなく、
> 「モデル ID ＋ reasoning_effort ＋ max_tokens」を束ねたモデル定義を許可リストで持つ**
> 点が本 ADR の中心。実装済み（`model-registry.ts`、threading、フォールバック、DB/API、
> 保護者設定 UI）。許可リストの初期顔ぶれは `scripts/probe-models.sh` で実測して
> 追加済み（既定は deepseek-v4-pro。flash / glm / qwen 系を追加）。

## コンテキスト

### 状況 (Situation)

チャット（Discord / Web UI）の LLM 呼び出しは `rpi-bridge/src/ai-service.ts` の
`chatCompletion()` に集約されており、モデルは次のように**ハードコード**されている。

| 要素 | 現状 | 場所 |
|---|---|---|
| モデル名 | `const MODEL = "deepseek-v4-pro"` | `ai-service.ts:22` |
| `reasoning_effort` | `"low"` 固定 | `ai-service.ts:37` |
| `max_tokens` | `8192` 固定 | `ai-service.ts:43` |
| apiKey / baseUrl | env から供給、**全関数に threading 済み** | `index.ts` → `chatCompletion()` |

OpenCode Go（`opencode.ai/zen/go/v1`）は OpenAI 互換ゲートウェイで、リクエストの
`model` フィールドを差し替えるだけで複数モデルを呼び分けられる。apiKey / baseUrl は
既に `chatCompletion()` から `runAsk()` / `runAskForWeb()` までパラメータで流れている
ため、「model も同じ経路に 1 本足す」のは機械的な作業で済む。

切り替え先の設定を置く土台も既にある。

- `users` テーブル: `mode` / `avatar` / 個別プロンプトは既に利用者別。
- `app_settings` テーブル: 保護者 PIN の保存に使用（key-value）。
- 保護者認証 API: `X-Parent-Token` で名前・モード・プロンプト変更を保護。

モデル切り替えは **rpi-bridge に完全に閉じる**。worker は転送プロキシであり
（`worker/src/ai.ts` の `MODEL` は旧構成のデッドコード）、変更不要。

### 課題 (Complication)

**第一に、単一モデル固定は OpenCode Go の「多モデル」という特徴を活かせていない。**
モデルには速度・コスト・推論の深さ・ツールの扱いの得意不得意があり、状況に応じて
使い分けられれば、応答の速さと質のバランスを運用側で取れる。コード変更や再デプロイ
なしに切り替えられることが望ましい。

**第二に、モデル名だけ差し替えるのは危険である。** この API は未知の
`reasoning_effort` 値を**黙って既定へフォールバック**する（OpenAI 標準の `"minimal"`
が受け付けられず既定に落ちる実績が `ai-service.ts` のコメントに記録されている）。
モデルを変えたとき、`"low"` がそのモデルで有効か・無視されるか・400 になるかは
モデルごとに異なる。`max_tokens=8192` も deepseek 前提のチューニングであり、
モデルごとの上限・コスト特性に合わない。

**第三に、ツール呼び出しが本体である。** この Bot は ai-rotom のツールを呼びながら
回答を組み立てる（最大 30 往復、[ADR-0006](./ADR-0006.md)）。function calling が
弱い、あるいは非対応のモデルを選ぶとツール連鎖が省略され、従来作の記憶で
ハレーションを起こす（`reasoning_effort="none"` 時にメガゲンガーの特性を
「のろわれボディ」と誤答した事例）。選択できるモデルは「ツール対応が確認できたもの」
に絞る必要がある。

**第四に、切り替えの単位と操作主体を決めないと UI も DB も定まらない。** Web は
利用者（父・娘）ごとの属性があるが、Discord はチャンネル単位で表示モードの概念が
ない（[ADR-0011](./ADR-0011.md)）。「誰が・どこで・どの範囲に」切り替えるのかが
設計の前提になる。

### 論点 (Question)

1. 切り替えの単位をどこに置くか（全体 / Web 利用者別 / Discord チャンネル別 / 会話別）
2. 選択可能なモデル一覧をどう管理するか（許可リスト / 動的取得 / 自由入力）
3. モデル依存パラメータ（`reasoning_effort` / `max_tokens`）をどう扱うか
4. 設定の置き場所と操作権限をどうするか
5. 選択モデルが失敗（廃止・権限なし等）したときの挙動をどうするか

### 検討した選択肢 (Options)

#### 切り替えの単位

- **案1: 全体で 1 つ（Discord / Web 共通）**
  - 概要: `app_settings` に既定モデルを持ち、保護者が変更。全経路に即時反映。
  - メリット: 実装最小。管理が 1 箇所。
  - デメリット: 利用者ごとの使い分け（父は深く・娘は速く、等）ができない。
- **案2: Web は利用者別、Discord は全体既定（採用）**
  - 概要: `users` に model 列を足し、Web は利用者ごとに上書き。Discord は既定のみ。
  - メリット: 既存の `mode` / `avatar` / 個別プロンプトと同列で自然。Discord は
    表示モードを持たない（[ADR-0011](./ADR-0011.md)）ため既定値で十分。
  - デメリット: 全体設定と利用者設定の 2 層になり、解決順序の規約が要る。
- **案3: Web 利用者別＋ Discord チャンネル別**
  - メリット: Discord 側もチャンネル単位で変えられる。
  - デメリット: Discord に設定 UI がなく、チャンネル→モデルの対応を別途管理する
    手段（コマンドや DB 直編集）が必要。運用コストに見合わない。
- **案4: 会話／セッション単位まで上書き可能**
  - デメリット: 子ども向けの利用ではほぼ不要。状態管理が増えるだけ。

#### 選択可能なモデル一覧の管理

- **案A: ハードコードの許可リスト（採用）**
  - 概要: モデル定義（ID＋推論設定）をコードに持つ。UI はそこに載ったものだけ提示。
  - メリット: 存在しない ID・ツール非対応・高コストモデルへの自由な切り替えを防げる。
    モデルごとの挙動を事前検証してから載せられる。
  - デメリット: 追加・削除にコード変更と再起動が要る。
- **案B: OpenCode Go の `/models` から動的取得**
  - メリット: 常に最新の一覧。
  - デメリット: 挙動検証なしでモデルが露出する。ゲートウェイに一覧 API があるかの
    確認も要り、ツール対応・推論設定の扱いがモデルごとに分からない。
- **案C: 自由入力**
  - デメリット: 利用者層（子ども／保護者）には不向き。事故（存在しない ID、高コスト、
    ツール非対応）を招く。

#### モデル依存パラメータの扱い

- **案①: モデル定義に束ねる（採用）**
  - 概要: `{ id, reasoning_effort, max_tokens }` を一体で持ち、呼び出し時に解決する。
    現行の `MODEL` / `REASONING_EFFORT` / `MAX_TOKENS` は deepseek 定義の初期値に移す。
  - メリット: モデルごとの推論設定の整合を型で守れる。未知パラメータの黙殺・400 を
    避けられる。推論非対応モデルは `reasoning_effort` を**送らない**形にできる。
  - デメリット: モデル追加時に定義を 1 件書く手間が増える。
- **案②: モデル名のみ差し替え、パラメータは共通固定のまま**
  - メリット: 実装最小。
  - デメリット: `reasoning_effort="low"` が効かない／400 になるモデルが出るリスクを
    負う。第三の課題に反する。
- **案③: パラメータも保護者 UI で個別調整可能にする**
  - メリット: 柔軟。
  - デメリット: 壊しやすい設定を素人に露出する。調整の効果検証も利用者任せになる。

#### 設定の置き場所と操作権限

- 既定モデル: `app_settings`（key-value）に保持。保護者設定画面（PIN）から変更。
  再起動不要で次回リクエストから反映。
- Web 利用者別: `users.model`（nullable）に保持。`PATCH /api/users/:id` を拡張
  （名前・モードと同様に保護者認証必須）。未設定（null）は既定モデルに従う。
- Discord: 既定モデルのみ参照。操作は保護者設定画面の既定値変更に一本化。

#### 失敗時のフォールバック

- **案Ⅰ: 既定モデルへ自動フォールバック（採用）**
  - 概要: 解決したモデルが許可リストに無い／API がエラーを返したとき、既定モデルで
    続行する。
  - メリット: 既存方針「無言で終わらせない」（`finalizeWithoutTools`）と整合。
    モデル廃止や権限変更で利用者が操作不能にならない。
  - デメリット: 切り替えの失敗に利用者が気づかない。
- **案Ⅱ: エラーとして通知しつつ既定モデルで継続**
  - メリット: 失敗が見える。
  - デメリット: 子ども向け UI にエラー通知の導線を足すコストが増える。
- **案Ⅲ: フォールバックせずエラーを返す**
  - デメリット: 設定ミスを隠さない代わりに、利用者に再操作を強いる。

## 決定

### 切り替えの単位は「Web は利用者別、Discord は全体既定」とする（案2）

`users.mode` / `avatar` / 個別プロンプトと同じく、モデルも Web 利用者の属性として
扱う。父と娘で速度・深さを使い分ける余地を残しつつ、Discord は表示モードを持たない
（[ADR-0011](./ADR-0011.md)）ため既定値のみで十分。Discord のチャンネル別・会話別の
切り替えは行わない。必要になったときに改めて ADR を書く。

### モデルは「許可リストに載ったモデル定義」からのみ選べる（案A）

コードにモデル定義の許可リストを持ち、UI はそこに載った ID だけを提示する。自由入力・
動的取得は行わない。載せるモデルは**ツール呼び出し（function calling）が確認できた
ものに限る**。ツール連鎖が本体である以上、これを満たさないモデルを選ばせると
ハレーション（[ADR-0007](./ADR-0007.md) の「収録データに基づく助言に限定」方針と
背反）に直結する。

### モデル定義に `reasoning_effort` と `max_tokens` を束ねる（案①）

モデルは「ID だけの文字列」ではなく、次の形の定義として持つ。

```ts
interface ModelDefinition {
  id: string;                 // OpenCode Go へ送る model 値（UI にもそのまま表示）
  reasoning_effort: string | null; // null は「フィールドを送らない」（推論非対応モデル用）
  max_tokens: number;
}
```

現行の `MODEL` / `REASONING_EFFORT` / `MAX_TOKENS` は deepseek-v4-pro 定義の初期値へ
移し、`chatCompletion()` はモデル ID から定義を引いて `reasoning_effort` と
`max_tokens` を解決する。`reasoning_effort: null` のモデルでは、`tools` が空のときに
フィールドごと省く既存の実装と同じ要領で**キー自体を送らない**。これにより、未知
パラメータの黙殺や 400 をモデル定義側で封じる。

### UI にはモデル ID をそのまま表示し、既定は設定画面・利用者別はユーザー行に置く

許可リストの ID（例: `deepseek-v4-pro`）を保護者設定にそのまま出す。用途別の
親しみやすいラベル（「はやい／くわしい」等）へのマッピングは今回見送る。モデルは
保護者が選ぶ設定であり、ID のままでも差し支えないと判断した。将来ラベルが必要に
なったら許可リストの定義に表示名を足せばよい（TBD）。

既定モデルは設定ダイアログ（`settings-dialog`）に `<select>` を置く。利用者別の
上書きは `mode-list` の各ユーザー行（`mode` の横）に `<select>` を足す。利用者別の
select には「既定に従う」を選択肢として置き、選ぶと `users.model` を NULL に戻す
（上書きを間違えたときの戻り経路を残す）。

### 解決順序とフォールバック

リクエスト開始時に次の順でモデルを解決する。

1. Web: `users.model` が設定済みかつ許可リストに存在すればそれを使う。
2. それ以外（Web 未設定・Discord・許可リストから消えた設定）: 既定モデルを使う。

生成中に選択モデルが API エラー（廃止・権限なし等）を返した場合は、既存の
`finalizeWithoutTools` 相当を**既定モデル**で実行し、無言で終わらせない（案Ⅰ）。
既定モデル自体が失敗した場合は従来どおりのエラー経路に落ちる。

### 会話履歴は切り替え時に引き継ぐ（リセット不要）

メッセージ形式は OpenAI 互換のため、履歴はモデルをまたいで引き継げる。system
プロンプト（kids/junior 指示・クイズ形式）はモデル非依存の指示であり、切替時の
会話リセットは行わない。モデルごとの文体・推論の深さの差は受け入れる。

## 影響

### メリット

- コード変更・再デプロイなしでモデルを切り替えられる。OpenCode Go の多モデルという
  特徴を活かし、応答速度・コスト・深さを運用で調整できる。
- 父と娘でモデルを使い分けられる（例: 娘は速いモデル、父は深いモデル）。
- モデルと推論設定を束ねるため、未知の `reasoning_effort` による黙殺・400 を
  構造的に防げる。モデルを足すときの検証項目が定義に集約される。
- 許可リストにより、ツール非対応モデルや高コストモデルへの誤切り替えを防げる。
- フォールバックにより、モデル廃止や権限変更で利用者が操作不能にならない。

### デメリット・トレードオフ

- モデルの追加・削除にコード変更と再起動が要る（許可リスト方式の代償）。
- 全体設定（既定）と利用者設定（Web）の 2 層になり、解決順序を誤ると「変えたのに
  効かない」が起きる。解決順序の規約（上記）をコードコメントとテストで守る。
- 切り替えの失敗は利用者に通知されず、既定モデルに黙って落ちる。
- モデルごとの文体・推論の深さの差は出る。kids/junior の指示が効きにくいモデルを
  載せないことは、許可リストへ載せる際の検証項目に含める。
- モデルが変わるとコスト・レイテンシも変わる。保護者がゲートキーパーになる前提だが、
  コスト表示は持たない（許可リストの顔ぶれで暴走を防ぐ）。

### 今後チームが意識すべきこと

1. **モデル名を直書きしない**。許可リストの定義を通し、`reasoning_effort` と
   `max_tokens` は定義から解決する。
2. **許可リストに載せる前に、そのモデルのツール呼び出しと `reasoning_effort` の
   扱いを実測する**。未知値の黙殺があるため、単に ID が通ることだけでは足りない。
3. **Web 利用者設定は nullable**。null は「既定モデルに従う」であり、既定を変えても
   利用者設定は上書きされない（上書きした利用者は既定変更の影響を受けない）。
4. **Discord は既定モデルのみ**。Discord は 12 分の締切（interaction token 15 分 −
   3 分マージン）があり、遅いモデルを既定にすると締切に当たりやすくなる。既定は
   実績のある deepseek-v4-pro を保ち、速度を変える場合は締切との兼ね合いを確認する。
5. **`usage.completion_tokens_details.reasoning_tokens` は推論モデルでしか返らない**。
   非推論モデルでは既存のログが 0 になるだけで、ログ処理を分岐させる必要はない。
6. **進捗表示の語彙（`tool-progress.ts` / `app.js` の `L.kids` / `L.junior`）は
   モデル非依存**。今回の変更で追加不要。

### 関連する ADR・追加作業

- ADR-0006（ツール結果の整形）: モデルを変えてもツール結果の整形は同じ。ただし
  ツール連鎖を省くモデルはハレーションの温床になるため、許可リストの検証対象。
- ADR-0007（収録データに基づく助言に限定）: 許可リストを「ツール対応済み」に絞る
  根拠。ツールを呼ばないモデルはこの方針に反する出力をしやすい。
- ADR-0011（3択クイズ）: クイズ生成の裏取り（ツール往復）はモデルのツール対応に
  依存する。許可リストに載せるモデルでは、クイズの記法遵守も確認する。
- 実装済み:
  - モデル定義の許可リスト（新モジュール `model-registry.ts`。
    `ModelDefinition { id, reasoning_effort: string | null, max_tokens }` を定義し、
    `MODEL` / `REASONING_EFFORT` / `MAX_TOKENS` を deepseek 定義へ移設。
    `resolveModelDefinition()` は未知 ID を既定へ落とす）
  - `chatCompletion()` ほか各関数への `model: ModelDefinition` の threading
    （apiKey / baseUrl と同経路。解決は `runAsk` / `runAskForWeb` で行い、解決済み
    定義を渡す）
  - モデル解決関数（`getDefaultModelId` / `getUserModelId`、conversation-manager に
    追加）とフォールバック（`executeToolCallLoop` の API エラー catch で、非既定
    モデル時に既定モデルで `finalizeWithoutTools`）
  - `users` への `model TEXT`（NULL = 既定に従う）列追加（マイグレーション）
  - API: `GET /api/models`（PIN 不要・許可リスト＋既定を返す）、
    `PUT /api/parent/model`（PIN 必須・許可リスト外は 400）、
    `PATCH /api/users/:id` の `model` 対応（変更時は PIN 必須、null で既定へ戻す）、
    `GET /api/users` の `UserInfo` に `model` を追加
  - 保護者設定画面の UI（既定モデルの select ＋ 各ユーザー行の select、
    「既定に従う」を含む）。`L.kids` / `L.junior` にラベル追加
  - `[ai]` ログへの `model.id` 追記
  - 一覧取得・実測スクリプト（`scripts/probe-models.sh`）
  - 許可リストの初期顔ぶれ（`scripts/probe-models.sh` で実測して追加済み）:
    deepseek-v4-flash / glm-5.3-flash / glm-5.3 / qwen3.8-max（既定は deepseek-v4-pro）。
    追加・削除は同じ手順（probe で実測 → 定義を追加）
- [ADR-0016](./ADR-0016.md): 回答の帰属（モデル名の保存・表示）。本 ADR の
  「`[ai]` ログへの model.id 追記」はサーバーログの話で、利用者向けの帰属表示は
  そちらに分離した。
