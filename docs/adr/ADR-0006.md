# ADR-0006: LLM に渡すコンテキストは「ツール別の整形層」と「役割別の履歴保持」で配分し、一律の文字数切り詰めを廃止する

## ステータス

採用

> 本 ADR は実装に先立って論点を固定するために書き起こし、実装を経て
> TBD だった整形仕様と保持件数を確定させた。実測値はすべて実装時点のもの。

## コンテキスト

### 状況 (Situation)

`rpi-bridge` は `@nonz250/ai-rotom` の 30 ツールを LLM に渡し、ツール呼び出しループで回答を組み立てる。
LLM に渡せる量には上限があるため、現在は次の 2 つの固定値で流量を絞っている。

| 定数 | 値 | 場所 | 役割 |
|---|---|---|---|
| `MAX_TOOL_RESULT` | 2000 文字 | `ai-service.ts` / `conversation-manager.ts` | ツール結果を先頭から切り詰める |
| `MAX_MESSAGES` | 20 件 | `conversation-manager.ts` | LLM へ渡す履歴の件数上限 |

どちらもツールの中身や役割を問わない一律の値である。

### 課題 (Complication)

#### 1. 分析系ツールの出力がほぼ捨てられている

MCP サーバー（v1.2.5）を直接起動して出力サイズを実測した（2026-08-07 時点）。

| ツール | 実出力 | LLM に届く量 | 破棄率 |
|---|---:|---:|---:|
| `find_counters`（候補プール無指定） | 5,692,717 字 | 2,000 字 | **99.96%** |
| `calculate_damage_all_moves` | 113,370 字 | 2,000 字 | **98.2%** |
| `analyze_party_coverage` | 53,027 字 | 2,000 字 | **96.2%** |
| `list_speed_tiers` | 38,101 字 | 2,000 字 | **94.7%** |
| `analyze_matchup` | 28,932 字 | 2,000 字 | **93.1%** |
| `analyze_selection` | 16,692 字 | 2,000 字 | 88.0% |
| `search_pokemon_by_type_effectiveness` | 14,977 字 | 2,000 字 | 86.6% |
| `get_pokemon_summary` | 1,436 字 | 全量 | 0% |
| `get_learnset` | 1,959 字 | 全量 | 0% |

`find_counters` は候補プールを 6 体に絞っても 155,866 字ある。1 候補につき
双方向の全技ダメージが入るためで、絞り込みでは解決しない規模である。

図鑑を引く系（`get_*`）は無傷だが、**勝つための分析系はほぼ全滅している**。
このシステムの目的は対戦の勝利に貢献することなので、失われている側が本体である。

#### 2. 切り詰めが JSON を破壊する

出力は JSON 文字列であり、2000 字目は構造の途中に落ちる。実際の切断面は次のとおり。

```
..."description":"0 SpA Garchomp Water Spout (150 BP) vs. 0 HP / 0 Sp
```

パース不能な断片を LLM に渡しており、幻覚の温床になっている。

#### 3. 先頭 2000 字に意味のあるデータが入っていない

`calculate_damage_all_moves` の結果は威力順にも KO 判定順にも並んでいない。
ガブリアス→カバルドンの実測では、先頭に来るのは「ハードプラント」「ハイドロカノン」
「ウォーターポンプ」であり、**本命の「じしん」は末尾に埋もれて捨てられる**。

「じしんで確定何発か」に対し、LLM が自信を持って誤答できる状態になっている。

#### 4. 会話の記憶が 1〜2 往復しか残らない

`MAX_MESSAGES = 20` は `role: "tool"` も 1 件として数える。
ツールを 8 回呼ぶと `assistant`(tool_calls) + `tool` × 8 で 17 件を消費し、1 往復で枠が埋まる。

README には「直近 20 件に絞られる」とあるが、実態は「直近 1〜2 往復」である。
パーティ構築の相談という最も価値の高い使い方が、この時点で成立していない。

### 論点 (Question)

1. ツール結果をどう削るか（何を残し、何を捨てるか、誰が判断するか）
2. 履歴として何を残すか（tool メッセージを会話の記憶とみなすか）
3. 削ったことを LLM にどう伝えるか

### 検討した選択肢 (Options)

#### ツール結果の削り方

- **案A: 現状維持（一律の先頭切り詰め）**
  - 概要: `MAX_TOOL_RESULT` の値だけを調整する
  - メリット: 変更が不要
  - デメリット: 上記 1〜3 が一切解決しない。値を上げてもコンテキスト上限に当たるだけ

- **案B: Pi 側にツール別の整形層を置く**
  - 概要: ツール名ごとに整形関数を持ち、並べ替え・上位 N 件抽出・不要フィールド除去を行う
  - メリット: 何を残すかを設計者が決められる。`calculate_damage_all_moves` なら KO 判定で
    降順に並べて上位 10 件の `description` だけ残せば 113,370 字 → 約 800 字に収まり、
    しかも**捨てる前より判断に必要な情報が増える**
  - デメリット: ツールごとに整形を書く必要がある。上流の出力形式が変わると追従が要る

- **案C: 生出力を LLM にもう一段渡して要約させる**
  - 概要: 「この結果を要約して」という補助的な呼び出しを挟む
  - メリット: 整形を書かなくてよい。未知の出力形式にも効く
  - デメリット: 往復とコストが増える。要約の誤りが本回答に乗る。
    そもそも 113,370 字は 1 回のコンテキストに載らないので、この案単独では成立しない

- **案D: 上流の `@nonz250/ai-rotom` に絞り込み引数の追加を提案する**
  - 概要: `calculate_damage_all_moves` に `moves` や `topN` を追加してもらう
  - メリット: 最も本質的。全ツールの利用者が恩恵を受ける
  - デメリット: 自分の手で完結しない。反映時期を制御できない

- **案E: 全文を渡す**
  - 概要: 切り詰めをやめ、コンテキスト上限まで使う
  - メリット: 情報が失われない
  - デメリット: 113,370 字は約 3〜5 万トークンで、1 ツール 1 回で予算を使い切る。成立しない

#### 履歴の残し方

- **案1: 現状維持（role を問わず 20 件）**
  - デメリット: 課題 4 のとおり会話が続かない

- **案2: user / assistant を N 件、tool は直近 1 ターン分のみ残す**
  - メリット: 会話の流れが残る。過去ターンのツール生データは再利用価値が低い
  - デメリット: 「さっき調べた数値」を LLM が覚えていない場合がある
    （ただし整形後の要点は assistant の回答に含まれるため、実害は限定的と見込む）

- **案3: 件数ではなく文字数（トークン）予算で管理する**
  - メリット: 実態に即している。長い 1 件と短い 10 件を同じ土俵で扱える
  - デメリット: 実装が重い。案 2 と排他ではなく、後から重ねられる

## 決定

### ツール結果は案B（ツール別の整形層）を主軸とし、案D を並行して進める

`ai-service.ts` のツール実行経路に整形層を挟み、ツール名ごとの整形関数を通してから
LLM に渡す。整形関数を持たないツールは従来どおり素通し（多くは 2000 字未満で収まる）。

整形の方針は「**捨てる順序を設計者が決める**」ことに尽きる。先頭から機械的に切るのをやめ、
判断に効く順に並べ替えてから上位を残す。

整形関数は `tool-result-formatter.ts` に置く。実装後の実測は次のとおり。

| ツール | 整形方針 | 生出力 → 整形後 |
|---|---|---|
| `find_counters` | 与ダメージ降順に上位 8 体。各候補は最大打点と最大被弾の 1 行ずつ | 5,692,717 → 3,221 |
| `calculate_damage_all_moves` | 与ダメージ降順に上位 10 件の `description` のみ | 113,370 → 1,159 |
| `analyze_party_coverage` | 抜群を取れない複合タイプのみ抽出、候補技は各 1 件 | 53,027 → 1,884 |
| `list_speed_tiers` | 速い順 45 件 + `around` / `range` の案内 | 38,101 → 5,495 |
| `analyze_matchup` | 双方の攻撃技を上位 5 件、素早さと先制技は維持 | 28,932 → 1,714 |
| `analyze_selection` | 6x6 の 36 マスは全件維持し、各マスを 1 行の文字列へ圧縮 | 16,692 → 3,661 |
| `search_pokemon_by_type_effectiveness` | 上位 40 体を名前・タイプ・種族値合計へ集約 | 14,977 → 2,728 |
| `search_pokemon_by_move` | 同上 | 11,449 → 2,132 |
| `calculate_damage_party_matchup` | 各マスを 1 行の文字列へ圧縮 | 6,057 → 1,695 |

整形関数を持たない 18 ツールは 5,000 字以下に収まっており、素通しする。

案D（上流への引数追加提案）は案B と競合しない。実装中に、提案すべき具体的な
不具合が 1 件見つかった。

> `calculate_damage_all_moves` は learnset を参照せず全技を計算している。
> ガブリアスで `results` が 280 件になり、上位に「ハードプラント」「ハイドロカノン」
> など実際には覚えない技が並ぶ（同じガブリアスでも `analyze_matchup` は 42 件で、
> こちらは learnset ベース）。並べ替えても**覚えない技が最上位に来る**ため、
> 整形層では警告文を添えるにとどめた。本来は上流で解決すべき問題である。

### 削ったことを必ず LLM に伝える

現在の `...(省略)` は「何かが省かれた」ことしか伝えず、全体像も再取得手段も示さない。
整形後は件数を明示する（例: 「全 42 技中、ダメージ上位 10 件」）。

LLM が「残りも見たい」と判断できるよう、絞り込み引数を持つツールはその使い方を
システムプロンプトに書く。

### 履歴は案2（役割別の保持）を採る

`MAX_MESSAGES`（role 一律 20 件）を `MAX_CONVERSATION_MESSAGES`（user / assistant の
やり取り 20 件）に置き換える。過去ターンの `tool` と tool_calls 付き `assistant` は落とす。
最後の `user` 以降（＝今回の質問）は件数上限に関係なく残す。

保持件数は 20 件のまま据え置いた。従来と同じ数字だが、数える対象がツール往復を
含まなくなったため、実効的な記憶量は大きく増える。

案3（トークン予算）は将来の拡張余地として残し、今回は採らない。

### 整形層はツール実行の内側に置き、保存前に適用する

`conversation-manager.ts` の `saveMessages()` にも同じ 2000 字切り詰めがあり、
実行時と保存時で二重に削られている。整形層を通した結果をそのまま保存する形に一本化する。

## 影響

### メリット

- 分析系ツールが初めて機能する。ダメージ計算・素早さ比較・対面分析が
  「呼んだが結果を見ていない」状態から脱する。全 27 ケースで整形後 6,000 字以内に
  収まることを実測で確認した
- 壊れた JSON を LLM に渡さなくなり、幻覚の一因が消える
- 同じコンテキスト量で**判断に必要な情報が増える**。整形は圧縮ではなく取捨選択である
- パーティ構築のような複数往復の相談が成立する

### デメリット・トレードオフ

- 上流 `@nonz250/ai-rotom` の出力形式に依存する。フィールド名が変われば整形層が壊れる。
  現在ツール定義は手書きで固定しており（`tool-definitions.ts`）、v1.2.5 時点では
  名前・引数とも実スキーマと一致しているが、追従は人手に頼っている
- ツールを追加するたびに整形の要否を判断する手間が増える
- 整形で捨てた情報は LLM から永久に見えない。捨てる基準の誤りが誤答に直結する

### 今後チームが意識すべきこと

1. **ツールを追加したら整形の要否を必ず確認する**。実出力サイズを計測してから判断する
2. **「先頭から切る」実装を再び入れないこと**。JSON を壊し、並び順の意味を無視する
3. **削ったときは必ず全体件数を添える**。LLM が「これで全部だ」と誤認するのを防ぐ
4. **上流のバージョンを上げたら整形層の動作を確認する**。出力形式の変更が壊れ方として
   現れるのは、整形結果が空になるときである

### 計測の再現方法

MCP サーバーを直接起動し、`client.callTool()` の結果長を測る。
`rpi-bridge` を経由しないため、整形層の有無に関わらず素の出力サイズが得られる。

```
StdioClientTransport({ command: "npx", args: ["-y", "@nonz250/ai-rotom"] })
```

### 関連する ADR・追加作業

- [ADR-0003](./ADR-0003.md): kids モードの「200 文字程度まで」という制約は、
  本 ADR が増やそうとしている情報量と正面から競合する。整形層で情報が増えた後、
  kids 向けに何をどこまで削るかは別途見直しが要る
- 追加作業: 上流 `@nonz250/ai-rotom` へ、`calculate_damage_all_moves` が learnset を
  参照していない件を報告する（上記「決定」の引用部）。あわせて `find_counters` に
  上位 N 件の絞り込み引数があれば、整形層は薄くできる
- 本 ADR に含めない範囲（別 ADR とする）:
  - 対戦環境・メタ情報の取り込み（外部検索の是非）
  - 応答配信の SSE 化と進捗の可視化
  - パーティ保存のユーザー分離
- 先行して修正済み（ADR 不要と判断した欠陥）:
  - `finish_reason: "length"` の未処理、ツール上限到達時の無言終了、
    Discord の 15 分ガード（コミット `19a394e`）
  - 未収録ポケモンをツールが返せないときの扱い（コミット `e3b4282`）
