# ADR-0026: 対戦記録は解析側の turns v2・boards・シーズン文脈に追随し、行動ログはサイドと盤面を明示して返す

## ステータス

採用

> R2 の実データ（2026-10-25 時点: `matches.parquet` 260 行 / 55 動画、
> `turns.parquet` 683 行 / 63 対戦 / 12 動画、`boards.parquet` 58 行 / 5 対戦 / 1 動画）を
> DuckDB の httpfs で読んで実測したうえで決定している。実装済み。

## コンテキスト

### 状況 (Situation)

[ADR-0022](./ADR-0022.md) は `get_match_turns` を「**自分の**行動ログ（技・交代・メガ）
だけを返す」ツールとして設計した。当時 `turns.parquet` の 239 行はすべて `species` が
`selfTeam` に含まれ、相手専用の種は 1 行も無かった。相手の行動・ダメージ・HP は
どの記録にも無く、その制約を応答の `notes` で AI に伝えていた。

解析側（`pokemon-champions-chapter`）が ADR-036〜039 で記録を深め、R2 のスキーマが
変わった。

| 変化 | 内容 |
|---|---|
| `turns.parquet` v2 | `side`（self / opponent）/ `slot`（0・1）/ `source`（template / vlm / manual）を追加。**相手の行動も同じ表に入る** |
| `boards.parquet`（新規） | ターン開始時点の盤面。自分は実数（`current`/`max`）、相手は %（`percent`）。**行動とは別テーブル**（混ぜると技の使用率の分母が水増しされるため） |
| `matches.parquet` | 26 列。`season` / `seasonSource` / `regulation` / `rankTierStart` 〜 `ratingEnd` を追加 |

実データでの充填は次のとおり。**機能は揃ったが、カバレッジはまだ薄い。**

| 項目 | 実測 |
|---|---|
| `side = opponent` の行動 | 37 行 / 683 行。**1 動画（`1UBNFA05GUU`）のみ**。他 11 動画は self だけ |
| `boards.parquet` | 58 行 / 5 対戦 / 1 動画（同じ `1UBNFA05GUU`） |
| `season` / `regulation` | 249 / 260 対戦。うち `seasonSource = ocr` は 5 件、残りは `inferred` |
| `rankTierStart` | 5 対戦のみ。`ratingStart` は 0 件 |

### 課題 (Complication)

**第一に、既存の実装がデータと食い違う。** `get_match_turns` は `side` を SELECT して
いなかったため、v2 の動画では**相手の行動を自分の行動と同じ配列で返していた**。
`notes` は「この行動ログは自分の行動のみ」と言い続けていたので、AI は相手の
ファイアローやインテレオンを「自分の選出」として読む余地があった。実際に
`1UBNFA05GUU` の振り返りで、相手の `おいかぜ` と自分の `おいかぜ` が同じ並びに
出ていた。

**第二に、HP と文脈がツールから見えない。** `boards.parquet` を読む経路が無く、
シーズン・レギュレーション・ランクも `get_match` が返していなかった。振り返りの
前提（どのシーズン・どのレギュレーションの対戦か）を AI が知らないまま、
ダメージ計算の結論だけを語ることになる。

**第三に、素直に足すと応答が壊れる。** 行動ログに `side`/`slot`/`source` と
`boards` をそのまま載せると、`1UBNFA05GUU_9` で **5,833 字**になり、整形関数を
持たないツールの素通し上限（5,000 字、[ADR-0006](./ADR-0006.md)）を超える。
実測では `1UBNFA05GUU_988` が 6,000 字で切れて JSON として解釈できなくなった
（`Invalid control character at char 6000`）。

### 論点 (Question)

1. 相手の行動をどう見せるか（サイドで分けるか、混ぜたまま `side` を付けるか）
2. HP 観測をどこで返すか
3. シーズン・ランクをどこで返すか
4. サイズをどう抑えるか
5. カバレッジの薄さ（相手行動 1 動画、boards 1 動画）をどう伝えるか

## 決定

### 1. 行動は `side` を付けて 1 本の並びのまま返し、ターンを `actions` と `boards` に分ける

`turns` の各ターンを `{ actions: [...], boards: [...] }` にする。`actions` は
時刻順の 1 本の並びを保ち、各行に `side`（self / opponent）を付ける。サイド別の
配列に割らないのは、そのターンの時系列（誰が先に動いたか）が崩れるため。

`slot` は 0 を、`source` は `template` を既定として省略する（描画テンプレートは
通常経路）。`confidence` は `uncertain` の判定にしか使わないので、0.8 以上では
落とす。`url` はターン内の先頭行動にだけ残す。ディープリンクの基準点が
ターンごとに 1 つあれば足りる。

### 2. `boards.parquet` は別テーブルのまま読み、応答でターンに結合する

`boards` は行動と同じ粒度で取れない（HP は連続量のサンプリング、行動は離散
イベント）ため、解析側でも表を分けている。こちらでも JOIN せず、`matchId` で
引いてターン番号で束ねる。未生成の環境では空を返し、行動ログだけは返せるように
する（`queryBoards` が失敗を握る）。

HP の型は解析側の非対称をそのまま保つ。自分は `{ kind: "actual", current, max }`、
相手は `{ kind: "percent", value }`。**観測が無いターン・スロットは要素自体が無い**
＝欠測であって、全快でも瀕死でもない。

### 3. シーズン・レギュレーション・ランクは `get_match` の `context` で返す

`list_matches` には各行へ `season` を 1 フィールドだけ足す（動画内の対戦を選ぶ
時点で文脈が要るため）。`get_match` は `context` に `season` / `seasonSource` /
`regulation` / `rankStart` / `rankEnd` をまとめる。記録が無ければキーごと省く。

`seasonSource` は値と一緒に返す。`inferred` は動画タイトルの録画日からの推定で、
確定事実ではない。これを隠すと AI が「M-7 の対戦だ」と断定してしまう。

### 4. `get_match_turns` に整形関数を追加する（素通し上限を上げない）

[ADR-0006](./ADR-0006.md) の原則どおり、一律の切り詰めではなく冗長さだけを削る。
落とすのは `confidence`（0.8 以上）・`slot`（0）・`source`（template）・
2 件目以降の `url`。**行動の順序・`side`・`species`・`move`・`boards` は削らない**
（そこが判断材料）。実測で `1UBNFA05GUU_9` は 5,833 → 4,635 字、boards を持つ
最大の対戦（`1UBNFA05GUU_988`、26 行動 + 14 盤面行）で 4,993 字に収まった。

### 5. カバレッジの薄さは `coverage.bySide` と `notes` で明示する

「opponent の行が無い」は未記録であって「相手が何もしなかった」ではない。
`boards` が無いことも同様。どちらも応答の `notes` に書き、`coverage.bySide` /
`coverage.boards` で件数を併記する。構造だけ見せて「無い＝していない」と
読ませない。

### 6. システムプロンプトとツール説明を同じ変更で更新する

`rpi-bridge/src/tool-definitions.ts` が単一の正で、`.pi/skills/rotom/SKILL.md` と
`.pi/extensions/rotom.ts` は `scripts/generate-pi.ts` の生成物である。行動ログの
読み方（サイド・boards・slot・source）と文脈（推定シーズン）を追記し、再生成する。
手で生成物を編集しない。

## 影響

- `get_match_turns` の `turns[turn]` が配列から `{ actions, boards }` に変わる
  **破壊的変更**。消費側は AI（プロンプト）だけで、コード上のパーサは無い。
  振り返り検品（[ADR-0021](./ADR-0021.md)）は `list_matches` の `matchAtTimestamp`
  しか見ないため影響しない
- 相手の行動・HP は**記録がある動画でしか出ない**。現時点では `1UBNFA05GUU` の
  5 対戦だけなので、「相手が何をしてきたか」を一般に語れるようになったわけではない。
  記録が増えれば同じコードでそのまま拾える
- `boards` の行数はダブルで 1 ターン最大 4 件。ターン数が多い対戦では応答が
  5,000 字に近づく。上限に当たる場合は整形の削り方（`notes` の圧縮など）を
  見直す。素通し上限を上げる方向には倒さない
- 過去の振り返り（`match_reviews`）は旧前提（相手行動なし）で書かれている。
  再生成はしない。新しい記録で振り返り直したときに上書きされる

## 未確定事項

1. `side = opponent` の行動は VLM 経路のみ（`source = vlm`）。確信度の分布が
   自分の経路（template 併用）と違うため、`uncertain` のしきい値 0.8 を
   相手側だけ変えるべきかは実データが増えてから判断する
2. `boards` を持つ対戦が 5 件しかないため、HP を使った振り返り（「このターンで
   耐えられたか」）の有用性は未検証
3. `ratingStart` / `ratingEnd` は 0 件（マスターボール級の動画が必要）。
   `context` の形は用意したが、値が入るのは当面先
