# ADR-0011: 3択クイズは 5 問を一括生成して構造で返し、正誤判定と進行はクライアントが担う

## ステータス

採用

> 壁打ちで論点を固定したのち実装した。ブロックの記法と「1 問でも壊れていれば
> 全体を捨てる」判断は実装時に確定させた。出題の精度と、最初の 1 問が出るまでの
> 待ち時間は、実際に遊んでから見直す。

## コンテキスト

### 状況 (Situation)

家庭用 Web UI「AIバトルコーチ」は Raspberry Pi 上で動き、利用者は父と小学生の娘 2 人
（小 1・小 5）である（[ADR-0001](./ADR-0001.md)）。表示モードは `kids` / `junior` の
2 段階をユーザー属性として持ち、UI の語彙・寸法と AI 応答の難易度の両方を切り替える
（[ADR-0003](./ADR-0003.md)）。

Web UI の応答は SSE で配信し、ツール実行の進捗を `tool` イベントで、最終応答を
`done` イベントで `{ session_id, reply }` として返す（[ADR-0008](./ADR-0008.md)）。
AI はツールを呼びながら回答を組み立てる（最大 30 往復、[ADR-0006](./ADR-0006.md)）。

この UI の実際の使われ方として、**娘が「ポケモンのクイズを出して」と頼み、
3 択で出題してもらう遊びが定着している**。当初の想定にはなかったが、対戦の助言よりも
こちらのほうが遊ばれている。

### 課題 (Complication)

**回答するたびに答えをテキストで打つ操作が、遊びのテンポを壊している。**

問題は入力の手間だけではない。次の 4 つが重なっている。

**第一に、小 1 にとってキーボード入力そのものが障壁である。** 「1」と打つならまだしも、
ポケモン名を打つには読みの入力と変換が要る。クイズは本来テンポよく続けるものであり、
1 問ごとに入力で数十秒止まると遊びとして成立しない。

**第二に、自由文の回答は判定を LLM の解釈に委ねることになる。** 「リザードン」
「りざーどん」「3」「3ばん」「まんなかのやつ」がすべて同じ回答として扱われる保証はない。
判定がブレると、正解したのに不正解と言われる事故が起きる。子どもはこれを強く嫌う。

**第三に、1 問ごとに LLM 往復が入るとテンポが死ぬ。** この構成は応答に数十秒かかる
ことがある。対戦の助言なら待てるが、クイズでは待てない。

**第四に、間違ったクイズは間違った知識をそのまま定着させる。** 子どもは AI の答えを
疑わない。通常の会話で誤った助言が混ざる害よりも、「正解」として提示された誤りの害は
大きい。ポケモンの一般知識であれば大きく外さないが、種族値や技の可否は LLM が
平気で間違える領域である。

加えて、**クイズがいつ終わるのかが曖昧である**。子どもが「もうやめる」と言い出すまで
続くか、AI が勝手に話題を変えるかのどちらかで、区切りを子ども自身が選べない。

### 論点 (Question)

1. この機能をどの経路に載せるか（Web UI のみか、Discord も含めるか）
2. 出題の正しさを誰が担保するか
3. テンポをどう確保するか
4. 選択肢の構造を、人が読む本文とどう分けてクライアントへ渡すか
5. 正誤判定を誰が行い、解説とフォローをどう出すか
6. 「クイズ中」という状態をどこに持ち、継続と終了をどう表現するか

### 検討した選択肢 (Options)

#### 適用範囲

- **案A1: Web UI のみ**
  - メリット: `kids` / `junior` は `users.mode` を持つ Web UI 固有の概念であり、
    範囲がそのまま一致する。既存の SSE 応答にフィールドを足すだけで届く
  - デメリット: Discord からは従来どおりテキストで答えることになる

- **案A2: Discord にも Message Components で対応**
  - メリット: どちらの経路でも同じ体験になる
  - デメリット: ボタン押下が新しい interaction として Worker に飛ぶ経路を設計する
    必要がある。Discord にはそもそも表示モードの概念がなく、
    「両モードで使える」という要件とも噛み合わない

#### 出題の正しさ

- **案B1: LLM が自由に出題する**
  - メリット: 実装が最小。対戦の振り返りやパーティの話から地続きで出題できる
  - デメリット: 誤った正解が混ざる。子どもはそれを疑わない

- **案B2: LLM が出題し、正解を ai-rotom のツールで裏取りする**
  - メリット: 出題の自由度を保ったまま、事実に基づく問題に寄せられる
  - デメリット: ツール往復のぶん、生成が遅くなる

- **案B3: ai-rotom のデータから機械生成する**
  - メリット: 正解が必ず正しい
  - デメリット: 出題パターンが設計した型に固定される。
    小 1 にとって面白い問題になるとは限らない

- **案B4: 対戦記録（[ADR-0010](./ADR-0010.md) の Parquet）から出題する**
  - メリット: 自分の対戦の復習になる
  - デメリット: 出題の幅が狭い。対戦をしていない期間は出題できない

#### テンポの確保

- **案C1: 1 問ずつ都度生成する**
  - メリット: 直前の回答や会話の流れに沿った出題ができる
  - デメリット: 毎問 LLM 往復が入る

- **案C2: 複数問をまとめて生成し、クライアントが順に消化する**
  - メリット: 2 問目以降は往復ゼロで即座に出る
  - デメリット: 途中で終了したぶんの生成は捨てることになる。
    回答内容に応じて次の問題を変えることはできない

- **案C3: クイズ生成時は tools を渡さない**
  - メリット: ツール往復を丸ごと排除でき、最も速い
  - デメリット: 案B2 の裏取りと両立しない

#### 選択肢の受け渡し

- **案D1: 応答末尾の専用ブロックに構造を書かせ、サーバーが抽出する**
  - メリット: 人が読む本文と機械が読む構造を分離できる。
    抽出に失敗しても、ブロックごと本文として表示すれば会話は止まらない
  - デメリット: LLM が記法を守る保証はない

- **案D2: 出題専用のツールを定義し、その引数を UI 命令として横取りする**
  - メリット: 既存のツールループの仕組みに乗る。引数はスキーマで縛れる
  - デメリット: ツールは結果を返すとループが続く前提で組まれており、
    「呼んだ時点で応答を終える」という例外的な扱いが要る

- **案D3: 応答テキストを正規表現でパースする**
  - メリット: LLM 側に何も要求しない
  - デメリット: 最も脆い。番号の振り方が変わるたびに壊れる

#### 正誤判定

- **案E1: 正解をクライアントへ渡し、押した瞬間に判定する**
  - メリット: 即座に反応が返る。判定がブレない
  - デメリット: 正解がブラウザ側に存在する（開発者ツールから見える）

- **案E2: 選んだ選択肢を発言として送り、LLM に判定させる**
  - メリット: 会話として自然で、履歴にそのまま残る
  - デメリット: 遅い。加えて **LLM が自分の出した正解を取り違える**ことがあり、
    判定の安定性という最大の要件を満たさない

## 決定

### 案A1 を採り、対象は Web UI に限る

`kids` / `junior` は `users.mode` に基づく Web UI 固有の概念である
（[ADR-0003](./ADR-0003.md)）。Discord 側はチャンネル単位のセッションで動いており
表示モードを持たないため、「両モードで使える」という要件は Web UI の中で閉じる。

Discord での 3 択クイズは行わない。必要になったときに改めて ADR を書く。

### 案B2 と案C2 を組み合わせ、1 回の生成で 5 問をまとめて作る

**この 2 つは相反しない。** 裏取りのツール往復は「5 問を作る 1 回の生成」に
集約されるため、生成が 1 回だけ遅くなり、2 問目以降は往復ゼロで即座に出る。
1 問ずつ裏取りする案（B2 + C1）が抱えるテンポの問題は、まとめて作ることで消える。

問題数は 5 問を基本とする（TBD: 実際に遊んで多い・少ないを見て調整する）。

案C3（tools を渡さない）は採らない。速度のために正しさを捨てる判断になるためで、
第四の課題に正面から反する。

### 案D1 を採り、構造は応答末尾の専用ブロックで受け取る

LLM には、人が読む本文に続けて構造化ブロックを出力させる。サーバーはこれを抽出して
`done` イベントのペイロードに載せ、**本文からは取り除いてから返す**。

抽出に失敗した場合は、**ブロックを取り除かずそのまま本文として表示する**。
選択肢ボタンは出ないが、会話は止まらない。3 択の文章はテキストとしても読めるため、
最悪でも現状と同じ体験に落ちるだけで済む。**構造が壊れた瞬間に画面が止まる作りには
しない。**

形式は次のとおり確定した（`quiz-block.ts`）。

````
```quiz
{"questions":[{"question":"…","choices":["…","…","…"],"answer":1,"explanation":"…"}]}
```
````

`answer` は 1〜3 で書かせ、サーバーが 0 始まりに直して `answer_index` として返す。
0 始まりで書かれた場合と見分ける手段がないため、**範囲外の値は推測で補正せず、
不正として扱う**。

**1 問でも形式が崩れていれば、そのブロック全体を捨てる。** 壊れた問題だけを落として
残りを出題すると、正解が誤ったまま出題される余地が残るためである。

### 本文からのブロック除去は API 境界で行い、DB には原文を保存する

抽出と除去は `index.ts` の応答組み立て時に行い、会話履歴には**ブロックを含む原文を
保存する**。

こうしないと、AI は自分が何を出題したかを履歴上で失う。「さっきの 3 問目、なんで
そうなるの？」というフォローに答えられなくなる。

この分離は、[ADR-0003](./ADR-0003.md) がモード指示を保存内容へ焼き込まないと
決めたのと同じ性質の判断である。**保存するものと見せるものを取り違えない。**

### 案E1 を採り、判定はクライアントが行う。解説は事前生成して同梱する

正解の番号と 1〜2 文の解説を、問題と一緒に構造ブロックへ含めさせる。子どもが選択肢を
押した瞬間に、クライアントが ○× と解説を表示する。**ここに LLM 往復は挟まない。**

正解がブラウザから見えてしまう点は、この利用者層と家庭内運用では無視してよい。

「回答へのフォローがほしい」という要求は、次の 2 段で満たす。

1. **即時**: 押した瞬間の ○× と、事前生成された短い解説
2. **深掘り**: クイズ終了後、通常の会話に戻って「3 問目をもっとくわしく」と聞ける。
   出題内容が履歴に残っているため成立する（前項の決定）

### 5 問終わったとき、および終了したときに、結果を 1 回だけ送って講評させる

成績（何問目に何を選び、正解だったか）をまとめて 1 回だけ送り、AI に講評させる。
1 問ごとに送らないのは、テンポを壊さないためである。

結果そのもの（「5 問中 4 問せいかい」）はクライアントが即座に表示する。講評は後から
届く。**押した直後に待たされる形にはしない。**

### クイズ中の状態はクライアントだけが持ち、サーバーはステートレスとする

「いま何問目か」「残りの問題」はブラウザのメモリに置く。DB にもセッションにも持たない。

- **つづける**: 手元に残っている次の問題を出す（往復なし）。使い切ったら
  「もんだいをつくってね」に相当する送信を 1 回だけ行う
- **おわる**: 手元の問題を捨て、選択肢 UI を畳んで通常の入力欄に戻る

DB に持たない理由は 2 つある。**リロードでクイズが終わるのは安全側の挙動である**こと。
そして [ADR-0003](./ADR-0003.md) の `mode` と紛らわしい 2 つ目の「モード」を
永続データに増やしたくないことである。

### 過去ログを開き直したとき、選択肢ボタンは復元しない

押せる問題は常に最新の 1 問だけとする。復元すると、いつの問題に答えているのか
本人にも分からなくなる。

履歴 API は、保存された原文のブロックを読める Markdown に変換して返す
（`renderStoredReply`）。正解の選択肢に ✅ を付け、解説も残す。既に答えた問題なので、
答えが見えていて構わない。

同じ原則から、**クイズの途中で普通の質問を送ったときも、答えかけの問題は畳む**。
押せるボタンを画面に残したまま別の話を始めると、どちらが生きているのか分からなくなる。

### キッズとジュニアの差分は最小に留める

差を付けるのは選択肢ラベルの語彙（「1ばん」/「A」）と、ボタンの寸法・文字サイズ
（既存のモードトークンで自動的に効く）に限る。

問題数や難易度の出し分けは、システムプロンプトのモード指示
（`MODE_INSTRUCTIONS`）で既に効いているものに任せ、クイズ専用の分岐を増やさない。
語彙テーブルの二重管理は既知の負債であり（[ADR-0003](./ADR-0003.md)）、
機能ごとに枝を増やすと管理しきれなくなる。

## 影響

### メリット

- 小 1 がキーボードに触れずにクイズで遊べる。表記ゆれの判定事故もなくなる
- 2 問目以降は待ち時間ゼロで進む。クイズが遊びとして成立する速度になる
- 正誤の判定が LLM の解釈に依存しなくなり、**正解したのに不正解と言われる事故が
  構造的に起きなくなる**
- 「つづける / おわる」を子ども自身が選べる。区切りが本人の手にある
- 裏取りを通すため、出題が ai-rotom の収録データに寄る
  （[ADR-0007](./ADR-0007.md) の「収録データに基づく助言に限定する」方針と揃う）

### デメリット・トレードオフ

- **LLM が構造ブロックの記法を守らない可能性が残る**。守らなければ選択肢ボタンは
  出ず、テキスト表示に落ちる
- まとめて生成するため、**回答内容に応じて次の問題を変えることはできない**。
  間違えた分野を追いかけて出題する、といった適応はできない
- 途中で終了したぶんの生成コストは捨てる
- 裏取りのぶん、最初の 1 問が出るまでは今までより遅くなる可能性がある
- リロードするとクイズが消える
- 正解がブラウザ側に存在する
- Discord との体験差が生まれる

### 今後チームが意識すべきこと

1. **構造ブロックの抽出に失敗しても会話を止めない**。フォールバックは
   「ブロックごと本文として表示する」であり、エラーにはしない
2. **DB に保存するのは除去前の原文**である。除去は API 境界（`index.ts`）で行う。
   履歴からクイズの内容が消えると、フォローの質問に答えられなくなる
3. **1 問ごとに LLM へ送らない**。テンポがこの機能の本体であり、
   往復を足す変更は体験そのものを壊す
4. **判定を LLM に戻さない**。判定の安定性がこの決定の中心にある
5. **UI 文言を追加するときは `L.kids` と `L.junior` の両方に定義する**
   （[ADR-0003](./ADR-0003.md)）
6. **クイズ生成のツール往復が増えていないか見る**。裏取りが重くなって最初の待ちが
   伸びるようなら、問題数を減らすか出題ジャンルを絞る
