# ADR-0009: パーティ保存のユーザー分離は Pi 側で名前空間を付け替えて実現し、MCP プロセスは 1 つに保つ

## ステータス

採用

> 実装に先立って論点を固定し、実装を経て TBD だった区切り文字と受け渡し方法を
> 確定させた。上流の保存方式および分離の動作は実測で確認済み。

## コンテキスト

### 状況 (Situation)

`@nonz250/ai-rotom` はパーティを保存するツールを 5 つ持つ。

`save_party` / `load_party` / `list_parties` / `delete_party` / `import_party_from_text`

`rpi-bridge` は MCP クライアントを **1 プロセスだけ** 起動し（`index.ts` の `main()`）、
Discord と Web UI の全リクエストがこれを共有する。

上流の保存方式を実測で確認した（v1.2.5）。

- 保存先は **`~/.ai-rotom/parties.json` の単一ファイル**
- パスは `os.homedir()` から組み立てられ、**環境変数によるオーバーライドはない**
- プロセスを再起動しても内容は残る（ファイル永続化）
- パーティは `name` を一意キーとする（同名は上書き）

### 課題 (Complication)

**家族全員が 1 つの名前空間を共有している。**

小 1 と小 5 がそれぞれ「じぶんのパーティ」という名前で保存すると、後から保存した
ほうが前を**黙って上書きする**（`save_party` の応答は `overwrote: true` を返すが、
AI がこれを利用者に伝える保証はない）。

`list_parties` は全件を返すため、他の家族のパーティも見える。Discord から使った場合も
同じ棚を共有する。

[ADR-0001](./ADR-0001.md) 以降、Web UI はユーザーという概念を持ち、会話履歴もシステム
プロンプトもユーザー単位に分離してきた。**パーティだけがその外側にある。**

加えて、Web UI にパーティを見る画面がない。保存されたパーティは会話の中で AI に
聞き出すしか確認手段がなく、存在を忘れられやすい。

### 論点 (Question)

1. 分離をどの層で行うか（上流 / Pi / 諦める）
2. 既存の Web ユーザー概念とどう結びつけるか
3. Discord 経由の利用をどう扱うか

### 検討した選択肢 (Options)

- **案A: 現状維持（家族共用の棚と割り切る）**
  - メリット: 実装が不要。家族で構築を共有できる面もある
  - デメリット: 黙って上書きされる事故が残る。子どもが自分の構築を安心して置けない

- **案B: Pi 側でパーティ名に名前空間を付ける**
  - 概要: パーティ系ツールの呼び出しを Pi で横取りし、`name` に `{userId}/` を前置する。
    `list_parties` の結果は自分の接頭辞を持つものだけに絞り、表示時に接頭辞を外す
  - メリット:
    - MCP プロセスは 1 つのまま。メモリも起動時間も増えない
    - 上流のロジック（`import_party_from_text` のポケソル解析など）をそのまま使える
    - 実装が 5 ツール分の引数と結果の書き換えに収まる
  - デメリット:
    - 保存ファイルの中身に接頭辞が見える。人が直接開いたときに読みにくい
    - 利用者が接頭辞を含む名前を自分で入力した場合の扱いを決める必要がある
    - ツール呼び出しの文脈に「今どのユーザーか」を渡す必要がある

- **案C: ユーザーごとに MCP プロセスを分ける（HOME を差し替える）**
  - 概要: `StdioClientTransport` の `env` で `HOME` をユーザー別ディレクトリに向ける
  - 検証: 実際に動くことを確認した。`HOME` を変えると保存先が
    `<指定パス>/.ai-rotom/parties.json` に変わる
  - メリット: 上流に手を入れず、ファイルレベルで完全に分離できる
  - デメリット:
    - **`npx` のキャッシュも `HOME` 配下に作られるため、ユーザーごとにパッケージが
      再ダウンロードされる**（`npm_config_cache` を別途固定すれば回避できるが、
      前提が増える）
    - ユーザー数だけプロセスが増える。Raspberry Pi のメモリを圧迫する
    - ユーザー追加のたびにプロセスを起こす必要があり、ライフサイクル管理が要る

- **案D: パーティ管理を Pi の SQLite に移し、上流のパーティツールを使わない**
  - 概要: 既存の DB にテーブルを足し、パーティ系ツールを自前実装に差し替える
  - メリット: ユーザー分離が既存の設計と完全に揃う。Web UI からの管理画面も作りやすい
  - デメリット: `import_party_from_text` のポケソルテキスト解析を自前で持つことになる。
    上流の改善を取り込めなくなる

- **案E: 上流に user スコープの追加を提案する**
  - メリット: 最も本質的。全利用者が恩恵を受ける
  - デメリット: 自分の手で完結しない。MCP サーバーは単一利用者を前提とした設計思想で
    あり、採用されない可能性がある

## 決定

### 案B を採る

パーティ系ツールの呼び出しを Pi 側で横取りし、`name` に利用者の名前空間を前置する。

| ツール | 書き換え |
|---|---|
| `save_party` | `name` に接頭辞を付ける |
| `load_party` / `delete_party` | `name` に接頭辞を付ける |
| `import_party_from_text` | `name` に接頭辞を付ける |
| `list_parties` | 結果を自分の接頭辞で絞り、表示名から接頭辞を外す |

案C を採らないのは、`npx` キャッシュの重複とプロセス増加という代償が、得られる分離の
強さに見合わないため。案D は最も筋がよいが、`import_party_from_text` を失う代償が
大きく、パーティ管理 UI が必要になった時点で改めて検討する。

### 名前空間は Web ユーザー ID、Discord は共用とする

- Web UI: `user:{userId}/` を接頭辞とする
- Discord: `discord/` を接頭辞とし、**チャンネル参加者の共用**とする

Discord はチャンネル単位で会話を共有する場であり（[ADR-0001](./ADR-0001.md) の
セッション設計と同じ考え方）、個人ごとに分ける必然性が薄い。

区切り文字は `/` とする。パーティ名に `/` が入力された場合も、接頭辞の長さで切る
実装（先頭一致 + `slice`）のため壊れない。「つよい/パーティ」という名前が正しく
往復することを実測で確認した。

利用者 ID が前方一致する場合（`user:a` と `user:ab`）も、接頭辞が `user:a/` と
`user:ab/` になるため誤って混ざらない。

### 名前空間は executor のクロージャに閉じ込める

`ai-service.ts` の `createToolExecutor(bridgeUrl, namespace)` が、ツール呼び出しの
前後で名前空間を出し入れする。HTTP ヘッダーで運ばないのは、`POST /tools/:name` の
呼び出し側が `ai-service.ts` だけであり、経路を増やす利点がないため。

この選択の帰結として、**`POST /tools/:name` を直接叩けば名前空間なしで生の棚に
到達できる**。この API は認証を持たず、家庭内 LAN での利用を前提としているため
（[ADR-0002](./ADR-0002.md) と同じ前提）、ここでは許容する。

### パーティ管理 UI は本 ADR の範囲外とする

分離が入れば「自分のパーティだけが見える」状態にはなる。画面から一覧・編集できる
ようにするかは、実際に使われるようになってから判断する。

## 影響

### メリット

- 兄弟がお互いの構築を黙って上書きする事故がなくなる
- 会話履歴・システムプロンプトに続き、パーティもユーザー単位に揃う
- MCP プロセスは 1 つのままで、Raspberry Pi の資源を消費しない

### デメリット・トレードオフ

- `~/.ai-rotom/parties.json` を人が直接開くと、接頭辞付きの名前が並ぶ
- 家族間でパーティを共有する手段が失われる（意図的に共有したい場合の経路は用意しない）
- 上流がパーティの保存形式を変えた場合、名前の書き換えが壊れる可能性がある
- **`POST /tools/:name` を直接叩けば分離を迂回できる**。認証のない内部 API であり、
  家庭内 LAN 前提のため許容する。インターネットへ公開する場合は前段の認証が必須
  （README の「セキュリティ上の注意」と同じ前提）

### 今後チームが意識すべきこと

1. **パーティ系ツールを直接呼ばないこと**。必ず名前空間を付ける経路を通す
2. **上流のバージョンを上げたらパーティの読み書きを確認する**。
   [ADR-0006](./ADR-0006.md) の整形層と同じ注意が要る
3. 接頭辞は内部表現であり、**利用者や AI に見せる場面では必ず外す**
