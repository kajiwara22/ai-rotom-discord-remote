# ADR-0004: 保護者向け操作は PIN 認証で保護し、アバターと文字サイズは子ども自身に開放する

## ステータス

採用

## コンテキスト

### 状況 (Situation)

[ADR-0001](./ADR-0001.md) では「プロンプト編集権限: 管理者ユーザーの概念は設けず、
全ユーザーが自身のプロンプトを編集可能とする」と決めていた。
LAN 内利用・認証なしという前提のもと、シンプルさを優先した判断である。

その後 [ADR-0003](./ADR-0003.md) で表示モードを追加し、ユーザー削除機能も実装した。
設定画面には次が並ぶようになった。

- 各ユーザーの表示モード（kids / junior）
- 各ユーザーのシステムプロンプト（AI の性格）
- ユーザーの追加・削除
- 外観（テーマ）

### 課題 (Complication)

実際の利用者は小 1・小 5 の子どもである。ADR-0001 の「全ユーザーが編集可能」のままだと、
次の事故が現実的に起こる。

1. **AI の人格を子どもが壊せる** — システムプロンプトは AI の応答方針そのもの。
   子どもが書き換えると全体の挙動が変わる
2. **他人のユーザーや履歴を消せる** — 削除機能に歯止めがない
3. **自分のモードを勝手に変えられる** — [ADR-0003](./ADR-0003.md) で「モードは固定して
   与える設定」としたが、本人が変えられては意味がない

一方で、**アバターや文字サイズまで保護者に握らせると過剰**である。これらは見た目の
好みでしかなく、子どもが自分で選べるほうが「自分のもの」という愛着につながる。

### 論点 (Question)

1. 保護者だけが行える操作と、子どもも行える操作をどう線引きするか
2. 認証の強度をどうするか（LAN 内前提とどう両立させるか）
3. UI だけのロックにするか、サーバー側でも強制するか

### 検討した選択肢 (Options)

- **案1: 現状維持（全ユーザーが全操作可能）**
  - メリット: 実装ゼロ
  - デメリット: 上記の事故が防げない。ADR-0003 のモード固定が形骸化する

- **案2: 管理者ユーザーを 1 人設け、ログインで区別する**
  - 概要: 保護者用アカウントにパスワードを設定する
  - メリット: 一般的な権限モデル
  - デメリット: ADR-0001 の「ユーザー名選択だけ・認証なし」を崩す。
    保護者も毎回ログインが要る。子ども用アカウントと保護者用アカウントの
    二重管理になる

- **案3: 保護者操作だけを PIN で保護し、成功時にトークンを発行する**
  - 概要: 4 桁 PIN を検証してトークンを発行し、保護者専用 API はトークン必須にする
  - メリット: 通常利用（ユーザー選択だけ）はそのまま。保護者操作の前だけ PIN を挟む。
    ログインの概念を持ち込まずに済む
  - デメリット: PIN の保存・検証・トークン管理の実装が要る

- **案4: UI 上でだけ設定画面を隠す（フロントのみのロック）**
  - 概要: PIN 一致で設定画面を表示するが、API 自体は無防備
  - メリット: 実装が軽い
  - デメリット: DevTools や API 直叩きで素通りできる。子どもは意外とこれを見つける。
    「ロックしている」という誤った安心感が一番危ない

## 決定

### 案3 を採用し、保護者操作を PIN + トークンで保護する

- 初期 PIN は環境変数 `PARENT_PIN`（既定 `1234`）。初回認証時に DB へ保存する
- PIN は **salt 付き scrypt でハッシュ化**して `app_settings` に保存し、平文では持たない
- 検証は**定数時間比較**（`crypto.timingSafeEqual`）で行う
- 認証成功で **30 分有効なトークン**をメモリ上に発行し、保護者専用 API は
  `X-Parent-Token` ヘッダーを必須とする（案4 の「UI だけのロック」を明確に否定する）

### 操作ごとの権限を次のように線引きする

| 操作 | PIN |
|---|---|
| アバター変更 | **不要**（見た目だけ。子ども自身が変えられる） |
| 文字サイズ変更 | **不要**（同上） |
| 表示名の変更 | 必要 |
| 表示モードの変更 | 必要 |
| システムプロンプトの編集 | 必要 |
| ユーザーの削除 | 必要 |

アバターは `PATCH /api/users/:id` のうち `avatar` のみの変更なら認証を免除する。
`display_name` や `mode` を含む場合は認証必須とする（サーバー側で判定する）。

### 安全策

- **最後の 1 人は削除できない**。全員消すと誰も使えなくなるため、
  サーバーが 409 を返し UI のボタンも無効化する
- **セッション・ユーザー削除は本人の user_id を条件に含める**。
  他ユーザーのデータを消せないようにする（一致しなければ 404）
- 設定ボタンは目立たない歯車に格下げし、PIN の背後へ隠す

## 影響

### メリット

- 子どもが AI の人格や他人のデータを壊す事故を防げる
- 通常利用（ユーザー選択→チャット）には認証が挟まらず、ADR-0001 の手軽さを保てる
- アバターと文字サイズは子どもが自分で選べ、愛着とアクセシビリティを両立する
- UI だけでなくサーバー側で強制するため、DevTools や API 直叩きにも耐える

### デメリット・トレードオフ

- **これは「本格的なアクセス制御」ではない**。目的は子どもの誤操作防止であり、
  LAN 内の信頼を前提とする点は ADR-0001 から変わらない
- PIN は 4 桁で総当たりに弱い。子どもの操作防止としては十分だが、
  インターネット公開時の防御には足りない（公開時は [ADR-0002](./ADR-0002.md) の
  HTTPS 化に加え、前段の認証が別途必要）
- トークンをメモリ保持するため、サーバー再起動で失効する（実害は軽微）
- 保護者トークンが平文で流れる問題は [ADR-0002](./ADR-0002.md) の HTTPS 化で対処する

### 今後チームが意識すべきこと

1. **保護者専用 API を追加したら `rejectIfNotParent()` を必ず通す**。
   フロントで隠すだけにしない
2. **削除系は user_id を条件に含める**。所有者チェックを省略しない
3. **「UI だけのロック」に退化させないこと**。案4 を明確に退けたのが本 ADR の要点
4. PIN のトークンをより堅くする場合（Secure Cookie 化など）は
   [ADR-0002](./ADR-0002.md) の HTTPS 化が前提になる
