# ADR-0002: 家庭内 Web UI の TLS 終端は Raspberry Pi 上の Caddy とし、証明書は Let's Encrypt の DNS-01 チャレンジで取得する

## ステータス

採用

## コンテキスト

### 状況 (Situation)

[ADR-0001](./ADR-0001.md) の決定により、Web UI「AIバトルコーチ」は Raspberry Pi 上の `rpi-bridge` が直接配信している。家族はブラウザから `http://<Pi の LAN IP>:3210/` を開いて利用する。

- 認証は行わず、ユーザー名の選択だけで使い分ける（LAN 内利用を前提とした ADR-0001 の判断）
- 保護者向け設定は 4 桁 PIN で保護し、サーバー側で検証したうえで 30 分有効なトークンを発行している
- Worker ↔ Pi 間は Cloudflare Tunnel + Access で保護されているが、Web UI はこの経路を通らない
- 家庭で使うドメインを Cloudflare で管理しており、このアプリ用のサブドメインを払い出せる

### 課題 (Complication)

LAN 内とはいえ、次の点が平文 HTTP のままでは解決できない。

1. **PIN とトークンが平文で流れる** — 保護者 PIN と `X-Parent-Token` が LAN 上を素通しで流れている。家庭内の Wi-Fi にはゲストや子どもの端末も接続する
2. **Secure Cookie が使えない** — トークンを `HttpOnly; Secure` な Cookie へ移す改善が、HTTPS でないと成立しない
3. **PWA 化できない** — Service Worker は secure context を必須とする。子どもの端末でホーム画面に追加して使わせたいが、HTTP では実現できない
4. **IP アドレス直打ちの運用が定着している** — Pi の IP が変わるたびに家族へ周知が必要で、家庭内ツールとして扱いにくい

### 論点 (Question)

1. 証明書をどこから、どの検証方式で取得するか
2. TLS をどこで終端するか
3. 名前解決をどう用意し、LAN 内からどう到達させるか
4. インターネットへ公開するか否か

### 検討した選択肢 (Options)

- **案1: Caddy + Let's Encrypt（DNS-01 / Cloudflare）で LAN 内に閉じる**
  - 概要: パブリック DNS に Pi の LAN IP を指す A レコードを置き、DNS-01 チャレンジで証明書を取得。Pi 上の Caddy が TLS を終端して `127.0.0.1:3210` へリバースプロキシする
  - メリット: ブラウザに正規に信頼される証明書が得られる。**Pi をインターネットへ公開しなくてよい**（80/443 の穴あけ不要）。端末側の準備が一切不要。ワイルドカードが取得でき、今後の家庭内サービスにも使い回せる。取得・更新が全自動
  - デメリット: パブリック DNS にプライベート IP が載る。DNS リバインディング保護に当たる場合がある。Cloudflare API トークンを Pi 上に置く必要がある

- **案2: Cloudflare Tunnel で Web UI も公開し、Cloudflare Access で認証をかける**
  - 概要: 既存の Tunnel に Web UI のホスト名を追加し、TLS は Cloudflare が終端する
  - メリット: 既存インフラの再利用。外出先からも使える。証明書の管理が不要
  - デメリット: 子どもに認証手段（Google アカウント / メール OTP）を用意させる必要があり、ADR-0001 で「操作が煩雑」として退けた案 4 に逆戻りする。家庭内からの利用でも Cloudflare を往復する。認証設定を誤ると子ども向け UI が無防備に公開される

- **案3: Cloudflare Origin CA 証明書を使う**
  - 概要: Cloudflare が発行する 15 年有効の証明書を Pi に置く
  - メリット: 有効期間が長く、更新の運用が不要
  - デメリット: **Cloudflare のプロキシを経由する前提の証明書であり、ブラウザは信頼しない。** LAN 直アクセスという今回の要件では使えない

- **案4: 内部 CA / mkcert による自己署名**
  - 概要: 自前の CA を立てて証明書を発行する
  - メリット: 外部サービスへの依存がなく、ドメインも不要
  - デメリット: 家族の全端末に CA 証明書をインストールする必要がある。iOS は「プロファイルのインストール」＋「証明書信頼設定」の 2 段階を要し、子どもの端末が増えるたびに作業が発生する

- **案5: Tailscale の `tailscale serve` を使う**
  - 概要: tailnet 内で `*.ts.net` の証明書を自動取得する
  - メリット: 証明書も名前解決も自動。外出先からも使える
  - デメリット: 全端末に VPN クライアントの導入が必要。せっかく管理しているドメインを活かせない

- **案6: 案1 + 案2 のハイブリッド（split-horizon DNS）**
  - 概要: 同一 FQDN に対し、内部はローカル DNS で LAN IP、外部は Tunnel で解決させる
  - メリット: 家庭内は低遅延の直接接続、外出先からも利用可能
  - デメリット: ローカル DNS サーバーの運用が必要。外部公開する以上、案2 の認証の課題をそのまま抱える

## 決定

**案1 を採用する。** Pi 上で Caddy を動かして TLS を終端し、証明書は Let's Encrypt の DNS-01 チャレンジ（Cloudflare DNS プラグイン）で取得する。Web UI はインターネットへ公開せず、家庭内 LAN からの利用に限定する。

この案を選んだ理由は次の 3 点である。

1. **公開せずに正規の証明書が得られる。** DNS-01 は Let's Encrypt が Pi へ到達する必要がないため、ルーターに穴を開けずに済む。「TLS のために攻撃面を広げる」という本末転倒を避けられる
2. **家族の操作が一切増えない。** ADR-0001 で「認証は LAN 内利用には過剰」と判断した方針を維持したまま、通信路だけを保護できる。案2・案5 は子どもの操作や端末準備を増やす
3. **今後の拡張の土台になる。** ワイルドカード証明書を 1 枚持つことで家庭内の他サービスにも展開でき、外出先アクセスが必要になった際も、Caddy を前段に置いたまま Tunnel を足して案6 へ移行できる

構成一式は `deploy/caddy/`（Dockerfile / docker-compose.yml / Caddyfile / 手順書）に置く。Caddy は Docker の host ネットワークで動かし、`127.0.0.1:3210` へリバースプロキシする。

あわせて `rpi-bridge` の `BIND_HOST` を `127.0.0.1` に戻す。Caddy が前段に立つため LAN へ直接バインドする必要がなくなり、平文の `:3210` を LAN から到達不能にできる。

## 影響

### メリット

- 保護者 PIN と `X-Parent-Token` が LAN 上を平文で流れなくなる
- `https://rotom.<家庭用ドメイン>/` という覚えやすい URL になり、Pi の IP 変更が家族に影響しなくなる
- 証明書の取得・更新が全自動になる（cron や certbot の運用が不要）
- secure context が満たされ、PWA 化とトークンの Secure Cookie 化への道が開ける
- ワイルドカード証明書により、家庭内サービスの追加が A レコードと `handle` ブロックの追記だけで済む

### デメリット・トレードオフ

- パブリック DNS に Pi のプライベート IP が載る（実害は小さいが、内部アドレスの露出ではある）
- Cloudflare API トークンを Pi 上に保持する必要がある。権限は `Zone:DNS:Edit`・対象ゾーン限定に絞って影響範囲を抑える
- ルーターや Pi-hole の DNS リバインディング保護に当たる場合、例外設定が必要になる
- Caddy というコンポーネントが 1 つ増える（Docker 前提の環境になる）
- 案2・案5 と異なり、**外出先からは利用できない**。これは ADR-0001 の方針を引き継いだ意図的な割り切りである

### 今後チームが意識すべきこと

- `deploy/caddy/.env` と Cloudflare API トークンはコミットしない（`.gitignore` 済み）
- `caddy_data` ボリュームを削除しない。証明書と ACME アカウント鍵が失われ、Let's Encrypt のレート制限に近づく
- HSTS の `max-age` は当面 1 時間とする。一度ブラウザに焼き付くとその期間 HTTP へ戻せないため、構成が安定するまで伸ばさない
- 設定を試行錯誤する際は `Caddyfile` の `acme_ca` でステージング環境を使う
- ホスト名を追加する際は、`Caddyfile` の `handle` ブロックに定義を足す。未定義のホスト名は `abort` で接続を切る方針とする
