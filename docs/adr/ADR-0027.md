# ADR-0027: ai-rotom のローカル改修は上流に送らず、パッチとセットアップスクリプトで維持する

## ステータス

採用

## コンテキスト

### 状況 (Situation)

rpi-bridge は `@nonz250/ai-rotom` の MCP サーバーを stdio で起動し、ポケモンチャンピオンズの
ツール群を LLM に渡している（[ADR-0006](./ADR-0006.md)）。起動方式は `AI_ROTOM_COMMAND` /
`AI_ROTOM_ARGS` で差し替えられ（[ADR-0019](./ADR-0019.md)）、実際の `rpi-bridge/.mise.local.toml`
は `~/ai-rotom/packages/mcp-server/dist/index.mjs` を指している。

`~/ai-rotom` には上流にないローカル差分が入っている。

1. **名前解決の補完** — フォルム接尾辞付きの名前しか持たない種（例: `ギルガルド(シールドフォルム)`）は、
   素名 `ギルガルド` での照合が完全一致で引っかからない。`NameResolver` に ja→en 専用のエイリアスを
   追加し、ベースフォーム名から接尾辞を剥がした素名を補完している
2. **pnpm への移行** — 上流は npm で管理しているが、この環境は pnpm に統一している。pnpm の隔離
   `node_modules` では `shared/` から `packages/mcp-server` の依存（`@smogon/calc`, `zod`）を
   解決できないため、root の devDependencies に追加している

### 課題 (Complication)

- 差分は実行時のツール動作に直結する。素名解決がないと、AI が日本語の素名でツールを呼んだときに
  「名前が見つからない」で終わる
- 上流へ PR を出す方針は取らない。修正がこのアプリ固有の前提（日本語での呼びかけ、pnpm 運用）に
  依存しており、上流の設計判断を縛りたくない
- 一方で差分は `~/ai-rotom` の作業ツリーに**未コミット**で置かれていた。`git checkout .` や
  ディスク故障で失われる。`dist/` は Git 管理外なので「どのソースから作った dist か」の記録もない
- 上流の main は 1.3.5 より先に進んでおり、追従には手作業の rebase が要る

### 論点 (Question)

上流に PR を出さずにローカル改修を維持しつつ、マシンが壊れても同じビルドを再現でき、上流追従も
破綻しない運用は何か。

### 検討した選択肢 (Options)

- **案A: ローカルブランチ + パッチ + セットアップスクリプト** — `~/ai-rotom` で `local/rpi-bridge`
  ブランチを切り、差分を `patches/ai-rotom/*.patch` としてこのリポジトリに置く。再現はスクリプト化する
- **案B: rpi-bridge 側で名前解決を吸収する** — ai-rotom の `pokemon.json` に依存することになり、
  上流のデータ更新に追従できない。フォルム種のマップをアプリ側に持つと二重管理になる
- **案C: fork して自リポジトリに push する** — 管理対象が 1 つ増える。PR を出さないならパッチで足りる
- **案D: npm 版（1.3.5）に戻す** — 素名解決が壊れる。1.3.5 にも該当処理はない
- **案E: 未コミットのまま維持する** — 差分がどこにも保存されない。現状の課題そのもの

## 決定

**案A を採用する。ローカルブランチを唯一の正とし、差分をこのリポジトリにパッチとして保存する。
セットアップはスクリプトで再現する。**

1. `~/ai-rotom` に `local/rpi-bridge` ブランチを作り、差分をコミットする。`main` は上流追従専用にする
2. 差分を `patches/ai-rotom/*.patch`（`git format-patch` 形式、適用順はファイル名の昇順）として
   このリポジトリに置く。基準は上流タグ `1.3.5`
3. `scripts/setup-ai-rotom.sh` が「clone → パッチ適用 → `pnpm install` → `pnpm build`」を再現する
4. 上流追従は**四半期に一度、意図的に**行う。手順は `patches/ai-rotom/README.md` に書く

### なぜパッチをアプリ側に置くか

上流に送らない差分は、送らない側のリポジトリに置かないと所在が消える。`~/ai-rotom` はビルド環境で
あって、正ではない。パッチならコードレビューの対象になり、上流の更新で当たらなくなったことも
検出できる。

## 影響

### メリット

- 差分がこのリポジトリでレビューできる。マシンが壊れても `setup-ai-rotom.sh` で復元できる
- 上流の更新に追従するとき、どこが衝突したかがパッチ適用で分かる
- 将来 PR を出したくなったとき、コミットが整理されているのでそのまま使える

### デメリット・トレードオフ

- 上流追従は自動化しない。`1.3.5` にピン留めし、追従は意図的な作業として行う
- `pnpm-lock.yaml` をパッチに含むため、パッチが大きい（約 180KB）。上流の依存が変わるたびに
  lock を作り直す必要がある
- `patches/ai-rotom` の更新を忘れると、`setup-ai-rotom.sh` が古いビルドを作る

### 今後チームが意識すべきこと

- 上流に追従したら、**必ずパッチを作り直して** `BASE_REF` を更新する
- `packages/mcp-server/src/tools/analysis/find-counters.test.ts` の
  「弱点タイプ攻撃技を覚える候補が 10 件を超える target」は Raspberry Pi 上で 60 秒の
  タイムアウトを超える（2026-10-27 時点・パッチとは無関係の性能問題）。追従時のテストは
  この 1 件を除いて合格を確認する
- `~/ai-rotom` のパスは `.mise.local.toml` に絶対パスで書かれている。場所を変える場合は
  `AI_ROTOM_ARGS` も更新する
- 起動ログの `[ai-rotom] 起動方式:` で、ローカルビルドが使われているかを確認できる
