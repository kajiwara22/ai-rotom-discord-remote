# ADR-0014: 使用率ランキングの取り込みは「順位＋ポケモン名」の一覧を r.jina.ai で都度取得する 1 ツールとし、数値の使用率は対象外とする

## ステータス

採用

> 実データ（https://yakkun.com/ch/ranking.htm）を r.jina.ai 経由で取得し、構造と
> サイズを実測して論点を整理した。**「使用率ランキング」と名が付くが、ページに数値の
> 使用率（%）は掲載されていない**点が本 ADR の最重要前提。壁打ちの結果、「順位のみ
> 取り込み・解説文は含めない・都度取得＋メモリキャッシュ」の 3 点で確定した。

## コンテキスト

### 状況 (Situation)

「今の環境で強いポケモンは」「このポケモンは今どれくらい使われているの」という問いに
チャット（Discord / Web UI）で答えられるようにしたい。対象は yakkun.com の
ポケモンチャンピオンズ「使用率ランキング」
（`https://yakkun.com/ch/ranking.htm`、シングル/ダブルの 2 種）。

既存の取り込みパターンは 2 つあり、いずれも bridge 側に閉じる。

- **対戦記録（ADR-0010）**: R2 の Parquet を DuckDB で都度読み、保存しない（常に最新）。
- **育成論（ADR-0013）**: r.jina.ai（`x-respond-with: html`）で取得し、SQLite の
  専用テーブル `theory_refs` に URL キーで保存。解析はベストエフォート。

yakkun.com は Cloudflare チャレンジで保護されており、素の fetch は 403。取得は
r.jina.ai 経由が確立済みの手段（ADR-0013）。取得・解析の実装は `theory-import.ts` に
集約されており、その fetch（EUC-JP→UTF-8 変換込み）は流用可能。

### 課題 (Complication)

ページの実構造を実測した結果は以下のとおり。

| 項目 | 実測 |
|---|---|
| ルール | シングル（既定）/ ダブル（`?rule=double`）。**順位は別物**（例: シングル 1 位ガブリアス、ダブル 1 位ドドゲザン） |
| 掲載件数 | **各ルール 100 件**（1〜100 位） |
| 1〜25 位 | `<h2 id="N位: 名前">` の個別セクション。名前・タイプ・種族値・特性・**解説文（各約 2.2KB）** |
| 26〜100 位 | `rank_short_list` に順位＋名前＋リンクのみ（セクション見出しは「26位～50位」だが実体は 26〜100 位） |
| 更新日 | 本文に「データの最終更新日: 2026/08/20」 |
| 数値の使用率 | **掲載なし**（`%` は種族値バーの CSS `--value` のみ。使用率の数値はページ全体に存在しない） |
| ページサイズ | 素 HTML 約 125KB（うち `<main>` 約 76KB） |

これにより、次の論点が立つ。

1. **「使用率」ではなく「順位」しか取れない**。ユーザーが期待する「ガブリアスは何 %」
   という数値はこのページからは得られない。名称と実データのギャップを ADR で明示しないと、
   あとで「数値が取れてない」と誤解される。
2. **名前の表記が MCP の名前と一致する保証がない**。`メガギャラドス`・`イダイトウ♂`・
   `ダイケンキ(ヒスイ)`・`キュウコン(アローラ)` など、yakkun の表記（フォルム名を
   `<span class="form_name">` で持つ）がそのまま返る。AI が既存の `get_pokemon_info` 等に
   渡すとき、名前の対応が取れるかが実運用の成否を分ける。
3. **1〜25 位の解説文をどうするか**。取り込めば 25 件 × 約 2.2KB ≈ 55KB になり
   ADR-0006 の整形が要る。取り込まなければ、順位表は名前だけ（100 件 ≈ 3KB）に収まる。
4. **保存の要否**。更新は「時々」で、対戦記録（都度読み）と育成論（SQLite キャッシュ）の
   どちらの型を採るか。

### 論点 (Question)

1. 取り込む範囲をどこに引くか（順位のみか、解説文・種族値・特性も含めるか）。
2. 取得・保存の方式（都度取得 / メモリキャッシュ / SQLite 保存）。
3. ツールの形（1 本にまとめるか、一覧と詳細に分けるか）。
4. 鮮度（更新日）を AI にどう伝えるか。

### 検討した選択肢 (Options)

#### 取り込む範囲

- **案1: 順位＋名前のみ（推奨）**
  - 概要: `{ rule, updatedAt, ranking: [{ rank, name }] }` だけを返す。解説文・種族値・
    特性・タイプは取り込まず、詳細が要るときは AI が既存の `get_pokemon_summary` /
    `get_pokemon_info` を呼ぶ。
  - メリット: 100 件で実測 3,067 字。ADR-0006 の整形が不要。このページ固有の価値
    （＝「今どれが人気か」という順序）だけを確実に届け、それ以外は MCP の正規データに
    一本化できる。
  - デメリット: 解説文（著者の環境読み）は失われる。ただし実測した解説文は
    「ガブリアスは物理アタッカーで…弱点はこおり・ドラゴン・フェアリー」という
    一般解説であり、`get_pokemon_summary`（防御相性・実数値まで返す）と重複する。
- **案2: 順位＋名前＋解説文（1〜25 位）**
  - 概要: 個別セクションの解説文も抽出して返す。26 位以下は名前のみ。
  - メリット: ページの「読み物」としての価値を残せる。
  - デメリット: 25 件 × 2.2KB ≈ 55KB で ADR-0006 の整形関数が必須。解説文の内容は
    一般知識と重複が多く、追加の判断材料になりにくい。
- **案3: 順位＋名前＋種族値＋特性（1〜25 位）**
  - メリット: 一覧だけで型の概形が見える。
  - デメリット: 種族値・特性は MCP の正規データと重複し、二重管理になる。不要。

#### 取得・保存の方式

- **案A: 都度取得＋モジュール内メモリキャッシュ（推奨）**
  - 概要: 呼び出しのたびに r.jina.ai から取得・解析し、プロセス内キャッシュに
    TTL（例: 24 時間）で保持する。DB には書かない。
  - メリット: マイグレーション不要。更新が「時々」でも、同一セッション内の連続
    呼び出しは 125KB の再取得を避けられる。常にほぼ最新。
  - デメリット: プロセス再起動でキャッシュは消える（＝再取得）。TTL をどうするか
    が運用上の判断になる。
- **案B: SQLite に保存（theory_refs と同型）**
  - 概要: 専用テーブルに順位表を保存し、更新日が古ければ再取得。
  - メリット: 永続化され、取得回数を最小化できる。
  - デメリット: マイグレーション＋鮮度管理（TTL・再取得契機）の設計が必要。
    100 件の順位表ごときの永続化は過剰。ADR-0013 が URL キーのキャッシュを採ったのは
    「同じ URL は同じ内容」だからで、順位表は同じ URL でも中身が変わる（＝キャッシュ
    のキーとして成立しづらい）。
- **案C: 毎回都度取得（キャッシュなし）**
  - メリット: 最も単純。常に最新。
  - デメリット: 1 回の問いの中で AI が複数回呼ぶと、そのたび 125KB を引き直す。

#### ツールの形

- **案①: 1 本 `get_usage_ranking`（推奨）**
  - 引数: `rule`（single / double）、`top`（省略時 100）、`pokemon`（省略可、指定時は
    該当ポケモンの順位を返す）。
  - 返り値: `{ rule, updatedAt, ranking }` または `pokemon` 指定時の `{ rule, rank, name }`。
  - メリット: 呼び出しが 1 往復で済む。`get_condition_info`（category/name で絞る）と
    同じ操作感。
- **案②: 一覧と詳細の 2 本（list_matches / get_match 型）**
  - メリット: 対戦記録と対称。
  - デメリット: 順位表は全量でも 3KB で、詳細（解説文）を返さない案1 なら分割する
    意味がない。往復が増えるだけ。

## 決定

- **取り込むのは「順位＋ポケモン名」の一覧のみ**とし、数値の使用率・解説文・種族値・
  特性・タイプは取り込まない（案1）。理由は、このページ固有の価値は「今どれが人気か」
  という**順序**だけであり、それ以外は既存の `get_pokemon_summary` / `get_pokemon_info`
  がより正確に持っているため。数値の使用率はページに存在しない以上、最初から対象外と
  明示する。
- **取得は r.jina.ai（ADR-0013 と同型）とし、保存しない**（案A）。プロセス内メモリ
  キャッシュに TTL（24 時間）で保持する。**キャッシュキーは `rule` ごと**（シングルと
  ダブルは別々のランキング・別 URL のため、別エントリとして保持する）。更新周期が
  実測で約 1 週間（更新日 8/20 を 8/26 時点で確認）であるため、1 時間 TTL では 1 日
  24 回の無駄な再取得になり、yakkun と r.jina.ai の双方に不要な負荷をかける。
  DB マイグレーションは行わない。順位表は「同じ URL でも中身が変わる」ため、URL キーの
  永続キャッシュ（theory_refs 型）は採らない。キャッシュはプロセス内に閉じるため、
  再起動すれば自然に再取得される。TTL 分の鮮度のずれは `updatedAt` を常に返すことで
  利用者に可視化してあるため許容する。
- **ツールは `get_usage_ranking` 1 本**（案①）。`rule`（single / double）、`top`、
  `pokemon`（任意）を受け、`{ rule, updatedAt, ranking: [{ rank, name }] }` を返す。
- **鮮度は `updatedAt`（ページの「データの最終更新日」）を必ず返す**。AI には
  「◯月◯日時点の順位」と明示させる。この指示は**ツールの description に書く**
  （システムプロンプトは Web/Discord の経路差があるため、ツール側で完結させる）。
- **名前は yakkun の表記のまま返し、変換しない**（`メガギャラドス`・`イダイトウ♂`・
  `ダイケンキ(ヒスイ)`・`キュウコン(アローラ)` 等）。フォルム名は `<span class="form_name">`
  を連結して復元する。既存ツールへの名前の引き渡しは AI に委ね、こちらで勝手に
  正規化して MCP の名前とずらす事故を避ける。

## 影響

### メリット

- 「今の環境で強いポケモン」「このポケモンは何位」に、生の順位データで答えられる。
- 全量 100 件でも約 3KB で ADR-0006 の整形が不要（実測済み）。ツール追加の手間が小さい。
- 保存しないためマイグレーション不要。取得・解析とも bridge 内に閉じ、MCP を変更しない。
- シングル／ダブルの 2 環境を同じ 1 ツールで扱える。

### デメリット・トレードオフ

- **数値の使用率には答えられない**。「何 %」と聞かれたら「順位しか公開されていない」と
  AI が説明できるようにする必要がある（ツール説明に明記）。
- r.jina.ai への外部依存（ADR-0013 と同型。レート制限・SLA なし）。
- 解説文（1〜25 位の環境読み）は失われる。ただし実測上は一般解説と重複しており、
  失う判断材料は小さい。
- 名前表記の揺れ（フォルム名）により、AI が既存ツールに渡す際に名前解決に失敗する余地が
  残る。フォルム名の復元は解析側で丁寧にやる。

### 今後チームが意識すべきこと

- **yakkun.com を直接 fetch しない**（403）。必ず r.jina.ai 経由。
- **「使用率ランキング」という名称に引きずられない**。このデータは「順位表」であり、
  数値の使用率ではない。AI にも「順位しか分からない」ことを言わせる。
- **フォルム名は削らない**（`(アローラ)` 等）。順位表の名前を `get_pokemon_info` に
  渡すときの材料になるため、解析時に `form_name` を連結して保存・返却する。
- **整形は不要だが、前提は「名前のみを返す」こと**。将来、解説文や種族値を応答に
  足すときは必ずサイズを測り直す（ADR-0006）。1〜25 位の解説文を全部入れると 55KB 超で
  素通し上限を大きく超える。
- **進捗表示の語彙を追加する**（`tool-progress.ts` の分類と `app.js` の
  `L.kids` / `L.junior` の `progress`）。

### 関連する ADR・追加作業

- ADR-0006（ツール結果の整形）: 本 ADR のツールは実測により整形不要と判断。前提崩れに注意。
- ADR-0013（育成論取り込み）: r.jina.ai 経由の取得・EUC-JP 処理・Playwright フォール
  バックを同型で流用する。
- ADR-0010（対戦記録）: 「保存せず都度読み、常に最新」という方針を順位表にも適用。
  ただし順位表はキャッシュキー（URL）が内容を固定しない点で異なる。
- 実装済み: `get_usage_ranking` の定義（tool-definitions.ts）、実行分岐（index.ts）、
  取得・解析＋メモリキャッシュ（新モジュール `ranking.ts`。r.jina.ai 取得＋
  EUC-JP→UTF-8 処理は ADR-0013 と同型）、進捗語彙（tool-progress.ts の `ranking` 種別、
  app.js の `L.kids` / `L.junior` の `progress.ranking`）。
- Playwright フォールバックは持たない（単発・低頻度のため jina 一本。ADR-0013 の
  フォールバックが必要になればそのとき足す）。
