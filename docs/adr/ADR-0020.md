# ADR-0020: ツール結果の整形とパーティ名前空間の適用はブリッジの共有実行層へ一本化し、整形済み実行 API として外部へ公開する

## ステータス

採用

> 壁打ちで確定させた論点（DP1〜DP6）を反映し、API のパスとスキーマ・戻り値の契約・
> エラーの返し方・タイムアウトの引き継ぎ方を確定させた。実行バックエンドの
> ファイル名と match-repository（DuckDB/R2）の実キャンセルのみ TBD として残す。

## コンテキスト

### 状況 (Situation)

ツール結果の整形（[ADR-0006](./ADR-0006.md) の `tool-result-formatter.ts`）と
パーティ名前空間の適用（[ADR-0009](./ADR-0009.md) の `party-namespace.ts`）は、
いずれも `ai-service.ts` の `createToolExecutor()` 内に閉じ込められている。

現在の適用順は次のとおり。

```
① applyPartyNamespace(toolName, args, namespace)   … 実行前: パーティ名へ接頭辞を前置
② POST /tools/:name（生出力を返す）
③ stripPartyNamespace(toolName, raw, namespace)    … 実行後: 接頭辞を除去・絞り込み
④ formatToolResult(toolName, raw)                  … 実行後: 整形（ADR-0006）
```

`POST /tools/:name` は生出力をそのまま返す。`find_counters` は実測 5,692,717 字に
達し、整形・名前空間はこの ask パイプラインの中だけで適用される。アクティブな
in-repo 利用者は `ai-service.ts` のみである（`worker/src/mcp-bridge.ts` /
`conversation-do.ts` は旧構成の遺産）。

並行して、**pi web 上の pi（コーディングエージェント）から同ツール群を使う案**
（ツールレベル統合。以下「pi 連携」）を検討している。pi は extension の
`registerTool()` でカスタムツールを呼べるが、組み込みの MCP クライアントは持たない。

### 課題 (Complication)

#### 1. 整形・名前空間が ask ループに密結合している

整形も名前空間も `ai-service.ts` の中でのみ機能し、ask パイプラインを経由しない
利用者（pi の extension、curl によるデバッグ、将来のツールプレイグラウンド等）から
到達できない。

#### 2. pi が素の `/tools/:name` を叩くと、両方の層が素通りする

pi 連携で pi が `POST /tools/:name` を直接呼ぶと:

- `find_counters` の 5.7MB がそのまま pi の文脈に入り、破綻する
- パーティ系ツールが名前空間なしの生の棚（`~/.ai-rotom/parties.json` の `name`
  そのまま）へ保存され、Web UI / Discord のパーティと別物になる
  （[ADR-0009](./ADR-0009.md) が「`POST /tools/:name` を直接叩けば分離を迂回できる」
  と注記した抜け穴が、新たな正規利用者に踏まれる形になる）

#### 3. 整形層を単体で検証する手段がない

本プロジェクトはテストが無く型チェックのみ（AGENTS.md）。整形層は現在、
OpenCode Go キー＋ネットワーク込みのフルパイプラインを回さないと結果を確認できず、
[ADR-0006](./ADR-0006.md) の「ツール追加時は実測してから整形要否を判断」という運用も
回しにくい。

#### 4. 自プロセスへの loopback HTTP で生出力を往復させている

`ai-service.ts` と HTTP サーバーは同一プロセスである。にもかかわらず
`createToolExecutor` は自プロセスの `/tools/:name` を HTTP で叩き、生の巨大出力を
受けてから整形している。シリアライズ／パースの無駄があり、巨大出力ほど顕著になる。

### 論点 (Question)

1. 整形・名前空間の適用をどこに置くか（`ai-service.ts` 内のまま／ブリッジの API
   境界に寄せる）
2. 外部利用者へどの形で公開するか（既存エンドポイントへのフラグ追加／新エンドポイント）
3. 既存の Discord / Web パイプラインを乗せ替えても、挙動が不変であることをどう保つか

### 検討した選択肢 (Options)

- **案A: 現状維持（整形・名前空間は `ai-service.ts` 内。pi 側へ同ロジックを再実装）**
  - 概要: pi の extension 側に TypeScript で整形関数を移植する（または skill で近似）。
  - メリット: ブリッジに変更が不要。
  - デメリット: 整形・名前空間のロジックが二重管理になる。上流の出力形式変更時に
    両方へ追従が必要。単体検証の問題も解決しない。却下。

- **案B: 既存 `/tools/:name` にフラグを追加（`?formatted=1` 等）**
  - 概要: クエリで整形の有無を切り替える。
  - メリット: エンドポイントが増えない。
  - デメリット: 名前空間の `apply`（実行前の引数書き換え）は整形フラグでは表現しきれ
    ない（実行前に行う必要がある）。既定を生のままにすると責務が分散したまま、
    既定を整形に変えると `ai-service.ts` のローカル整形との二重整形を壊す。
    半端な分離になるため却下。

- **案C: 共有実行層の新設と、整形済み実行エンドポイントの公開（採用案）**
  - 概要: ①〜④ を `ai-service.ts` から切り離してブリッジの共有実行層（`tool-runner.ts`
    相当）へ一本化する。`ai-service.ts` はプロセス内でこれを直接呼び、外部利用者は
    HTTP エンドポイント `POST /api/tools/:name/run` で同じ実行層へ到達する。
  - メリット:
    - 整形・名前空間の責務がブリッジの 1 箇所に集約され、二重管理が消える
    - `ai-service.ts` と pi が同じ実行層を共用し、将来の整形改良が双方へ自動で効く
    - curl で整形層を単体検証できる（論点3の再現・検証が容易になる）
    - `ai-service.ts` の loopback HTTP が廃止され、巨大出力のシリアライズが消える
  - デメリット:
    - 共有関数の切り出しとエンドポイント追加というリファクタが必要
    - 生出力が不要な利用者（現状 `ai-service.ts` のみ）にとっては内部実装が 1 層増える

## 決定

### 整形・名前空間の適用を共有実行層へ一本化する（案C）

`applyPartyNamespace` → ツール実行 → `stripPartyNamespace` → `formatToolResult` の
順を、`ai-service.ts` から切り離して共有実行層へ移す。この層が「LLM に渡る形の
ツール結果」の唯一の正（single source of truth）となる。

- 共有実行層は `runTool(namespace, toolName, args)` の形をとり、実行バックエンド
  （MCP `client.callTool` と、match / theory / ranking / review の各実行関数）を
  注入できるようにする。`index.ts` の `handleToolCall` が今持つ実行分岐をバックエンド
  として切り出し、`handleToolCall`（生）と共有実行層の両方から使う。
- `runTool` の戻り値は `{ ok: true, text } | { ok: false, error }` の構造体とする
  （DP1）。「LLM に渡る文字列」に閉じず、成否を判定できる形にする。
  - `ai-service.ts` 側: `ok` なら `text` を、`!ok` なら
    `JSON.stringify({ success: false, error })` をツールメッセージへ入れる（現行の
    `createToolExecutor` が LLM に渡していた文字列と一致させる）
  - HTTP 側: 構造体をそのままエンベロープへ写す（下記）
- **`ai-service.ts` は共有実行層をプロセス内で直接呼ぶ**。自プロセスへの loopback
  HTTP は廃止する。これにより課題4の巨大ペイロード往復が消える。
- 適用順と結果は従来と同一とし、Discord / Web の挙動を変えない。

### 外部利用者向けに `POST /api/tools/:name/run` を設ける

共有実行層の上に、薄い HTTP エンドポイントを載せる。既存の `POST /tools/:name`
（生）はツール実行のプリミティブとして残し、外部利用者は原則この新エンドポイント
を使う。

```
request:  POST /api/tools/:name/run
body:     { "args": { ... }, "user_id": "yutaka" }
response(成功, 200):        { "success": true, "content": [{ "type": "text", "text": "<整形済み>" }] }
response(ツール失敗, 200):  { "success": false, "error": "..." }
response(不正リクエスト, 400): { "error": "..." }
```

- `user_id` は必須。`webNamespace(userId)`（＝ `user:{userId}`）を導出して共有実行層へ
  渡す（[ADR-0009](./ADR-0009.md)）。Discord 経路はこのエンドポイントを通さず、
  `ai-service.ts` が従来どおり `discord` 名前空間で共有実行層を直接呼ぶ（DP4）。
- ステータスコードは、実行が例外を投げた場合（MCP タイムアウト・接続断・ブリッジ側
  実行関数の throw）は **200 で `{ success: false, error }`** を返す（DP2）。一方、ツールが
  論理エラーを出力に含めて返した場合（未収録・パーティが見つからない等）は従来どおり
  `{ success: true, content: [...] }` とし、エラーテキストを content に載せる（MCP の
  「ツール結果としてのエラー」と同じ扱い。整形層が素通しする）。どちらも 5xx にせず、
  pi 側の LLM がエラー内容を読んでループを継続できる。`args` の parse 不能・
  `user_id` 欠落のみ 400 とする。
- 認証は持たない。家庭内 LAN 前提という既存 API と同じ前提（[ADR-0002](./ADR-0002.md)、
  [ADR-0009](./ADR-0009.md)）に従い、インターネットへ公開する場合は前段の認証を必須
  とする。`user_id` を変えれば他ユーザーの棚に到達できるが、これは既存の
  `/api/web/ask` と同じ前提であり、本 ADR では許容する。

### 既存パイプラインの乗せ替えは挙動不変を条件とする

`ai-service.ts` の `createToolExecutor` を共有実行層の呼び出しへ置き換える。置き換えの
際に失われないよう、以下を明示的に引き継ぐ（DP3）。

- **60 秒の打ち切りは `runTool` を `Promise.race` + 60 秒で包んで維持する**。これは
  現行と同じ「待つのを諦めて LLM に失敗を返す」挙動であり、HTTP 往復の廃止で
  挙動が変わらない。なお現行の loopback `fetch` の abort も、背後の実行
  （MCP `callTool` や DuckDB/R2 読み込み）を止めてはいなかった（give-up-waiting）。
- **MCP は `client.callTool` の `timeout` オプション（SDK 1.29.0 が対応）で実キャンセル
  する**。60 秒を渡し、abort では実現できていなかったキャンセルを追加する（低リスクな
  改善）。`theory-import` / `ranking` は既に自前の fetch timeout を持つため、従来どおり。
- **`match-repository`（DuckDB httpfs → R2）の実キャンセルは今回見送る**。外側の
  `Promise.race` による give-up-waiting で従来と同じ上限は維持される。実キャンセル
  の要否は TBD として別途検討する。
- 失敗を例外にせず構造体で返す挙動（DP1）は、`ai-service.ts` 側で現行と同じ文字列へ
  写すことで維持する。

## 影響

### メリット

- 整形・名前空間がブリッジの 1 箇所に集約され、`ai-service.ts` と pi 連携の双方が
  同じ正を共用する。二重実装・二重メンテナンスが消える。
- pi 連携では、pi の extension が「`user_id` 固定 + args を投げる」だけで整形済み・
  名前空間処理済みの結果（≤6,000 字）を得られる。5.7MB の素通りと、パーティの
  名前空間漏れが同時に防げる。
- 整形層を curl 1 本で単体検証できるようになる。[ADR-0006](./ADR-0006.md) の
  「ツール追加時は実測してから整形要否を判断」という運用の再現性が上がる。
- `ai-service.ts` の自プロセス loopback HTTP が廃止され、巨大出力のシリアライズ／
  パースが 1 回分減る。

### デメリット・トレードオフ

- 共有関数の切り出し＋エンドポイント追加というリファクタが発生する。実行バックエンド
  の注入方法など、切り出し時の設計判断が 1 つ増える。
- `POST /api/tools/:name/run` は認証を持たないため、外部公開時は前段の認証が必須。
  家庭内 LAN 前提を崩す運用では、素の `/tools/:name` と同じく分離・整形の意味が
  薄れる点は変わらない（整形はされるが、誰でも実行できる）。
- 生出力が必要な利用者が増えた場合（デバッグ等）、`/tools/:name`（生）と
  `/api/tools/:name/run`（整形済み）の 2 口の使い分けが生じる。現時点の生出力利用者は
  `ai-service.ts` のみで、これは共有実行層へ移行するため、実質の生利用者は消える。

### 今後チームが意識すべきこと

1. **整形・名前空間は共有実行層を通して適用すること**。`ai-service.ts` や pi 連携側で
   個別に整形・名前空間を再実装しない。二重管理に戻らない。
2. **上流のバージョンを上げたら共有実行層の出力を確認する**。[ADR-0006](./ADR-0006.md)、
   [ADR-0009](./ADR-0009.md) と同じく、上流の出力形式変更は整形・名前空間の壊れ方として
   現れる。
3. **ツール実行の 60 秒打ち切りは `runTool` の `Promise.race` で維持する**。MCP の実
   キャンセル（`callTool` の `timeout`）と、外側の打ち切りの両方を忘れずに設定する。
   `match-repository`（DuckDB/R2）の実キャンセルは未対応のままである点に注意する。
4. **接頭辞は内部表現であり、利用者や AI に見せる場面では必ず外す**（[ADR-0009](./ADR-0009.md)
   の原則を共有実行層でも守る）。

### 関連する ADR・追加作業

- [ADR-0006](./ADR-0006.md): ツール別整形層。本 ADR はその適用箇所を ask ループから
  共有実行層へ移すもの。整形方針そのものは変わらない。
- [ADR-0009](./ADR-0009.md): パーティ名前空間。本 ADR は「名前空間は executor の
  クロージャに閉じ込める」という実装位置の決定を改め、適用箇所を共有実行層へ移す。
  名前空間の方式（接頭辞・単一 MCP プロセス）は変わらないため、ADR-0009 のステータスは
  採用のままとする（差し替えではない）。
- 実装メモ:
  - 共有実行層（`tool-runner.ts` 相当・新設）: `runTool(namespace, toolName, args)` を
    実装。戻り値は `{ ok, text | error }`。
  - `index.ts`: 実行分岐をバックエンド関数（`executeToolRaw`）へ切り出し、
    `POST /api/tools/:name/run` を追加。`handleToolCall`（生）も同バックエンドの上に
    再構築する（DP5）。
  - `ai-service.ts`: `createToolExecutor` を共有実行層の直接呼び出しへ置き換え、戻り値
    を現行と同じ文字列へ写す。
  - 挙動不変の検証: 代表ツール（`find_counters` / `list_speed_tiers` / `load_party` /
    `list_matches`）で before/after の整形後文字列が一致することを確認する。
  - curl による単体検証手順の整備（例: `find_counters` の整形結果確認）。
- 追加作業: 対戦振り返りの検品＋自動保存（[ADR-0017](./ADR-0017.md)）の API 化は
  [ADR-0021](./ADR-0021.md) として切り出した。本 ADR 単独でも採用は成立するが、
  pi 連携で「対戦振り返り」を行うには ADR-0021 の実装が必要になる。
