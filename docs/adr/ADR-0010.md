# ADR-0010: 対戦の振り返りは R2 の Parquet を DuckDB で都度読み、一覧と詳細の 2 ツールに分けて提供する

## ステータス

採用

> 論点を壁打ちで固定し、実装に先立ってツール応答サイズを Parquet から実測して
> 整形不要と確認した。稼働機の `uname -m` が `aarch64` を返すことも確認済み。

## コンテキスト

### 状況 (Situation)

別リポジトリ `pokemon-champions-chapter` が、YouTube にアップロードした対戦動画を
解析し、対戦単位のレコードを Parquet として R2 に置いている
（`s3://pcc-data/index/matches.parquet`）。現時点で 92 行 13KB。動画を追加するたびに
再生成される。

スキーマは以下のとおり。

| カラム | 型 | 内容 |
|---|---|---|
| `matchId` | varchar | `{videoId}_{startSec}` 形式。例 `04UGCh6KtUk_496` |
| `videoId` | varchar | YouTube の動画 ID |
| `startSec` / `endSec` | integer | 動画内での対戦の開始・終了位置。最終戦の `endSec` は NULL |
| `title` | varchar | 「対戦2 vs エルフーン&フラエッテ」 |
| `videoTitle` / `publishedAt` | varchar | 動画のメタ情報 |
| `battleFormat` / `result` / `platform` | varchar | `double` / `win`・`lose` / `mobile` |
| `opponentTeam` | varchar[] | 相手の 6 体 |
| `opponentLead` / `opponentSelection` | varchar[] | 相手の先発 2 体 / 選出 4 体 |
| `selfLead` / `selfSelection` | varchar[] | 自分の先発 2 体 / 選出 4 体 |

`rpi-bridge` 側には、AI がツールを呼びながら回答を組み立てるループが既にある
（最大 30 往復、[ADR-0006](./ADR-0006.md)）。ツールは `tool-definitions.ts` に
定義を並べ、`ai-service.ts` の executor が実行する。パーティの保存・読み出しは
上流 `@nonz250/ai-rotom` のツールが担い、ユーザーごとの名前空間を Pi 側で
付け替えている（[ADR-0009](./ADR-0009.md)）。

### 課題 (Complication)

**解析済みの対戦データが、チャットから参照できない。**

現在このデータを見る手段は `pokemon-champions-chapter` の Web UI だけで
（同リポジトリの ADR-008）、AI バトルコーチとは接続されていない。
「この前の対戦、何が悪かったの」と聞いても、AI はポケモンの一般知識で
答えるしかない。

データを渡すには、3 つの隔たりを埋める必要がある。

**第一に、1 つの動画に複数の対戦が入っている。** 多いもので 8 戦。
利用者が「どの対戦か」を指定する手段がない。`matchId` は安定した一意キーだが、
`04UGCh6KtUk_496` を人が打つことは想定できない。

**第二に、自分のパーティ 6 体が Parquet にない。** あるのは選出 4 体
（`selfSelection`）だけで、控えの 2 体は記録されていない。持ち物・技・努力値も
入っていない。「なぜその 4 体を選んだのか」を論じるには、手元の情報が足りない。

**第三に、行動ログが一切ない。** 技・ダメージ・ターン推移は記録されていない。
「3 ターン目のあの技が悪手だった」という分析は、このデータからは原理的に
組み立てられない。

### 論点 (Question)

1. この機能が返せるものの範囲をどこに引くか
2. Pi から R2 の Parquet をどう読むか
3. 利用者が「どの対戦か」をどう指定するか
4. 欠けている自分のパーティ 6 体をどう補うか
5. R2 に到達できないときどう振る舞うか

### 検討した選択肢 (Options)

#### データ取得経路

- **案A1: Parquet を JSON に変換して R2 に併置し、Pi は fetch して `JSON.parse`**
  - メリット: 新規依存がゼロ。92 行なら全件をメモリに載せられる
  - デメリット: `pokemon-champions-chapter` 側の出力処理に手を入れる必要があり、
    ADR が 1 本増える。データが増えたときに転送量がそのまま効く

- **案A2: Pi に DuckDB を入れて Parquet を読む**
  - メリット: Parquet をそのまま扱える。将来数万行になっても耐える。
    絞り込みと整形を SQL に寄せられる
  - デメリット: Raspberry Pi への依存追加。バイナリは数十 MB 規模

- **案A3: `pokemon-champions-chapter` 側に検索 API を立てて Pi から叩く**
  - メリット: 検索ロジックが解析側に集約される。Pi は薄いまま
  - デメリット: デプロイ対象と障害点が増える。2 リポジトリの結合が強まる

- **案A4: Parquet を取得して Pi の SQLite に取り込む**
  - メリット: 既存の `better-sqlite3` を再利用でき、新規依存がない
  - デメリット: 取り込みバッチと鮮度管理（TTL・再取り込み契機）を設計する必要がある

#### 対戦の指定方法

- **案B1: 一覧 → 選択の 2 段階**
  - 概要: `videoId` で対戦一覧を返し、そこから `matchId` を選んで詳細を取る
  - メリット: 利用者も AI も、実在する対戦の中からしか選べない
  - デメリット: ツール往復が 1 回増える

- **案B2: 「videoId + 何戦目」を直接指定**
  - メリット: 会話が 1 往復短い
  - デメリット: 再解析で検出数が変わると、同じ指定が別の対戦を指す。
    手動補正フロー（`pokemon-champions-chapter` の ADR-011）と衝突する

- **案B3: 相手の顔ぶれで指定**
  - メリット: `videoId` を意識せずに済む
  - デメリット: 同じ相手構築と複数回当たると曖昧になる

#### パーティ情報の結合

- **案C1: 結合しない。AI に別々に呼ばせる**
  - 概要: 新ツールは対戦データだけを返し、パーティは既存のパーティツールで
    AI が別途取得して文脈上で突き合わせる
  - メリット: 名前空間の付け替えが [ADR-0009](./ADR-0009.md) の 1 箇所に留まる
  - デメリット: ツール往復が増える。AI がパーティを取りに行かない可能性がある

- **案C2: 新ツールが `partyName` を受けて内部で合成**
  - メリット: 1 回の呼び出しで「対戦 + 自分の 6 体」が揃う
  - デメリット: 名前空間の付け外しが 2 箇所に増える。
    [ADR-0009](./ADR-0009.md) の「executor のクロージャに閉じ込める」方針と衝突する

## 決定

### 本機能の範囲は選出フェーズの振り返りに限る

返せるのは、相手の構築 6 体と先発 2 体、自分の先発と選出、勝敗、そして動画内の
位置までである。ターン単位の分析は行わない。**この制約はデータの制約であって
実装の手抜きではない**ため、ツールの説明文にも明記し、AI が持っていない情報を
推測で埋めないようにする。

将来 `pokemon-champions-chapter` 側が行動ログを抽出できるようになれば、
そのときに改めて範囲を広げる ADR を書く。

### 案A2 を採り、DuckDB の httpfs で R2 を都度参照する

`@duckdb/node-api` は `linux-arm64` のビルド済みバイナリを配布しており
（v1.5.5 時点）、`better-sqlite3` のようなネイティブコンパイルは発生しない。

**ただし前提は「ハードが 64bit であること」ではなく「OS が 64bit であること」**である。
稼働機は Raspberry Pi 400（Cortex-A72 / メモリ 4GB）で 64bit に対応しているが、
Raspberry Pi OS は長く 32bit 版が既定であったため、64bit ハードに 32bit OS が
載っている構成は珍しくない。`uname -m` が `aarch64` を返すことを実機で確認する。
`armv7l` であれば prebuilt が存在せず、この選択は成立しない。

R2 へは `httpfs` 拡張の S3 互換アクセスで直接到達する。ローカルへ落とす経路
（案A1・案A4）を採らないのは、同期ジョブと鮮度管理という状態を持ちたくないため。
解析側が Parquet を差し替えた瞬間から新しいデータで答えられる。

R2 は path style を要求するため、接続設定は以下になる。

```sql
CREATE SECRET (
  TYPE s3, PROVIDER config,
  KEY_ID '...', SECRET '...',
  ENDPOINT '<account>.r2.cloudflarestorage.com',
  REGION 'auto', URL_STYLE 'path'
);
```

認証情報は `fetch_parquet.sh` が使っている R2 のものをそのまま流用する
（`R2_ENDPOINT_URL` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`）。

起動時にメモリテーブルへ載せる案も検討したが採らない。現行 92 行では性能差が
問題にならず、常に最新である利点のほうが大きい。件数が増えて往復が体感できる
ようになった時点で、キャッシュを入れる判断をする。

### httpfs 拡張はセットアップ手順で導入し、実行時は LOAD だけを行う

DuckDB の拡張は初回に `extensions.duckdb.org` から取得され、以後は
`~/.duckdb/extensions/` に残る。この取得を**サーバー起動時ではなく、Pi の
セットアップ手順に組み込む**。

- セットアップ時（README の「Raspberry Pi 側の準備」に追加）: `INSTALL httpfs;` を
  一度実行する
- 実行時: `LOAD httpfs;` と `CREATE SECRET` を、DuckDB インスタンスの初期化時に
  一度だけ呼ぶ（ツール呼び出しのたびには呼ばない）

起動時に `INSTALL` を呼ばないのは、ネットワークが不調な再起動でサーバー全体の
起動が遅れたり失敗したりする経路を作りたくないため。拡張が入っていなければ
`LOAD` が失敗し、対戦振り返りのツールだけがエラーを返す（後述の障害時の方針と
同じ振る舞いになる）。

なお `LOAD` の失敗はセットアップ漏れを意味するため、エラーメッセージには
`INSTALL httpfs;` の実行を促す文言を含める。

### 案B1 を採り、ツールは一覧と詳細の 2 つに分ける

| ツール | 引数 | 返すもの |
|---|---|---|
| `list_matches` | `video`（videoId または YouTube URL） | その動画の対戦一覧。`matchId` / `title` / `result` / `startSec` / `opponentLead` |
| `get_match` | `matchId` | その対戦の全項目と、動画の該当位置への URL |

利用者はまず YouTube の URL を貼る。**URL から `videoId` を取り出す処理は
ツール側に置く**。`youtu.be/xxx` 形式や `&t=` 付きを AI の抽出任せにすると、
形式によって失敗する余地が残るため。`videoId` をそのまま渡してもよい。

`get_match` の応答には `https://youtu.be/{videoId}?t={startSec}` を含める。
選出の是非まで見たら、あとは人が動画で確かめられるようにする。

### 案C1 を採り、パーティは結合しない

`get_match` はパーティを知らない。自分の 6 体が必要なら、AI が既存の
`list_parties` / `load_party` を呼んで文脈上で突き合わせる。

こうすることで、[ADR-0009](./ADR-0009.md) の名前空間の付け外しは
`createToolExecutor` の 1 箇所に留まる。往復は増えるが、上限 30 回に対して
問題になる量ではない。

AI が自発的にパーティを取りに行かない場合は、まずツールの説明文で誘導し、
それでも足りなければシステムプロンプトで補う。

### ツール結果の整形関数は用意しない

[ADR-0006](./ADR-0006.md) は、ツールを追加したら整形の要否を実測で判断せよと
定めている。実装前に Parquet から応答 JSON を組み立てて測った結果は以下のとおり。

| 応答 | 最大文字数 | `PASSTHROUGH_LIMIT`（5000）比 |
|---|---|---|
| `list_matches`（1 動画 8 戦、最大の動画） | 995 | 20% |
| `get_match`（1 戦） | 432 | 9% |
| （参考）全 92 件を返した場合 | 39,514 | 790% |

いずれも素通しの上限に十分収まるため、`tool-result-formatter.ts` に整形関数を
追加しない。`list_matches` が 5000 文字に達するには 1 動画あたり約 40 戦が必要で、
実際の配信形態では起こらない。

この判断は**動画単位で応答が閉じていること**に依存している。全件を返す形に
変えた瞬間、上限の 8 倍に飛ぶ。

### 横断分析は今回の範囲外とする

「同じ相手構築と過去に当たったときの戦績」は全 92 行を横断すれば容易に出せるが、
今回は入れない。まず 1 戦の振り返りが使われるかを見てから判断する。

上の実測が示すとおり、全件をそのまま返す形は素通しの上限を大きく超える。
横断分析を足すときは `search_matches` のような独立したツールにし、
件数の上限と整形関数を設計に含めること。既存ツールに検索条件を後付けして
応答を膨らませる形は採らない。

### R2 に到達できないときは振り返り機能だけを失う

ツールは例外を投げず、失敗内容を文字列で AI に返す（既存のツール実行と同じ方針）。
AI は一般知識で会話を続けられる。起動時に接続を確認して落とすことはしない。
対戦振り返り以外の機能まで巻き込んで停止させる理由がないため。

## 影響

### メリット

- 「この前の対戦どうだった」から、実際の対戦記録に基づいた会話ができる
- 解析側が Parquet を更新した瞬間から反映される。同期の遅れを説明しなくてよい
- Parquet を直接読むため、`pokemon-champions-chapter` 側に変更が要らない
- 将来データが数万行に増えても、絞り込みを SQL に寄せられる

### デメリット・トレードオフ

- **Parquet のスキーマが暗黙の契約になる**。解析側がカラム名を変えると
  こちら側が黙って壊れる。リポジトリをまたぐため、変更が伝わる仕組みがない
- R2 が落ちる、あるいは認証情報が失効すると、振り返り機能は使えなくなる
- ツール呼び出しのたびに R2 への HTTP 往復が発生する
- Raspberry Pi のディスクとメモリを DuckDB のバイナリ分だけ消費する
- R2 の認証情報を Pi に置くことになる（`.env` の管理対象が増える）
- 案C1 の帰結として、AI がパーティを取りに行かなければ、控え 2 体を欠いたまま
  振り返ることになる

### 今後チームが意識すべきこと

1. **Parquet のスキーマ変更は両リポジトリにまたがる破壊的変更として扱う**。
   `pokemon-champions-chapter` 側でカラムを変える際は、こちらの
   `list_matches` / `get_match` を必ず確認する
2. **応答が動画単位で閉じている前提を崩さない**。整形不要の判断は
   「1 動画あたり最大 8 戦 = 995 文字」という実測に依存している。
   全件や複数動画を横断して返す変更を加えるときは、必ず測り直す
   （[ADR-0006](./ADR-0006.md)）
3. **進捗表示の語彙を追加する**。`tool-progress.ts` の分類と、
   Web UI `app.js` の `L.kids` / `L.junior` に対応する文言を足す
4. **データにないことを AI に語らせない**。ツールの説明文で範囲を明示し、
   ターン単位の分析を求められたら「記録がない」と答えられるようにする
