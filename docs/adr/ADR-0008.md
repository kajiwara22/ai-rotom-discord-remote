# ADR-0008: Web UI の応答は SSE で配信し、まずツール実行の進捗を見せる。Discord は現行の一括送信を維持する

## ステータス

採用

> 実装に先立って論点を固定し、実装を経て TBD だった進捗文言の設計を確定させた。
> 実装中に判明した落とし穴は「決定」と「今後チームが意識すべきこと」に追記している。

## コンテキスト

### 状況 (Situation)

現在、AI の回答は 2 つの経路で届く。

| 経路 | 方式 | 待っている間の表示 |
|---|---|---|
| Web UI | `POST /api/web/ask` の完了を待つ単発 JSON | 経過秒数のカウンタのみ |
| Discord | 3 秒以内に deferred 応答 → 完了後に Webhook で PATCH | Discord 標準の「考え中…」 |

処理はツール呼び出しループを最大 30 回まで回すため、1 回の質問が数十秒から
数分に及ぶ。[ADR-0006](./ADR-0006.md) の整形層で 1 回あたりの往復は軽くなったが、
**呼び出し回数そのものは減っていない**。

### 課題 (Complication)

#### 1. 待っている間、何も分からない

サーバー側は `[ai] ツール実行: get_pokemon_info (loop=3)` というログを持っているが、
これは UI に一切届かない。利用者から見えるのは増えていく秒数だけである。

利用者は小 1 と小 5 を含む。**大人でも無言で 2 分待つのは苦しく、子どもは待てない。**
「ロトムが しらべているよ！」の下に「カバルドンを しらべているよ」と出るだけで、
待ち時間の意味がまるで変わる。

#### 2. 止められない

`app.js` の送信処理に `AbortController` はなく、送信後の取り消し手段がない。
質問を間違えたと気づいても、終わるまで待つしかない。

#### 3. 回答が一気に現れる

長い回答でも、完成するまで 1 文字も表示されない。読み始められるのが最後になる。

### 論点 (Question)

1. 配信方式をどうするか（同期 JSON / SSE / ポーリング）
2. 何を流すか（ツール進捗 / 回答トークン / 両方）
3. Discord をどう扱うか（統一するか、分けるか）
4. 中断をどう扱うか（サーバー側の処理も止めるか）

### 検討した選択肢 (Options)

- **案A: 現状維持**
  - メリット: 実装が不要
  - デメリット: 上記 3 点がそのまま残る

- **案B: SSE でツール実行の進捗だけを流す（回答は完成後に一括）**
  - 概要: `POST /api/web/ask` を SSE に変え、`tool` イベントと最終 `done` イベントを流す
  - メリット:
    - 実装が軽い。`executeToolCallLoop` にコールバックを 1 つ渡すだけで済む
    - **課題 1 を単独で解決する**。効果に対して変更が小さい
    - 上流の API がストリーミングに対応していなくても実現できる
  - デメリット: 回答そのものは一気に現れる（課題 3 は残る）

- **案C: SSE で回答トークンもストリーミングする**
  - 概要: 案B に加え、OpenCode Go API の `stream: true` を使って逐次配信する
  - メリット: 課題 1 と 3 の両方が解決する
  - デメリット:
    - 上流 API のストリーミング対応と、ツール呼び出しとの併用可否を検証していない
    - 逐次到着する Markdown を描画する処理が要る（表やコードブロックが未完成な状態を
      どう描くか）
    - kids モードは 200 文字程度と短く、恩恵が小さい

- **案D: ジョブ ID を返してポーリングする**
  - 概要: 受付時に ID を返し、`GET /api/jobs/:id` を定期取得する
  - メリット: SSE を使えない環境でも動く。実装が素朴
  - デメリット: リクエストが増える。遅延がポーリング間隔に縛られる。
    家庭内 LAN という前提では SSE を避ける理由がない

## 決定

### 案B を採り、まずツール実行の進捗を見せる

`POST /api/web/ask` を SSE 化し、次のイベントを流す。

| イベント | 内容 | UI での表示 |
|---|---|---|
| `tool` | 実行中のツール名と対象 | 「カバルドンを しらべているよ」 |
| `done` | 最終回答とセッション ID | 現行と同じ描画 |
| `error` | エラー内容 | 現行のエラーカード |

**ツール名をそのまま出さない。** サーバーが送るのは種別と対象名だけで、文言は
モード別の語彙テーブル（[ADR-0003](./ADR-0003.md) の `L.kids` / `L.junior`）が組み立てる。

30 ツール分の文言を個別に持つのではなく、**5 種別に丸めた**。ツールを追加しても
分類さえ合っていれば文言の追加が要らず、追加漏れで表示が欠けることもない。

| kind | 対象ツール | kids の例 | junior の例 |
|---|---|---|---|
| `lookup` | `get_*` | 「カバルドン を しらべているよ」 | 「カバルドン のデータを取得中」 |
| `search` | `search_*` | 「〜の なかまを さがしているよ」 | 「〜から候補を検索中」 |
| `calculate` | `calculate_*` | 「〜の つよさを けいさんしているよ」 | 「〜のダメージを計算中」 |
| `analyze` | `analyze_*`, `find_counters`, `compare_parties`, `list_speed_tiers` | 「〜を くらべているよ」 | 「〜の対面を分析中」 |
| `party` | パーティ系 5 ツール | 「パーティを みているよ」 | 「パーティを読み書き中」 |

対象名は引数から 1 つだけ拾う（`name` / `moveName` / `attacker.name` など、よくある
位置を順に見る）。取れなければ対象なしの文言にフォールバックする。

### SSE は `Accept` ヘッダーで切り替える

`Accept: text/event-stream` を含むときだけ SSE を返し、それ以外は従来の JSON を返す。
README に載せている curl での動作確認をそのまま使えるようにするため。

### 案C（トークンのストリーミング）は本 ADR では採らない

上流 API のストリーミング対応とツール呼び出しの併用可否が未検証であり、
案B と同時に進めると切り分けが難しくなるため。案B の SSE 基盤ができていれば、
後から `token` イベントを足す形で追加できる。

### 中断はクライアント側の打ち切りに留める

`AbortController` で SSE を切り、UI 上は停止扱いにする。**サーバー側の処理は止めない。**

ツール呼び出しループの途中で中断すると、DB に未完のツール往復が残る。これは
[ADR-0006](./ADR-0006.md) の履歴トリミングが落とすため実害は出ないが、処理を途中で
殺すよりは完走させて保存するほうが単純である。既に払ったコストも回収できる。

### Discord は現行の一括送信を維持する

Discord の interaction は 3 秒以内の応答が必須で、その後は Webhook で編集する仕組みで
あり、SSE を差し込む余地がない。無理に統一せず、経路ごとに最適な方式を採る。

進捗を見せたい場合は、Webhook の PATCH を複数回行って「調べています…」を先に出す
方法があるが、レート制限とメッセージの散らかりを招くため本 ADR では採らない。

## 影響

### メリット

- 待ち時間に「何が起きているか」が見える。子どもが待てるようになる
- 間違えた質問を取り消せる
- SSE 基盤ができるため、後からトークンのストリーミングを足せる

### デメリット・トレードオフ

- `POST` に対する SSE 応答となり、`EventSource` API は使えない（`fetch` の
  `ReadableStream` を自前で読む必要がある）
- 進捗表示のためにツール名と文言の対応表を保守する必要が生じる。ツールを追加した
  ときに文言を足し忘れると、その間だけ表示が止まって見える
- サーバー側処理を止めないため、中断してもトークンは消費される

### 今後チームが意識すべきこと

1. **ツールを追加したら `tool-progress.ts` の分類を確認する**。5 種別に丸めたため
   通常は追記が不要だが、命名規則から外れるツールは `analyze` に落ちる
2. **進捗イベントに生のツール引数を載せないこと**。UI に出す前提の情報だけを流す
3. Discord と Web で応答経路が違うことを前提に置く。統一しようとしない
4. **切断検知に `req.on("close")` を使わないこと**。POST のボディを読み終えた時点で
   発火済みのため、後から登録しても二度と呼ばれない。`res.on("close")` を使い、
   `res.writableEnded` が false のものだけを本当の切断として扱う
5. **Caddy の `encode` から SSE を除外したままにすること**。圧縮を挟むとイベントが
   バッファに溜まり、進捗が届かなくなる
