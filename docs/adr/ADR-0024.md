# ADR-0024: 相手の選出は「見えた範囲」として扱い、ダブルで 4 体そろわなくても誤りとしない

## ステータス

採用（実装済み）

> [ADR-0018](./ADR-0018.md) の体数マッピングを前提にしたまま、**相手側の選出は
> 観測できた範囲しか記録されない**という例外を明示する。ADR-0018 を覆すものではなく
> 補うもの。ADR-0018 のステータスは「採用」のままにする。
>
> 発端は [ADR-0023](./ADR-0023.md) の実装検証。実データの振り返りで評価役が誤検知し、
> 約 25% の確率で書き直しが走ることを確認した。修正後は同一データ 4 回で 0 件に収まった。

## コンテキスト

### 状況 (Situation)

[ADR-0018](./ADR-0018.md) は、選出・先発の体数表記を `battleFormat` に応じて
出し分けると決めた。シングルは選出 3 体・先発 1 体、ダブルは選出 4 体・先発 2 体で、
未知の値はダブル扱いに fallback する。`get_match` は Parquet の `selfSelection` /
`opponentSelection` をそのまま返し、システムプロンプトとツール description もこの
体数を前提に書かれている。

### 課題 (Complication)

ダブルでは、相手が有利に展開すると**相手の選出が最後まで観測できない**。先発 2 体は
分かるが、3 体目まで見えて 4 体目が不明なまま終わることがある。したがって
`opponentSelection` は「選出の全量」ではなく「観測できた範囲」である。

実データ（`vuqQ2ClrtiU_427`、2026-10-12、ダブル）はこのケースだった。

```json
{"battleFormat": "double",
 "opponentLead": ["オオニューラ", "プテラ"],
 "opponentSelection": ["オオニューラ", "プテラ", "イエッサン(メス)"],
 "selfSelection": ["プテラ", "サーフゴー", "ヒスイウインディ", "リザードン"]}
```

記録として正しい 3 体を、[ADR-0023](./ADR-0023.md) の検品条件 #7（選出とチームの
混同）が「ダブルなのに選出が 3 体。事実の誤り」と判定した。振り返り本文は記録を
書き写しているだけなので、利用者側に落ち度は無い。実測では 4 回中 1 回（約 25%）で
この誤検知が起きた。Discord/Web の `/ask` 経路は不合格を受けて**1 回だけ書き直させ、
再検品せずに保存する**ため、記録に無い 4 体目を作文させる圧力になる。

誤検知の原因は 1 箇所ではない。同じ決め打ちが 3 箇所にあった。

| 箇所 | 記述 |
|---|---|
| `review-harness.ts` の完成条件 | 選出（シングル 3 体／ダブル 4 体）とチーム（6 体）を混同していない |
| `tool-definitions.ts` のシステムプロンプト | 相手の構築 6 体・先発・選出（選出は battleFormat に応じ…） |
| `tool-definitions.ts` の `get_match` description | 選出・先発の体数は battleFormat に応じ、ダブルは選出 4 体 |

`match-repository.ts` は `opponentSelection` が**丸ごと欠けている**場合だけ注記を
足していた。3 体だけある場合は注記が付かず、AI には「4 体そろっているはず」と見える。

### 論点 (Question)

相手の選出がフォーマットの体数に満たないとき、記録・プロンプト・検品でどう扱うか。

### 検討した選択肢 (Options)

- **案 1: 上流のデータを直し、常に 4 体そろえる**
  - 概要: Parquet 側で不足を補完する。
  - メリット: 下流の前提を変えずに済む。
  - デメリット: 観測できていない選出は存在しない情報であり、補完は推測になる。
    記録の正しさを優先する方針（ADR-0010 / ADR-0022 の「記録に無いものを断定しない」）
    と衝突する。

- **案 2: 検品条件 #7 の文言だけを緩める**
  - 概要: 「ダブルでも 3 体以下のことがある」と条件へ追記する。
  - メリット: 変更が 1 行で済む。誤検知は止まる。
  - デメリット: システムプロンプトと `get_match` の説明が「4 体」のまま残り、
    別の振り返りや別のモデルで同じ誤りが再発する。注記が無いので、AI は
    3 体しか無いことを記録の欠落として扱えない。

- **案 3: 「相手の選出は観測範囲」と 3 箇所そろえて扱う**
  - 概要: 完成条件、システムプロンプト、`get_match` の description と `notes` を
    そろえる。`opponentSelection.length < 本来の体数` のときは注記を足す。
  - メリット: 同じ誤りの再発を塞ぐ。AI が「見えていないだけ」と判断でき、記録に無い
    選出を作文しなくなる。
  - デメリット: 変更範囲が広い。注記が増える分、応答サイズが少し増える。

## 決定

**案 3 を採る。** 相手の選出は「見えた範囲」として扱い、フォーマットの体数に満たなくても
誤りとしない。具体的には次の 4 点を変更した。

1. 検品の完成条件 #7 を「選出とチームを混同していない。相手の選出は見えた範囲だけ
   記録されるため、ダブルでも 3 体以下しか載っていないことがある（それを事実の誤りと
   して指摘しない）」に改めた。
2. システムプロンプトの「事実」欄に、相手の選出は見えた範囲だけのことがあり、
   ダブルで 4 体そろわなくても誤りではないと明記した。
3. `get_match` の description に、相手の選出は見えた範囲で、記録に無い選出を推定で
   補わないことを明記した。
4. `match-repository.ts` で `opponentSelection.length < 本来の体数` のとき、
   「相手の選出は見えた範囲のみ（N 体／本来 M 体）」という注記を足すようにした。
   丸ごと欠けている場合の既存注記はそのまま残す。

上流のデータは変更しない。観測できなかった選出は記録に無いままで正しく、補完しない。

## 影響

### メリット

- 評価役の誤検知が消えた。修正前は実データ 4 回中 1 回、同じ本文が
  「事実の誤り」で fail した。修正後は 4 回すべて pass した。
- AI が「相手の選出は 3 体しか見えていない」と認識できる。記録に無い 4 体目を
  作文する圧力が無くなる。
- 3 箇所そろえたので、モデルや経路（Discord/Web/pi）が変わっても同じ前提で動く。

### デメリット・トレードオフ

- `getMatch` の `notes` が 1 行増える。応答サイズへの影響は小さいが、ADR-0006 の
  整形方針に従い、必要なら実測する。
- 検証サンプルは同一データ 4 件と小さい。誤検知率の推定ではない。
- 相手の選出が 2 体（先発のみ）のケースは、丸ごと欠けている場合と区別が付かない。
  現状は「未記録」注記に寄せる。件数が増えたら扱いを再検討する。

### 今後チームが意識すべきこと

1. **記録に無い情報を推定で補わない**（ADR-0010 / ADR-0022 と同じ原則）。相手の選出が
   少ないことは、データの欠落ではなく観測の限界である。
2. **体数の決め打ちを 1 箇所だけ直さない**。ADR-0018 が列挙した 3 箇所
   （`notes` / description / システムプロンプト）を常にそろえて確認する。
3. **ADR-0018 のマッピングは自分の選出には引き続き有効**。相手側にだけ例外が付く。
4. 選出に関する記録を増やすときは、`opponentSelection` が観測範囲であることを
   スキーマの説明に引き継ぐ。
