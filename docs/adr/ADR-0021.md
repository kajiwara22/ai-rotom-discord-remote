# ADR-0021: 対戦振り返りの検品・自動保存はブリッジの検品 API に切り出し、外部の実行役（pi 連携）からも呼べるようにする

## ステータス

検討中

> [ADR-0020](./ADR-0020.md) の採用に伴い、対戦振り返りの検品＋自動保存
> （[ADR-0017](./ADR-0017.md)）を外部から呼べる形にするか否かを別 ADR として切り出した。
> 検品 API の入力契約と、検品不合格時の書き直しの担当は未確定（TBD）。

## コンテキスト

### 状況 (Situation)

[ADR-0017](./ADR-0017.md) が実装した対戦振り返りの検品＋自動保存は、`ai-service.ts` の
`applyReviewHarness()` に実装され、ask パイプライン（`processAiMessages()`）の中でのみ
動く。

- トリガーは「そのターンに `list_matches` / `get_match` を呼んだか」（`isReviewTurn`）
- 処理は 3 段: 機械的検品（`inspectReview`）→ 評価役 LLM（OpenCode Go、不合格なら
  1 回だけ書き直し）→ `match_reviews` へ upsert（`saveMatchReview`）
- 依存するのは「そのターンのメッセージ履歴（ツール呼び出しの並び・引数・結果）」と
  「OpenCode Go API キー」「SQLite（`match_reviews`）」

[ADR-0020](./ADR-0020.md) は「単一ツールの整形＋名前空間込み実行」を API 化した。
しかし検品はターンレベルの処理（回答本文＋ツール呼び出し列の突き合わせ）であり、
単一ツール実行 API の範囲外である。

### 課題 (Complication)

pi 連携（ツールレベル統合）では実行役が pi のモデルになる。pi は
`list_matches` → `get_match` → `load_party` → `analyze_*` と進めて振り返りを書くが、
その経路に ask パイプラインが無いため、**検品も保存も走らない**。

- 検品が無いと、[ADR-0017](./ADR-0017.md) が防ぐ以下の失敗が検知・訂正されない:
  - `load_party` を飛ばして `analyze_*` を呼ぶ（SP=0 混入の数値を断定）
  - 行動ログが無いのにターン・ダメージ推移を語る
  - `list_matches` の `matchAtTimestamp`（t=）と `get_match` の matchId の食い違い
  - 従来作（SV 等）の仕様で語る
- 保存が無いと、`match_reviews` に積まれず、`get_match_review` や「前回の振り返りで
  決めた改善点は？」が pi 連携の振り返りでは機能しない。振り返りが使い捨てになる。
- 役割分離の観点では、pi 連携は「実行役＝pi のモデル、評価役＝ブリッジの deepseek」と
  別システムに分かれるため、[ADR-0017](./ADR-0017.md) の「役割を分ける」趣旨に
  むしろ合致する。

### 論点 (Question)

1. 検品・保存をどこで・どの API として公開するか
2. 検品に必要な入力（ツール呼び出しの並び・引数・結果）を pi からどう集めるか
3. 評価役が不合格としたとき、書き直しを誰が行うか（ブリッジの deepseek か、pi のモデルか）
4. 保存のタイミング（検品通過後か、修正後か）

### 検討した選択肢 (Options)

- **案A: pi 側に検品を再実装（skill / extension での自己レビュー）**
  - 概要: pi の extension や skill で「書いた振り返りを自己レビューさせる」。
  - メリット: ブリッジに変更が不要。
  - デメリット: 評価役が実行役と同じ pi のモデルになり、[ADR-0017](./ADR-0017.md) の
    役割分離が崩れる。`match_reviews`（SQLite）へ到達できず保存が実現しない。
    却下方向。

- **案B: ブリッジに検品 API を新設（採用方向）**
  - 概要: `POST /api/reviews/inspect` を新設し、回答本文＋ツール呼び出しの並びを受け、
    機械的検品 → 評価役 LLM → 必要なら書き直し → `match_reviews` 保存までをブリッジで
    完結させ、指摘・判定・保存有無を返す。
  - メリット: `review-harness.ts` / `match-reviews.ts` の実装を再利用できる。役割分離が
    保てる。保存がブリッジ内で完結する。
  - デメリット: 入力契約の設計が必要。書き直しを誰が担うかの分岐が生じる。評価役 LLM
    のレイテンシ／コストが増える（従来どおり振り返り時のみ）。

- **案C: 対戦振り返りターンだけ `/api/web/ask` に委譲（ハイブリッド）**
  - 概要: pi は振り返り時のみ `/api/web/ask` を呼び、検品込みの回答を得る。PT 構築は
    [ADR-0020](./ADR-0020.md) の直接ツール実行。
  - メリット: 実装最小（既存 API そのまま）。検品・保存とも既存どおり動く。
  - デメリット: 振り返りターンの実行役が deepseek に戻り、「pi のモデルが推論する」と
    いう方針から振り返りだけ外れる。`user_id`／セッションの管理が二重化する。

## 決定（叩き台）

### 案B を採る方向

`POST /api/reviews/inspect` を新設し、検品＋保存をブリッジで完結させる。評価役 LLM は
ブリッジが OpenCode Go で呼び、`buildEvaluatorMessages` / `parseVerdict` /
`buildRevisionMessages` を再利用する。保存は `buildMatchReview` / `saveMatchReview`
を再利用する。

### 入力契約（TBD）

機械的検品（`inspectReview`）が実際に使う情報は次の 3 点＋回答本文に限られる。

- 呼んだツール名の並び（`calledToolNames`）
- `get_match` に渡した matchId（`extractMatchId`）
- `list_matches` 結果に含まれる `matchAtTimestamp`（`extractMatchAtTimestamp`）

したがって入力は最小でも以下の形にできる（候補・要確定）。

```
POST /api/reviews/inspect
body: {
  "reply": "<pi が書いた振り返り本文>",
  "called_tools": ["list_matches", "get_match", "load_party", "analyze_selection"],
  "match_id": "...",            // get_match に渡した matchId
  "match_at_timestamp": "..."   // list_matches 結果の t= が指す対戦
}
response(成功): { "success": true, "issues": [...], "passed": true/false, "saved": true/false }
```

### 書き直しの担当は TBD（論点3）

評価役が不合格としたときの書き直しは、2 案が残っている。

- (i) **ブリッジの deepseek が書き直す**。応答が即座に完成品になり、pi 側のターンを
  増やさない。ただし書き直しの実行役が pi でなくなる。
- (ii) **指摘（issues）だけを返し、pi のモデルが書き直す**。役割分離は保てるが、pi 側で
  追加のターンが発生し、保存のタイミングも「修正後に再度 inspect を呼ぶ」必要がある。

(i) は従来の ask パイプラインの挙動（評価役 → 1 回だけ書き直し → 保存）に最も近い。
(ii) は「実行役＝pi」の思想を保つ。どちらを採るかは pi 連携の実装と合わせて決める。

## 影響

### メリット

- [ADR-0017](./ADR-0017.md) の検品・保存をそのまま再利用でき、pi 連携の振り返りにも
  品質保証と永続化が乗る。
- 実行役（pi）と評価役（ブリッジの deepseek）が別システムに分かれ、役割分離がより
  明確になる。
- 振り返りが使い捨てにならず、`get_match_review` で後から読み戻せる。

### デメリット・トレードオフ

- 入力契約（`called_tools` / `match_id` / `match_at_timestamp`）を pi 側で組み立てる
  必要がある。従来は内部の messages 配列から暗黙に取れていた。
- 書き直しの担当が未確定で、どちらにも「実行役が揺れる」または「ターンが増える」と
  いう代償がある。
- 評価役 LLM により、振り返り質問のレイテンシとトークンが増える（従来どおり振り返り時
  のみ）。

### 今後チームが意識すべきこと

1. **検品は「削る」より「注記」を優先する**（[ADR-0017](./ADR-0017.md) の方針を踏襲）。
2. **評価役 LLM は振り返り時のみ、1 往復に限る**。
3. **保存は検品通過後**。未検証の回答を `match_reviews` の正本にしない。
4. **行動ログは依然として無い**（[ADR-0010](./ADR-0010.md)）。検品 API を経由しても
   「ターン分析を語らせない」制約は変わらない。
