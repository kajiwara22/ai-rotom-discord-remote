# ADR-0025: pi 連携の検品 API に評価役 LLM を常時組み込み、書き直しは pi が担う

## ステータス

採用（実装済み）

> [ADR-0021](./ADR-0021.md) が v1 で保留した「評価役 LLM と書き直し担当（D3）」を
> 決定して実装した。ADR-0021 のステータスは「採用」のままにする（方針は変えず、
> 保留を解消しただけ）。
>
> 実装済み:
> - `POST /api/reviews/inspect` に評価役 LLM を追加（`index.ts` の `handleReviewInspect`）
> - 評価役プロンプトをツール名配列から組み立てる `buildEvaluatorMessagesFromTools`
>   （`review-harness.ts`）
> - 応答に `evaluator` を追加（`ran` / `pass` / `issues` / `model`）
> - pi 側の extension と skill を再生成し、不合格時に書き直して再呼び出しする指示を追加
>
> 未検証（TBD）: pi のエージェントが実際に「書き直して再呼び出し」に従うか。
> API では強制しないため、skill の指示が守られるかは実運用で確認する必要がある。

## コンテキスト

### 状況 (Situation)

[ADR-0021](./ADR-0021.md) は、対戦振り返りの検品と保存をブリッジの
`POST /api/reviews/inspect` に切り出した。入力の捕捉は pi の extension が自動で行い、
モデルは本文（`reply`）だけを渡す。v1 の範囲は**機械検品と保存だけ**で、評価役 LLM は
「後からフラグで追加できる設計」として保留された。

### 課題 (Complication)

pi 経由の振り返りは機械検品しか受けない。`/ask` 経路（Discord / Web）は
`applyReviewHarness` で評価役 LLM を通すため、次の違いが残る。

- [ADR-0023](./ADR-0023.md) で追加した観測制約や出力契約の検品が pi 経路では効かない
- 従来作の仕様で語る、根拠の無い数値を断定する、といった文脈依存の違反を検知できない
- 実データ検証（[ADR-0023](./ADR-0023.md)）でも、pi 経路は `/api/reviews/inspect` を
  呼ぶだけで評価役が走らないことを確認した

ADR-0021 は「評価役を追加する際に、(i) ブリッジの deepseek が書き直す／(ii) issues だけ
返して pi が書き直す、のどちらかを改めて決める」と明記して、この選択を保留していた。

### 論点 (Question)

1. 評価役 LLM を検品 API にどう組み込むか
2. 不合格のとき、書き直しを誰が担うか（ADR-0021 の D3）
3. 評価役を既定で動かすか、明示時だけか

### 検討した選択肢 (Options)

- **案A: ブリッジが書き直して `final_reply` を返す**
  - 概要: `applyReviewHarness` と同じく、評価 → 不合格ならブリッジが 1 回書き直す。
  - メリット: 1 回の呼び出しで完結する。pi 側の変更が不要。`/ask` と同じ振る舞い。
  - デメリット: 書き直しは元回答と指摘しか見られない（ツール結果も会話も無い）。
    pi が選んだモデルの出力を、ブリッジの別モデルが文脈なしで置き換えることになる。

- **案B: 評価役はブリッジ、書き直しは pi（採用）**
  - 概要: 検品 API は判定と指摘だけを返す。pi が文脈とツール結果を使って書き直し、
    もう一度同じ API を呼ぶ。`saveMatchReview` は upsert なので上書きされる。
  - メリット: 役割分離（実行役＝pi、評価役＝ブリッジ）を保ちながら、書き直しの品質が
    高い。ADR-0021 の趣旨に合う。
  - デメリット: pi の skill / extension の更新が要る。pi が指示に従わないと
    未修正のまま保存される。再呼び出しの回数は API では強制できない。

- **案C: 評価のみで書き直しをしない**
  - 概要: 指摘を返すだけで、修正は利用者に委ねる。
  - メリット: 実装が最小。
  - デメリット: 修正されないまま保存され、ADR-0017 の「検品で品質を安定させる」効果を
    得られない。

- **既定動作の候補**
  - 常時 on / body のフラグで opt-in / 環境変数で切り替え

## 決定

**案B を採り、評価役は常時実行する。**

1. `handleReviewInspect` は機械検品のあとに評価役 LLM を 1 回呼び、判定と指摘を
   `evaluator` として返す。書き直しは行わない。
2. 応答は `{ success, issues, evaluator, saved, match_id, final_reply }` とする。
   `evaluator` は `{ ran: true, pass, issues, model }` か `{ ran: false, reason }` で、
   **評価できなかったことと不合格を区別する**。評価不能を不合格に置き換えない。
3. 機械検品の指摘は従来どおり `final_reply` に注記として付ける。保存本文には含めない。
   保存は従来どおり呼ぶたびに行い、pi の再呼び出しで上書きされる。
4. pi 側は extension の `details` に `evaluator` を載せ、skill に
   「`evaluator.pass` が false なら、指摘を反映して書き直し、もう一度呼ぶ（1 回まで）」
   を追記する。
5. 評価役のモデルはブリッジの既定モデル（`getDefaultModelId()`）を使う。検品 API には
   利用者やセッションが無いため、`/ask` のような利用者別モデルは適用しない。

フラグは設けず常時 on とする。振り返りは元々ターンの重い処理であり、評価 1 回分の
レイテンシ（実測 20〜70 秒）を許容する。レイテンシが問題になったら、その時に
`evaluate: false` を足す。

## 影響

### メリット

- pi 経由の振り返りでも、`/ask` と同じ評価役の検品を受けられる。ADR-0023 の観測制約・
  出力契約も pi 経路で効く。
- 書き直しは pi のモデルが会話とツール結果を使って行うため、文脈を失わない。ADR-0021 の
  「実行役＝pi、評価役＝ブリッジ」の役割分離がそのまま成立する。
- 評価不能（`ran: false`）を不合格と区別するので、API キー未設定やタイムアウトで
  振り返りが無駄に書き直されることがない。

### デメリット・トレードオフ

- pi の振り返り 1 回につき評価役 1 回分のレイテンシとトークンが増える。ツール呼び出しが
  数十秒〜分単位になる。
- **再呼び出しは API で強制できない**。pi が指示に従わない場合、`match_reviews` には
  未修正の本文が残る（保存自体は成功する）。skill と extension の description で
  誘導するに留まる。
- 評価役の判定は確率的に揺れる。[ADR-0023](./ADR-0023.md) の検証でも、同じ本文が
  条件によって pass/fail に分かれた。書き直しの往復が増えすぎないよう、skill で
  「1 回まで」としている。

### 今後チームが意識すべきこと

1. **評価不能を不合格にしない**。`ran: false` は API キー未設定・解釈失敗・例外を
   まとめて示す。呼び出し側は `pass` だけを見て書き直しを決めない。
2. **機械検品の指摘と評価役の指摘を混ぜない**。前者は `final_reply` の注記、
   後者は `evaluator.issues` として返る。保存本文には注記も指摘も含めない。
3. **`.pi/` 配下は生成物**。`scripts/generate-pi.ts` を直し、
   `cd rpi-bridge && node --import tsx ../scripts/generate-pi.ts` で再生成する。
   手編集しない。
4. **評価役の呼び出しは 1 回**。`chatCompletion` のタイムアウト（240 秒）がそのまま
   上限になる。書き直しをブリッジで足すと 2 回になり、HTTP の長時間処理として
   見直しが要る。
5. 振り返りの保存は upsert。呼ぶたびに上書きされる前提を崩さない。
