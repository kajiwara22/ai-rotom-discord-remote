# ADR-0028: 構築メモの閲覧は既存 Web UI の `/docs/` に読み取り専用で相乗りさせ、目次は毎回 `docs/` から生成する

## ステータス

採用

## コンテキスト

### 状況 (Situation)

`docs/concepts/` に構築メモと選出ルールが溜まってきた（2026-11 時点で 3 ファイル・約 100KB）。
対戦中に「相手のメガはどれか」「この並びは禁止対面か」を確認したいが、PC を開くのは遅い。
余っている iPhone を横に置いて、数秒で該当節を引きたいという要求がある。

前提として次の環境が既にある。

- `docs/concepts/` は Pi 上のリポジトリで直接編集している
- `rotom.<家庭用ドメイン>` は Caddy が TLS 終端し、rpi-bridge の `public/` を配信している（[ADR-0002](./ADR-0002.md)）
- rpi-bridge はビルド不要で `public/` の静的ファイルをそのまま返す（[ADR-0001](./ADR-0001.md)）

### 課題 (Complication)

1. **Markdown のままでは iPhone で読めない** — 表が横幅に押し込まれて 1 列 2〜3 文字で折り返し、判断に使えない
2. **更新の反映経路を増やしたくない** — ビルドやコピーを挟むと、メモを直したのに古い内容が表示される事故が起きる
3. **正を二重化したくない** — 外部サービスへ貼ると、リポジトリとサービスで内容がずれる
4. **公開範囲を広げたくない** — 構築メモは自分用で、認証を足すほどの秘匿性はないが、インターネットには出したくない

### 論点 (Question)

1. 配信をどこに置くか（既存ホストに相乗り／専用サブドメイン／外部サービス）
2. Markdown をどこで HTML にするか（サーバー／ブラウザ）
3. 目次をどう作るか（固定リスト／都度生成）
4. オフライン対応を入れるか

### 検討した選択肢 (Options)

- **案1: 既存 rotom ホストの `/docs/` に相乗り**
  - 概要: rpi-bridge に読み取り専用の配信ルートを足し、Markdown はブラウザ側の `marked` で描画する
  - メリット: 追加インフラがゼロ（DNS・証明書・Caddy 設定の変更なし）。`docs/` を保存すれば次に開いたとき反映される。既存の HTTPS と `marked.js` をそのまま使える
  - デメリット: rpi-bridge の責務が増える。認証は Web UI 本体と同じく無い

- **案2: 専用サブドメインに静的サイトを立てる（Docsify / MkDocs）**
  - 概要: Caddy の `file_server` で `docs/` を配信し、ナビゲーション付きのテーマを被せる
  - メリット: 責務が分離される。検索やサイドバーが最初から付く
  - デメリット: DNS レコード・Caddy 設定・compose のマウントが増える。Docsify の日本語検索は実質使えない。3 ファイル・100KB に対して設定の割が合わない

- **案3: PI Web（`pi.<家庭用ドメイン>`）で開く**
  - 概要: 既に動いている開発用 UI でファイルを閲覧する
  - メリット: 追加実装がゼロ
  - デメリット: 開発用 UI で、対戦中に「パッと読む」用途には重い。目次も無い

- **案4: 外部サービス（Notion / GitHub / Obsidian + iCloud）**
  - 概要: ドキュメントを外部へ置き、モバイルアプリで読む
  - メリット: モバイル UI は最も良い
  - デメリット: リポジトリと外部で正が二重化する。更新のたびに手作業か push が要る

## 決定 (Answer)

**案1 を採用する。** 具体的には次のとおり。

1. `GET /docs/` を rpi-bridge に追加し、`docs/` 配下の Markdown を**読み取り専用**で配信する。書き込み API は作らない
2. Markdown は `text/markdown` のまま返し、描画はブラウザ側の `marked` に任せる。サーバーにビルドもテンプレートも持たせない
3. 目次はリクエストのたびに `docs/concepts/` と `docs/adr/` を走査して生成する。見出し ID は h2 の出現順 `s1`, `s2`, ... とし、本文描画時の付番と一致させる
4. パスは `resolve` したうえで `docs/` の前方一致で検証し、外に出る要求は 403 とする
5. `manifest.webmanifest` と `apple-touch-icon` を置き、Safari の「ホーム画面に追加」で起動できるようにする
6. **Service Worker は入れない。** 前提が家庭内 LAN であり、オフライン要件が無いため

## 影響

### 良い影響

- `docs/` を保存するだけで目次と本文に反映される。ビルド・コピー・再起動が不要
- 対戦中はホーム画面アイコン → 目次 → 「すぐ見る」の直リンクで 2 タップで該当節に着く
- 追加インフラが無く、既存の HTTPS・証明書・DNS の運用に手を入れない
- ファイルを足せば目次に出るため、`docs/concepts/` を増やすときに一覧の更新を忘れない

### 悪い影響・制約

- rpi-bridge が「Web UI」と「ドキュメント閲覧」の 2 つの役割を持つ。大きくなったら案2 へ切り出せるよう、配信は `docs-site.ts` に閉じてある
- 認証は無い。家庭内 LAN 前提であり、`rotom.<家庭用ドメイン>` をインターネットへ公開する場合は前段の認証が別途必要（[ADR-0002](./ADR-0002.md) と同じ前提）
- Markdown 内の見出しアンカー（`#見出し`）は `s1` 形式へ読み替えるため、外部から貼られた元のアンカーは引き継がない
- オフラインでは開けない。必要になった時点で Service Worker を足す（この ADR を差し替える）
