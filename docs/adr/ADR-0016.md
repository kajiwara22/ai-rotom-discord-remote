# ADR-0016: 回答の帰属はモデル名をメッセージ単位で保存し、Web UI の junior モードにのみ表示する

## ステータス

採用

> 壁打ちの結果、専用の比較 UI は作らず「手動で切り替えて Web UI で見比べる」運用とし、
> **回答のモデル名が見えれば充足する**という結論に落ち着いた。本 ADR はその
> 「帰属（どのモデルが回答したか）」の記録と表示のみを扱う。実装済み（`messages.model`
> 列、応答の `data.model` の記録、`WebAskResponse` / 履歴 API への `model`、junior のみ
> の表示）。

## コンテキスト

### 状況 (Situation)

[ADR-0015](./ADR-0015.md) により、LLM モデルは実行時に切り替え可能になり、Web は
利用者別・Discord は全体既定でモデルが解決される。切り替えの効果（応答の文体・深さ・
速度）は、実際に使って比べることでしか判断できない。

現状、OpenCode Go の応答には `model` フィールド（実際に使われたモデルをエコー）が
含まれるが、`ai-service.ts` はこれを**読み捨てている**。DB の `messages` にモデルは
保存されず、Web UI / Discord にも表示されない。モデルが deepseek 固定だった頃は
これで問題なかった。

### 課題 (Complication)

**第一に、切り替えを始めると「どの回答がどのモデルか」が分からなくなる。** 利用者
（父）は、モデルを切り替えて同じ質問を投げ直し、履歴を見比べる運用を想定している。
このとき回答にモデル名が付いていないと、見比べようがない。

**第二に、フォールバックの誤帰属に注意が要る。** [ADR-0015](./ADR-0015.md) では、
選択モデルが API エラーを返した場合に既定モデルへ自動フォールバックする。このとき
「選択したモデル名」を記録すると、実際には既定モデルが生成した回答に別のモデル名が
付いてしまい、比較を誤らせる。

**第三に、モデル名は技術的な情報である。** 表示モードは `kids` / `junior` の 2 段階で
（[ADR-0003](./ADR-0003.md)）、`kids` はひらがな中心のため、モデル ID
（`deepseek-v4-pro` 等）はノイズになる。利用者は父と小学生の娘 2 人であり、モデルを
選ぶのは父（junior 側）である。

### 論点 (Question)

1. 帰属をどの層に記録するか（ログ / DB / API / UI）
2. 誰に表示するか（kids / junior / 非表示）
3. 専用の比較 UI を作るか

### 検討した選択肢 (Options)

#### 記録の層

- **案1: DB の `messages` に保存し、API 経由で UI に出す（採用）**
  - 概要: `messages` に `model` 列を追加し、assistant メッセージに実際のモデル ID を
    保存。`WebAskResponse` と履歴 API に載せ、UI が描画する。
  - メリット: 過去ログを開き直してもモデル名が残る。比較の土台として後から何にでも
    使える（メトリクス集計など）。
  - デメリット: マイグレーションと保存処理の変更が要る。
- **案2: ログに出すだけ**
  - メリット: 最小。
  - デメリット: 利用者本人には見えない。履歴を開き直して見比べるという運用を満たせない。

#### 表示の対象

- **案A: junior のみ表示（採用）**
  - 概要: `currentUser.mode === "junior"` のときだけ assistant メッセージにモデル名を
    小さく表示する。kids では隠す。
  - メリット: モデルを選ぶのは父（junior）であり、kids の画面を汚さない。
  - デメリット: kids では見えない（ただし kids ユーザーがモデルを選ぶことはない）。
- **案B: 常に表示**
  - デメリット: ひらがな中心の kids 画面にモデル ID が混ざる。
- **案C: チャットでは非表示（親向けの別ビュー）**
  - デメリット: 別ビューを作るコスト。手動で見比べる運用には大げさ。

#### 比較 UI

- **案ⅰ: 作らない（採用）**
  - 概要: 手動で切り替えて同じ質問を投げ直し、履歴のモデル名表示で見比べる。
  - メリット: 実装が帰属だけで済む。比較は非決定性（同じモデルでも回答がブレる）の
    影響を受けるため、専用 UI を作っても「1 回のスナップショット」にしかならない。
  - デメリット: 並べて見られず、見比べは利用者の記憶頼み。
- **案ⅱ: A/B 比較 UI を作る**
  - 概要: 2〜3 モデルを選び、同じ質問を投げて並べる。
  - デメリット: リクエスト単位のモデル指定（ADR-0015 の解決順序の例外）が要り、
    コストも倍増する。必要になるまで作らない。

## 決定

### 帰属は `messages` にモデル名をメッセージ単位で保存する（案1）

`messages` テーブルに `model` 列（nullable）を追加し、assistant メッセージに
**実際に生成したモデル ID** を保存する。記録する値は、リクエストで送ったモデル名
ではなく、**応答の `data.model`（ゲートウェイがエコーする実モデル）を正とする**。
これにより、フォールバックで既定モデルに落ちた回答は既定モデルとして記録され、
誤帰属が起きない。リクエスト値で記録すると、フォールバック時に「選んだのに効いて
いない」回答が別モデルのラベル付きで残り、比較を誤らせる。

### `WebAskResponse` と履歴 API に `model` を載せる

新規応答（`toWebAskResponse`）と、過去ログを開き直す履歴 API
（`GET /api/sessions/:id`）の両方にモデル名を含める。履歴 API は保存された
`messages.model` をそのまま返す。これにより、直後の回答にも、後から開いた履歴にも
モデル名が表示される。

### Web UI は junior モードのみ、assistant メッセージにモデル名を小さく表示する（案A）

`appendMessage` で `role === "assistant"` かつ `currentUser.mode === "junior"` のとき、
`.who` の横（またはバブル末尾）にモデル ID を小さく表示する。kids では表示しない。
Discord には表示しない（Discord は全体既定の 1 モデルで動き、表示しても比較の
材料にならない。必要になれば別途検討する）。

### 専用の比較 UI は作らない（案ⅰ）

利用者は手動でモデルを切り替え、同じ質問を投げ直し、履歴のモデル名表示で見比べる。
この運用で充足する。A/B 比較 UI・並列実行・レイテンシ／トークンの並記はすべて
今回のスコープ外とし、必要になったときに改めて ADR を書く。

## 影響

### メリット

- 切り替えの効果を履歴で見返せる。どの回答がどのモデルかを確実に区別できる。
- フォールバック時の誤帰属を防げる（実モデルで記録するため）。
- 実装が小さい（カラム追加＋保存＋API＋junior 表示）。比較 UI のような新規画面は要らない。
- モデル名を保存しておけば、将来メトリクス集計（レイテンシ・トークン・コスト）へ
  拡張する土台になる。

### デメリット・トレードオフ

- junior のメッセージにモデル ID という情報が増える（小さく表示し、邪魔にしない）。
- 手動比較は非決定性の影響を受ける。同じモデルでも回答はブレるため、見比べは
  「どちらが好みか」の判断であり、厳密な優劣ではない。
- kids ではモデル名が見えない（モデルを選ぶのは父＝junior なので実害はない）。
- 切り替え前の既存メッセージにはモデル名が無い（`model` 列は nullable で、過去分は
  null のまま。表示時に null ならラベルを出さない）。

### 今後チームが意識すべきこと

1. **記録は実モデル（応答の `data.model`）で行う**。フォールバックを挟んでも誤帰属に
   しない。リクエスト値で書かない。
2. **kids にはモデル名を出さない**。表示条件は `currentUser.mode === "junior"`。
3. **履歴 API にも `model` を載せる**。直後の応答だけに付けて履歴に付け忘れると、
   開き直したときだけモデル名が消える。
4. **語彙テーブル（`L.kids` / `L.junior`）**。モデル名そのものは ID をそのまま出すが、
   必要ならラベル用のキーを追加する。kids では表示しないため、junior 側の語彙のみで
   足りる（追加するなら両方に定義する）。
5. **比較はスナップショット**。同じ質問でもツール結果や生成が揺れるため、
   「このモデルが正しい」ではなく「このモデルの出し方が好み」という見方をする。
