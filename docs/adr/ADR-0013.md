# ADR-0013: 育成論（ポケ徹）の取り込みは bridge 側の専用ツールとし、取得は r.jina.ai リーダー、保存は SQLite の専用テーブルで行う

## ステータス

採用

## コンテキスト

### 状況 (Situation)

ポケモン徹底攻略（yakkun.com）の「ポケモンチャンピオンズ育成論」を、チャット（Discord / Web UI）から取り込める「口」を作りたい。対象例は `https://yakkun.com/ch/theory/n413`（ヒスイダイケンキの育成論）。

既存の構成は次のとおりで、MCP に存在しないツールは bridge 側で直接処理するパターンが既にある（対戦記録 `list_matches` / `get_match` は MCP を経由せず `match-repository.ts` が R2 を読む。ADR-0010）。

- `worker`（Cloudflare）→ `rpi-bridge`（Pi / Node+tsx）→ `@nonz250/ai-rotom` MCP
- ツールは `rpi-bridge/src/tool-definitions.ts` の `TOOL_DEFINITIONS` で LLM に公開
- `index.ts` の `handleToolCall` が MCP 呼び出しと bridge 内処理（`isMatchTool`）を分岐

育成論 1 ページの構造は実測で次のようになっている（n413 の場合）。

| フィールド | 値（例） | HTML 上の位置 |
|---|---|---|
| ポケモン | ダイケンキ(ヒスイ) | タイトル / パンくず `/ch/theory/p503h` |
| タイトル | 【漢は倒れねえ！】漢気ヒスイダイケンキ！！ | `<h2>` |
| 性格 | いじっぱり | `<dl><dt>性格</dt><dd>` |
| 特性 | きれあじ | `<dt>特性</dt><dd>` |
| 持ち物 | くろいメガネ | `<dt>持ち物</dt><dd>` |
| 能力ポイント(SP) | HP:18 / 攻撃:17 / 防御:18 / 特防:9 / 素早:2 | `<dt>能力ポイント(努力値配分)</dt><dd>` |
| 覚えさせる技 | ひけん・ちえなみ / ふいうち / つるぎのまい / せいなるつるぎ | `<dd class="move_dd">` 内の `<div class="name">` |
| ルール | シングルバトル | `<dt>ルール</dt><dd>` |
| 役割 | 物理サポート | `<dt>このポケモンの役割</dt><dd>` |
| 考察本文 | 調整意図・与/被ダメ計・立ち回り・苦手対面（実測 約 4〜7KB） | `<div id="consideration">` 内の `<div itemprop="articleBody">` |

このうち「性格・特性・持ち物・SP・技」は、既存の `save_party` のメンバー形式（name / nature / ability / item / evs / moves）とほぼ 1:1 に対応する。SP の表記（HP:18 / 攻撃:17 …）も `evs`（hp / atk / def / spa / spd / spe）に機械的に変換できる。

### 課題 (Complication)

1. **直接取得できない**。yakkun.com は Cloudflare の「Just a moment...」チャレンジで保護されており、素の `fetch` / `curl` は HTTP 403 を返す（実測）。
2. **育成論の価値は考察本文にある**。構造化ヘッダだけ取り込んでも、調整意図・与/被ダメ計・立ち回り・苦手対面という「著者の思考」が失われる。この本文は約 4〜7KB あり、`save_party` の `memo`（最大 4000 文字）には収まりきらない。
3. **「他人の構築」と「自分のパーティ」は意味が違う**。育成論を `save_party` に 1 体パーティとして混ぜると、`list_parties` / `load_party`（ADR-0009 の名前空間で利用者ごとに分離している「自分の棚」）が外部の型で汚れる。

### 論点 (Question)

- 取得方法をどうするか（Cloudflare チャレンジをどう越えるか）。
- 取り込んだ育成論をどこに保存し、どう参照させるか。

### 検討した選択肢 (Options)

#### 取得方法

- **案1: r.jina.ai リーダーを使う**
  - `https://r.jina.ai/https://yakkun.com/ch/theory/n413` に `x-respond-with: html` ヘッダを付けると、Cloudflare を通過した HTML（UTF-8 へ変換済み）が返る（実測 200 / 約 119KB）。デフォルトでは Markdown も返る。
  - メリット: 実装が最小（`fetch` 1 回）。Pi に重い依存を足さない。今すぐ動く。
  - デメリット: 外部サービス依存（無料枠はレート制限あり、SLA なし）。将来サービス終了・挙動変更のリスク。
- **案2: Playwright ヘッドレスブラウザで取得する**
  - 実ブラウザが Cloudflare チャレンジをその場で解く。最も頑健・自己完結。
  - メリット: 外部サービスに依存しない。構造化 HTML を確実に取れる。
  - デメリット: Pi に Chromium 未導入（`~/.cache/ms-playwright` なし、`playwright` 未インストール）。導入・常駐コストが大きく、初回取得に数秒〜十数秒かかる。
- **案3: 直接 fetch する**
  - Cloudflare チャレンジにより不可（403）。ボツ。

#### 保存・参照方法

- **案A: 専用 SQLite テーブル（bridge 内）に保存する**
  - 新テーブル `theory_refs`（url, pokemon, title, nature, ability, item, evs, moves, rule, role, body_text, created_at）を `db.ts` に追加。取り込みツールが fetch→parse→保存し、`get_theory` / `list_theories` で参照する。
  - メリット: 考察本文を全文保持できる。パーティ棚と混ざらない。ADR-0010（match-repository）と同型で bridge に閉じる。
  - デメリット: マイグレーション＋参照ツールの実装が増える。
- **案B: `save_party` に 1 体として保存する**
  - 構造化ヘッダを 1 体メンバーに、考察本文を `memo`（4000 字で打ち切り）に詰める。
  - メリット: 既存の `load_party` / `analyze_*` がそのまま使える。実装が最小。
  - デメリット: 本文が欠ける。自分のパーティ棚が汚れる。名前空間（ADR-0009）の取り回しが必要。
- **案C: 保存せず、その場で構造化データを返すだけ**
  - 「取り込み」ではなく「閲覧」になるため、要件（取り込み）を満たさない。ボツ。

## 決定

- **取得は r.jina.ai リーダー（`x-respond-with: html`）を主とし、失敗時は Playwright ヘッドレスへフォールバックする**。単発・低頻度の取り込みであり、jina の無料枠で足りる。Playwright は「jina が落ちた / レート制限に当たった場合の代替」として実装するが、**Pi には未導入**（`npm i playwright && npx playwright install --with-deps chromium` が必要）。
- **保存は bridge の SQLite に専用テーブル `theory_refs` を新設して行う**。キーは URL（同じ育成論は同じ内容のため、利用者ごとの分離は不要）。`import_theory_from_url` / `get_theory` の 2 ツールを bridge 側に追加する（ADR-0010 と同型）。
- **解析はベストエフォート**。取れなかったフィールドは null にし、**考察本文（articleBody）は必ず全文を DB に保存**する。これにより「全ページが同じ構造とは限らない」懸念に対して、構造が取れなくても本文は失わない形にする。
- **構造化ヘッダ（性格・特性・持ち物・SP・技）は取り込み時に解析し、ツール結果として AI へ返す**。これにより AI は「この型で analyze_matchup して」「うちのパーティと compare して」を既存ツールにそのまま渡せる。`save_party` への自動保存はしない（必要なときは AI が明示的に呼ぶ）。
- **対象は単一 URL**（個別ページ `nNNN`）。ポケモン別一覧（`pNNN`）からの複数取り込みは今回のスコープ外。
- **入口はチャット**（Discord / Web UI とも「URL を取り込んで」と話しかける）。専用の UI ボタンは設けない。
- 取り込みの再利用頻度が高くないことを踏まえ、`list_theories`（一覧）は設けない。URL をキーにしたキャッシュ＋再取得（`get_theory`）だけに留める。

## 影響

### メリット

- 育成論の全文（考察）を失わずに取り込め、AI が著者の調整意図・ダメ計・立ち回りを引用して回答できる。
- 自分のパーティ棚（ADR-0009）を汚さず、保存済みパーティと外部育成論を明確に区別できる。
- 取得・保存・整形がすべて bridge 内に閉じ、MCP（`@nonz250/ai-rotom`）を変更する必要がない。

### デメリット・トレードオフ

- r.jina.ai という外部サービスへの依存が生まれる（レート制限・SLA なし・挙動変更リスク）。対策としてタイムアウト（既存 `AbortSignal.timeout` の慣例に合わせる）と、失敗時に「取得できませんでした」を AI へ返す経路を設ける。
- 新テーブル＋マイグレーション＋参照ツールの実装が必要。

### 今後チームが意識すべきこと

- **yakkun.com は直接 fetch してはならない**（403）。取得は必ず r.jina.ai（または将来の Playwright）経由。
- **考察本文は巨大になりうる**ため、`get_theory` の応答は ADR-0006 の整形層（`tool-result-formatter.ts`）で「調整意図・与/被ダメ計・苦手対面」を判断に効く順へ整形してから LLM に渡す。先頭からの一律切り詰めは入れない。
- **URL のフラグメント（`#持ち物`）は取り込み時に落とす**。`t=` のような識別子はないため、URL 正規化は「フラグメント除去」のみでよい。
- 取り込んだ型をパーティ分析に使わせる場合、SP 表記を `evs`（hp/atk/def/spa/spd/spe）へ変換する対応表（攻撃→atk、防御→def、特攻→spa、特防→spd、素早→spe、HP→hp）を `theory-import.ts` に一元化する。
- 育成論には投稿者による SP 配分ミスがありうる（n413 は合計 64 で 66 未満）。**数値は投稿されたまま取り込み、正規化や補正はしない**（AI に「合計 66 に満たない」ことを指摘させる材料として残す）。

### 関連する ADR・追加作業

- ADR-0006（ツール結果の整形）: `import_theory_from_url` / `get_theory` の整形関数（考察本文を 4800 字で区切り、構造化ヘッダは切らない）を追加済み。
- ADR-0009（パーティ名前空間）: 今回は save_party を使わないため関与しないが、将来「取り込んだ型を save_party に保存」を足す場合は名前空間を通すこと。
- ADR-0010（match-repository）: bridge 内ツールの実装パターンとして踏襲済み。
- 実装済み: `theory_refs` テーブル（db.ts）、`theory-import.ts`（fetch/parse/save/get）、`tool-definitions.ts` への 2 ツール追加、`index.ts` への分岐、`tool-result-formatter.ts` への整形追加、`tool-progress.ts` / `app.js` への進捗語彙（theory）追加。
