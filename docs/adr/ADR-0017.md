# ADR-0017: 対戦の振り返りは「完成品の形・検品・記録」をハーネスとして固定し、回答品質を安定させる

## ステータス

採用

> 「ハーネス理論（AI の実用力 = モデル能力 × ハーネスの質 × 検品の質）」を対戦の
> 振り返りへ適用した。8 部品のうち「道具（ツール）」「地図（正しい情報源）」は既に
> [ADR-0006](./ADR-0006.md) / [ADR-0010](./ADR-0010.md) / [ADR-0012](./ADR-0012.md) が
> 実装しており、本 ADR は残る「ゴール」「役割」「検品」「記録」を実装した。
> 発端となった外部資料: https://x.com/MakeAI_CEO/status/2093264660082597994
>
> 実装済み:
> - 完成品の形をシステムプロンプトへ追加（`tool-definitions.ts`）
> - 機械的検品 + 評価役 LLM の 2 段検品（`review-harness.ts` / `ai-service.ts`）
> - `match_reviews` テーブル + `get_match_review` ツール（`match-reviews.ts` / `db.ts`）
> - 役割は実行役 + 評価役の 2 役（計画役は置かない）
>
> 未実装（TBD）: 機械的検品の「ポケモン名のハルシネーション検出」（固有名詞辞書の
> 整備が要るため。文脈に依存する違反は評価役 LLM が代わりに検知する）

## コンテキスト

### 状況 (Situation)

対戦の振り返りは、[ADR-0010](./ADR-0010.md) の `list_matches` / `get_match` と
[ADR-0012](./ADR-0012.md) の `selfPartySlug` / `selfTeam` 埋め込みによって動くように
なった。流れはシステムプロンプト（`tool-definitions.ts` の「対戦振り返りの手順」）に
固定されている。

1. `list_matches`（URL の `t=` を保持）で振り返る matchId を決める
2. `get_match` で自分の party / team / 先発 / 選出と、相手の構築・先発・選出・勝敗を確認
3. `load_party` で自分の持ち物・技・性格・SP を取得
4. `analyze_selection` / `analyze_matchup` などで分析

ツール出力の整形は [ADR-0006](./ADR-0006.md) の `tool-result-formatter.ts` が担い、
`get_match` の `notes` が次の一手（`load_party` を先に、team(6 体) を使え、等）を誘導
する。**「道具（ツール）」と「地図（正しい情報源）」は既にハーネスとして機能して
いる**。

一方で、この振り返りは「1 モデルが手順をなぞって回答を 1 回書いたら終わり」であり、
**回答そのものの品質検証はどこにもない**。モデルが「できました」と言った回答を、
そのまま Discord / Web に返している。ツール出力は整形層で検品されるが、その先で
モデルが組み立てる回答は野放しである。

### 課題 (Complication)

**第一に、最終回答の検品がない。** 以下の失敗はすべてプロンプトの「〜してはいけない」
に頼っており、実際に起こると検知も訂正もされない。

- `get_match` / `load_party` に存在しないポケモン・パーティ名を書く（ハルシネーション）
- `load_party` を飛ばして名前だけを `analyze_selection` 等へ渡し、SP=0・持ち物なしで
  計算した数値を実戦の結論として書く
- 行動ログが記録されていない（[ADR-0010](./ADR-0010.md)）のに、ターン・技・ダメージの
  推移を語る
- `list_matches` が `matchAtTimestamp` で指した対戦と、回答が振り返っている対戦が食い違う

**第二に、振り返りの結論が消える。** セッションはチャンネル単位で TTL 30 分・最大
20 メッセージ（`conversation-manager.ts`）。「前回の振り返りで決めた改善点は？」と
聞かれても、セッションが失効していれば答えられない。Web は 30 日と長いが、
「あの対戦の振り返り」を matchId 単位で引き出す仕組みはない。

**第三に、完成品の形が未定義である。** システムプロンプトは「簡潔に回答する」としか
言っておらず、振り返りとして何を残せば成功なのかが決まっていない。同じ質問でも
回答の粒度・観点がブレ、「振り返った気になるが、次に活かせる結論がない」ことがある。

### 論点 (Question)

1. 振り返りの完成品の形（観点と順序）を固定するか。固定するならどこに置くか
2. 最終回答の検品を、どの層で・どう実装するか
3. 振り返りの結論を matchId 単位で永続化するか。読み戻しはどうするか
4. 「役割を分ける」をどこまでやるか（計画役・実行役・評価役のうち何役を置くか）

### 検討した選択肢 (Options)

#### 論点1: 完成品の形

- **案A: システムプロンプトに固定の構成を置く（採用案）**
  - 概要: 「対戦振り返りの手順」の下に、振り返り回答の標準構成（後述）を置く。
  - メリット: 追加インフラ不要。既存のプロンプト構成に乗る。
  - デメリット: プロンプトが長くなる（「地図は目次」の原則に反しないよう短く保つ）。
- **案B: スキル／別ファイル化**
  - 概要: 手順を別ファイルへ切り出し、必要なときだけ読む。
  - メリット: プロンプトを圧迫しない。
  - デメリット: 本システムにはスキルローダーがなく、新設コストが大きい。見送り。

#### 論点2: 検品の実装

- **案A: 機械的検品のみ（フック）**
  - 概要: 回答を返す前に、ツール呼び出し履歴と回答本文を突き合わせる軽量チェック。
  - メリット: レイテンシ・コスト増なし。検知できる違反は決定的に検知できる。
  - デメリット: 「書くべき観点が抜けている」等の質は測れない。
- **案B: 評価役 LLM のみ**
  - 概要: 回答の後に 1 回だけ、完成条件リストで採点する LLM を呼ぶ。
  - メリット: 質・観点抜けまで検知できる。
  - デメリット: レイテンシとコストがほぼ倍。検知が非決定的。
- **案C: 機械的検品 + 評価役 LLM の 2 段（採用案）**
  - 概要: まず機械的検品で確実な違反（名無し・SP=0 混入・ターン分析・t= 食い違い）を
    検知し、その上で評価役 LLM が完成条件で採点する。基準未満なら 1 回だけ書き直す。
  - メリット: 確実な違反は決定的に、質は LLM で検知。役割分離（実行役/評価役）を満たす。
  - デメリット: 実装が最も大きい。評価役は振り返り時のみ起動して影響を抑える。

#### 論点3: 記録の永続化

- **案A: `match_reviews` テーブル新設 + `get_match_review` ツール（採用案）**
  - 概要: matchId をキーに振り返りの要点・改善候補・次の一手を upsert し、
    `get_match_review(matchId)` で読み戻す。
  - メリット: セッション失効後も「あの対戦の振り返り」を引き出せる。[ADR-0013](./ADR-0013.md)
    の `theory_refs` と同じ DB パターンで実装できる。
  - デメリット: テーブル・保存・読み戻しツールの追加。応答サイズは要実測（ADR-0006）。
- **案B: `messages` に流すだけ**
  - メリット: 実装最小。
  - デメリット: セッションと運命を共にし、30 分 / 20 メッセージで消える。論点3 の
    「結論が消える」を解決しない。
- **案C: 永続化しない**
  - デメリット: 同上。振り返りが使い捨てになる。

#### 論点4: 役割の分割

- **案A: 実行役 + 評価役の 2 役（採用案）**
  - 概要: 既存ループを実行役、検品（論点2）を評価役とみなす。計画役は置かない。
  - メリット: 振り返りの手順は固定されており、計画役のコストに見合う不確実性がない。
    「最初は 2〜3 役」の最小構成。
  - デメリット: 計画の自由度はない（現状もプロンプトで固定しているため実害なし）。
- **案B: 計画・実行・評価の 3 役**
  - デメリット: 単発の Q&A である本システムでは過剰。レイテンシ増。

## 決定（案）

以下は叩き台であり、各項目は独立に議論・差し替え可能。

### 1. 振り返りの完成品の形を固定する（論点1 案A）

システムプロンプトに、振り返り回答の標準構成を置く。**事実と解釈を分ける**ことを
原則とし、数値の根拠（どのツールで得たか）を明示させる。振り返り（list_matches /
get_match を含むターン）に限って適用し、単発の質問にまで全見出しを強制しない。

（構成案・要調整）

```
## この対戦について
- 動画 / 対戦 / 勝敗 / 再生位置（t=）
## 事実（記録に基づく）
- 自分のパーティ（party 名・6 体）
- 自分の先発・選出（選出は battleFormat に応じ、シングル 3 体／ダブル 4 体）/ 相手の構築 6 体・先発・選出
## 選出の振り返り
- 先発・選出の良し悪しと根拠（相性・素早さ・ダメ計はツール結果に基づく）
## 構築相性
- 有利・不利な対面（analyze_selection 等）
## 改善候補
- 次に試す選出・対策（find_counters 等）
## 次の一手
- 実践で試す具体的な 1 手
```

kids モード（[ADR-0003](./ADR-0003.md)）では語彙テーブルに従い、構成の見出しも
ひらがな中心へ変換する。構成そのものは共通。

### 2. 検品は「機械的検品 → 評価役 LLM」の 2 段とする（論点2 案C）

- **機械的検品（フック）**: 回答を返す前に、そのターンのツール呼び出し履歴
  （`resultMessages` の role:"tool"）と回答本文を突き合わせ、以下を検知する。
  - 分析系ツール（`analyze_*` など）を呼んだのに `load_party` を呼んでいない（SP=0 混入の疑い）
  - 行動ログがないのにターン推移を語る表現（「ターン目」等）の検出
  - `matchAtTimestamp` が指す対戦と、回答が扱う対戦の食い違い
  検知時は該当箇所を削るか注記する。**会話は止めない**（[ADR-0011](./ADR-0011.md) の
  「抽出失敗時は本文をいじらず表示」と同じ方針）。
  「ツール結果に存在しないポケモン名（ハルシネーション候補）」は固有名詞辞書が要る
  ため TBD とし、現時点では実装しない。
- **評価役 LLM**: 振り返り（list_matches / get_match を含むターン）のときだけ、
  回答 + 完成条件リストを渡して 1 回採点する。基準未満なら 1 回だけ書き直させる。
  評価役は tools を渡さず、Discord の 12 分締切（`DEADLINE_MARGIN_MS`）を侵さないよう
  1 往復に限る。

### 3. 振り返りの結論を `match_reviews` に永続化する（論点3 案A）

`match_reviews`（match_id 主キー）へ、検品を通った振り返りを upsert する。読み戻しは
`get_match_review(matchId)` ツールで行い、`get_match` の応答は膨らませない（ADR-0006 の
サイズ維持）。保存するのは原文（review_text）と、見出しからベストエフォートで抜き出す
改善候補・次の一手。読み戻しツールの本文は整形層で上限（4800 字）に切り、DB には全文
を残す（ADR-0006 / ADR-0013 の `theory_refs` と同型）。

### 4. 役割は実行役 + 評価役の 2 役、計画役は置かない（論点4 案A）

## 影響

### メリット

- 「できました」を信用せず、確実な違反（SP=0 混入・ターン分析）を機械的に検知できる。
  検知漏れや文脈依存の違反（ハルシネーション、従来作の仕様で語る等）は評価役 LLM が
  質・観点抜けとして補う。
- 完成品の形が固定され、回答の粒度が揃う。「次に活かせる結論」が出やすくなる。
- 振り返りがセッション失効後も matchId 単位で引き出せる。過去の結論との比較・積み上げ
  ができるようになる。

### デメリット・トレードオフ

- 評価役 LLM により、振り返り質問のレイテンシとトークンが増える（ほぼ倍）。ただし
  振り返り時のみ起動し、機械的検品だけの質問は増えない。
- 機械的検品の「ポケモン名のハルシネーション検出」は固有名詞辞書の整備が要るため
  TBD とし、今回の実装では見送った。文脈依存の違反は評価役 LLM が検知する。
- 検品は正の方向にしか働かない保証はなく、誤検知（false positive）で回答を削ると
  過修正になりうる。**削るより注記する**方針を優先する。
- `match_reviews` の読み戻しツールは応答サイズを実測してから整形要否を決める必要が
  ある（ADR-0006）。

### 今後チームが意識すべきこと

1. **検品は「削る」より「注記」を優先する**。過修正で会話を止めない（ADR-0011 の方針を踏襲）。
2. **評価役 LLM は振り返り時のみ、1 往復に限る**。Discord の 12 分締切を侵さない。
3. **`match_reviews` への保存は検品通過後**。未検証の回答を正本にしない。
4. **完成品の形は kids / junior で見出しを語彙テーブルに従わせる**（ADR-0003）。
   構成そのものは共通。
5. **ツールを追加したら整形の要否を実測する**（ADR-0006）。`get_match_review` も例外ではない。
6. **行動ログは依然として無い**（ADR-0010）。検品が入っても「ターン分析を語らせない」
   制約は変わらない。
