# COAT V14.0 をアプリへ反映する検討

対象資料: `attachments/attachment-20261015-130022-062-1--_COAT_V14.0_.pdf`
（『競技ポケモンの戦略理論 COAT V14.0』87頁、2026年10月14日、DAHM 1.4）

採用範囲は [ADR-0023](../adr/ADR-0023.md) で確定した。本文書はその判断の根拠と章対応を残す。

## 結論

COAT V14.0 からアプリへ入れる価値があるのは、計算アルゴリズムではなく**助言の作法**である。
具体的には次の4点で、いずれも既存のプロンプト・検品ハーネスを置き換えずに足せる。

1. 当時観測できた情報だけで判断を採点する（第2章・第6章）
2. 助言の出力契約を固定する（第43章）
3. 診断と規範を分離し、固定閾値や重み付き加点を持ち込まない（第50章・第52章）
4. 頻度と発生率、使用率と妨害率を混同しない（第15章・第35章・第48章）

一方で、DAHM の台帳、選出ゲームの線形計画、CFR/PSRO、警報の累積スコアは**採用しない**。
理由は「実装コストに見合う入力データが手元にない」ことと、資料自身が実戦検証 n=0 を明記していること。

## 資料の性格

反映範囲を決める前に、この資料が何であり何でないかを押さえる。

- 研究用の統合理論文であり、将来実装の仕様書。実対戦による効果検証は n=0 と本文が繰り返す。
- 旧版（V13.0〜V13.10）にあった疑似精密な加算式、勝ち筋本数、固定閾値、κ などの合格条件を**明示的に撤回**している。撤回されたものを持ち込むと、資料の主旨と逆行する。
- 「診断」「運用代理」「命題」「観測」「仮説」を毎章で区別する。診断は候補を探す道具であって、構築の合否判定ではない。
- 数値例はすべて人工例として明示される。実在構築の勝率ではない。
- 第53章が記号をプレイヤー語へ翻訳する対応表を用意している。アプリの利用者向け語彙を作る下地としてそのまま使える。

つまり、アプリへ入れるのは理論の全体像ではなく、**助言を書くときの制約と出力の型**である。

## 現在のアプリの助言構造

反映先を整理するため、いま助言がどこで組み立てられているかを確認する。

| 層 | 実装 | 現状 |
|---|---|---|
| システムプロンプト | `rpi-bridge/src/tool-definitions.ts` の `getSystemPrompt()` | ツール連鎖、収録外対応、SP 振り、振り返り手順、振り返り回答の6見出し |
| モード別付加 | `rpi-bridge/src/conversation-manager.ts` の `MODE_INSTRUCTIONS` | kids / junior の語彙と文字数 |
| 会話単位の付加 | 同ファイルの `QUIZ_INSTRUCTIONS` | クイズ形式（ADR-0011） |
| 検品 | `rpi-bridge/src/review-harness.ts` | 機械検品4項目＋評価役LLMの完成条件8項目 |
| 対戦記録 | `match-repository.ts`（ADR-0010/0012/0022） | 選出・構築・自分の行動ログ。相手の行動は無い |
| 過去の振り返り | `match-reviews.ts`（ADR-0017/0021） | 本文を保存し、次回に参照 |

重要な制約が1つある。**利用者は設定画面からシステムプロンプトを保存でき、保存済みプロンプトが既定を上書きする**（`getStoredSystemPrompt`）。`getSystemPrompt()` を書き換えても既存利用者には届かない。このため、COAT 由来の指示は本文へ焼き込まず、`MODE_INSTRUCTIONS` や `QUIZ_INSTRUCTIONS` と同じ**実行時付加レイヤ**として足すのが安全である。

## 採用するもの

### 1. 当時観測できた情報だけで判断を採点する

第2章と第6章の中心。完全状態には相手の持ち物・型・後発が含まれるが、プレイヤーの観測履歴には含まれない。同じ観測履歴には同じ行動分布しか許されない。したがって、対戦後に判明した型を根拠に「あの選出が誤りだった」と断じてはいけない。

アプリへの落とし方。

- 既存の「相手の行動を断定しない」は、この制約の一部（観測に無いものを書かない）である。COAT 版は少し強い。**観測できなかった情報を、判断の評価に使わない**という採点規則まで含む。
- 具体的には「相手の持ち物が○○だったので、あのターンは△△すべきだった」という書き方を禁じ、代わりに「その時点で見えていた情報では□□が妥当だった。○○だった可能性は当時区別できない」と書かせる。
- 第6章の人工例（識別不能な二択で実行可能値は 1/2、全知値は 1）は、この規則が単なる表現の問題ではなく、値を変えるという説明に使える。

検品への落とし方。機械検品では、後から判明した情報を根拠にした断定を正規表現で捉えきれない。評価役 LLM の完成条件に「当時区別できなかった情報で当時の判断を断罪していない」を1項追加するのが現実的である。

### 2. 出力の最小契約

第43章が定める最小契約は次の7項目。

推奨入力／適用する観測条件／主要な理由／代償と例外／証拠の種類／推定の幅／有効期限。

現在の振り返り構成（6見出し）は「事実と解釈の分離」までは持つが、**代償と例外・証拠の種類・推定の幅・有効期限**が無い。構築の修正案を出すときほど、この4つが効く。

- 代償と例外: 「通常時は下がるが特定の相手には上がる」を必ず併記する。
- 証拠の種類: ダメージ計算の結果か、使用率の順位か、こちらの一般論かを区別する。
- 推定の幅: 境界付近なら優劣を確定しない。第15章の q* がその代表例。
- 有効期限: レギュレーションと使用率の時点。ランキングには `updatedAt` を必ず添える既存方針と一致する。

振り返りの見出しを増やすのではなく、「改善候補」の中にこの4項目を要求する形が収まりがよい。

### 3. 診断と規範を分離する

第1章の層の表と第50章の採否表が求めているのは、診断を結論に昇格させないこと。第9章は同じ損失を何度も減点しないことを求める。

アプリでは次の2つを守る。

- 「弱点がある」「回答が1つしかない」は修正候補を作る警報であって、採用・不採用の結論ではない。文面では「〜という穴がある。対策候補は△△だが、通常時の代償と比較が必要」までを1セットにする。
- D・C・Ω・X（削り・主導権・読み・再現しやすさ）を点数化しない。第9章はこれらが終端効用の一意な加算分解ではないと明記する。プロンプトでは説明の観点としてのみ列挙する。

第52章が「根拠のない重み付き加点式を復活させない」と書いているので、アプリ側でスコアを合成する実装は入れない。

### 4. 頻度と発生率を混同しない

第15章の損益分岐（通常時の損失 c、妨害時の改善 g、境界 q* = c/(c+g)）は、修正案の採否を頻度の関数として示す。第35章と第48章は、使用率を妨害の発生率と同一視しないことを繰り返す。

アプリには既に「使用率ランキングは順位のみ」「数値の%は公開されていない」という制約がある。COAT を入れると、この制約がより一般化する。**構築の修正を勧めるときは、頻度の出所を書く**。出所が順位しか無いなら「この順位の相手に当たる頻度は不明なので、修正の優劣は未確定」と明示する。

機械検品に足せる候補。

- 使用率の%を断定する文（ランキングツールは%を返さない）
- 根拠のない勝率%（ダメージ計算ツールは勝率を返さない）

### 5. 記録の分離

第33章は事象の真偽（`C_value`: 1/0/NA）と試行の有無（`attempt`: T/NT/NA）と正式結果（W/D/L）を直交させる。第49章は実務五欄を定める。

現状のアプリは自由記述の振り返りを保存するだけで、事前予測を持たない。このため校正の計算はまだできない。今すぐ構造化スキーマを入れるより、**振り返り本文のなかで3つを混ぜない**ことを徹底するほうが費用対効果が高い。

- 未試行（NT）を不成立（0）へ置き換えない。「やらなかった」と「やっても成立しなかった」を書き分ける。
- 「勝ったから選出が正しかった」を禁じる。結果と判断の妥当性は別である（第30章・第47章）。
- 判定不能（NA）を0にしない。行動ログが空の対戦は「何もしなかった」ではなく「記録が無い」。

将来、事前予測を保存する機能を入れるなら、第49章の実務五欄がそのまま設計図になる。

### 6. 頑健性は「共通方策の存在」で見る

第14章の要点は「各妨害に別々の答えがあるだけでは足りない」こと。識別できない2つの状況で同じ観測に同じ行動を返せなければ、対処が存在しても実行できない。

アプリでは使用頻度が低い概念だが、候補の比較で「対策Aと対策Bは同じ起点に依存していないか」を尋ねる場面では使える。プロンプトに1文だけ入れる。

> 対策を並べるときは、それぞれの対策が同じ駒・同じ持ち物・同じ初手に依存していないか確認する。依存が同じなら、片方を止められて両方失う。

### 7. プレイヤー語への翻訳

第53章の対訳表は、そのままモード別語彙に使える。

| COAT | kids | junior |
|---|---|---|
| 終端効用・勝率 | かつ見込み | 勝率の見込み |
| 臨界事象 C_i | やまば | 山場 |
| 妨害シナリオ r | あいてのじゃま | 相手の止め方 |
| 情報増分 Δ_info | 見てから決める強み | 情報を取ってから選ぶ価値 |
| 未評価質量 ε | まだ見てない分 | 未検討の相手 |
| 通常時の損失 c / 妨害時の改善 g | ふだんの弱まり／じゃまされた時の強まり | 通常時の代償／妨害時の利得 |

既存の kids モードは「数値を並べず感覚で説明」と定めている。COAT の記号をそのまま出すのではなく、この表で言い換える。

### 8. 実戦 n=0 の明示

第46章と第54章が、効果未検証を繰り返し明記する。アプリが COAT の枠組みで助言するとき、**枠組み自体が勝率を上げる証拠は無い**ことを前提に置く。プロンプトには「COAT は助言の整理術であり、これを使うと勝てるという実測はまだ無い」と短く書く。

これは免責文ではなく、断定度を値の不確実性へ合わせるという第43章の要求の一部である。

## 採用しないもの

| 候補 | 理由 |
|---|---|
| DAHM 1.4 の台帳（工程辺・資源更新・抽象化仕様） | 入力になる工程データが無い。概念として「共有入口・共有終点」の説明にだけ借りる |
| 選出ゲームの線形計画、混合保証値 | 相手の選出分布の推定が無い。現在の `analyze_selection` は期待値の見積りであり、保証値と表示しない |
| CFR / PSRO / オフ方策評価 | 計算基盤が無く、対象も将来の研究実装 |
| 警報の反射累積スコアと ARL | 1人・数10戦の記録では校正できない |
| 融合プローブによる情報漏洩検出 | LLM の出力に機械的な入力経路が無い。評価役の文章検査へ縮退させる |
| 固定閾値、重み付き加点、スコア合成 | 第50章が撤回済み |

## 実装案

実装は3ファイルの小さな追加で足りる。大掛かりな構造変更は要らない。

### `conversation-manager.ts`

`QUIZ_INSTRUCTIONS` と同じ位置に `COAT_INSTRUCTIONS` を足し、`getSystemPromptForUser` で常時付加する。利用者ごとの保存プロンプトを壊さずに配れる唯一の経路である。

内容は次の4つのみ。長さは 400〜600 字を目安にする。

1. 当時観測できた情報で判断を採点する（後から判明した型・持ち物で断罪しない）
2. 改善候補には代償・例外・証拠の種類・推定の幅・有効期限を付ける
3. 診断を結論にしない（弱点の指摘は修正候補とセット、点数化しない）
4. 頻度の出所を書く（使用率は順位のみ、境界が不明なら未確定と言う）

### `tool-definitions.ts`

`getSystemPrompt()` の「振り返り回答の構成」に、改善候補の項を1つ足す。ただし既存利用者の保存プロンプトには効かないため、実質は新規利用者向け。既存利用者へは上記レイヤで届く。両方に同じ規則を書くと二重になるので、レイヤを正とし、既定プロンプト側は見出しの文言をそろえる程度に留める。

### `review-harness.ts`

評価役の完成条件に3項を足す。

- 当時区別できなかった情報で、当時の判断を断罪していない
- 改善候補に代償・例外が付いている（断定だけで終わっていない）
- 使用率・勝率の%を、公開されていない数値として断定していない

機械検品には2項を足す。

- 根拠のない勝率%（`\d+[％%][^。\n]{0,8}勝` など）
- 使用率の%断定（ランキングは順位のみ）

### `docs/adr/ADR-0023.md`

「助言の作法として COAT V14.0 の出力契約・観測制約のみ採用する」という1本を起票する。採用範囲と不採用範囲を明記し、後から「COAT 全体を実装しろ」と膨らまないようにする。既存の ADR-0017（振り返り検品）と ADR-0021 を参照する。

## 実装順

1. `COAT_INSTRUCTIONS` の追加（プロンプトのみ。既存挙動を変えない）
2. 検品の評価役条件と機械検品の追加（テストは型チェックのみの現状に合わせ、既存の検品ケースで回帰確認）
3. 実データ1〜2戦で振り返りを走らせ、指摘が過剰に出ないか確認する
4. 問題が無ければ ADR-0023 を起票して確定

手順3が重要である。評価役の条件を増やすと、軽微な表現を毎回指摘して書き直しループに入りやすくなる。既存の「軽微な表現の好みは指摘しない」方針を維持し、追加条件は明確な違反だけに絞る。

## 決定済み（ADR-0023）

- 採用範囲は「観測制約・出力の最小契約・診断と規範の分離・頻度と発生率の分離」の4点。計算系は採用しない。
- 出力の最小契約（代償・推定の幅・有効期限）を必須にするのは、**構築の修正を扱う振り返りに限る**。通常の選出振り返りでは推奨に留める。
- ADR を先に起票してから実装に入る。
- 適用先は `junior` 以上と Discord（`__discord__`）。**kids は対象外**。

## 未決事項

- 事前予測を保存する機能を将来入れるか。入れるなら第49章の実務五欄が設計図になるが、利用者の入力負担が増える。
- 第53章の対訳表を、`tool-progress.ts` の語彙テーブルと同じ場所で管理するか、別ファイルに分けるか。
